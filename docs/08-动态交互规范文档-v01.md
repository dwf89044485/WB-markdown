我会把这份作为 **02 动态交互与渲染流程规范 v0.1**。这一份专门处理“运行过程中信息如何逐步出现、更新、折叠、展开、下钻”，会采纳你原文里关于渐进披露、等待体验、错误/重试/修复、状态体系、控制权按场景出现、完成态验收等内容。你的原文已经明确：主对话流默认服务结果、过程信息默认收起；透明不是默认裸露，而是需要时可追溯；等待越久状态越要具体；错误不隐藏但要分层展示；完成态应该像任务验收，而不是普通回复结尾。




Writing

Agent Run 动态交互与渲染流程规范 v0.1
1. 文档目的
本文定义 Agent Run 在运行过程中的动态交互与渲染规则。
如果《Agent Run 对话流体验规范》回答的是：
信息有哪些层级，应该放在哪里？
那么本文回答的是：
信息什么时候出现、如何更新、什么时候折叠、如何展开、如何下钻？
本文关注：
用户发起任务后界面如何进入执行态；
思考、规划、执行节点如何逐步出现；
节点状态如何变化；
长任务等待时如何表达推进感；
复杂节点如何展示工具、文件、命令等事件；
任务完成后如何切换到结果交付态；
用户如何从结果回溯过程；
错误、重试、恢复、等待确认如何动态呈现。
本文不定义：
后端字段；
LLM 协议；
工具调用 schema；
真实数据结构；
完整 mock 数据；
生产级动画细节。
2. 总体动态原则
Agent Run 的动态体验应遵循一条主线：
```
用户委托
→ Agent 开始理解
→ 生成执行计划
→ 执行节点逐步出现
→ 节点状态持续更新
→ 复杂事件可下钻查看
→ 任务完成
→ 结果交付
→ 过程折叠为可追溯入口
```
核心原则：
运行中，让用户感知过程还在推进；完成后，让用户优先看到干净结果。
3. 两种主要视图状态
Agent Run 在视觉上至少有两种主要视图状态。
3.1 执行过程态
任务尚未完成时，界面处于执行过程态。
此时用户最关心：
Agent 是否已经开始；
当前正在做什么；
是否还在推进；
是否卡住；
是否需要我确认；
是否可以停止或补充要求。
执行过程态的主角是过程，但过程仍然需要被组织，而不是变成日志流。
3.2 结果交付态
任务完成后，界面切换为结果交付态。
此时用户最关心：
最终结果是什么；
交付物在哪里；
哪些完成了；
哪些部分完成或失败；
下一步可以做什么。
结果交付态的主角是结果，执行过程默认折叠为入口。
核心规则：
```
执行中：过程优先可感知
完成后：结果优先可验收
```
4. 动态流程总览
Agent Run 的推荐动态流程如下。
```
Step 0 用户发送消息
Step 1 创建 Agent Run
- 显示 Agent 已开始处理
- 出现基础状态区
- 开始计时
Step 2 任务理解 / 规划
- 显示“任务理解中”或“正在拆解任务”
- 可逐步出现任务理解摘要
- 完成后生成第一个节点
Step 3 执行计划形成
- 展示预计执行阶段
- 阶段可以先以 pending 状态出现
- 当前阶段进入 running 状态
Step 4 节点逐步执行
- 当前节点持续更新
- 已完成节点收起为摘要
- 新节点逐步出现
Step 5 复杂事件出现
- 工具、技能、文件、命令等以事件摘要出现
- 详情默认不展开
- 用户可点击进入浮层
Step 6 异常 / 重试 / 恢复
- 轻量提示异常
- 展示重试或恢复状态
- 已恢复异常不抢占主流程
Step 7 任务完成
- 执行过程收束
- 结果生成
- 进入结果交付态
Step 8 用户追溯
- 点击执行过程入口
- 展开过程总览
- 展开节点
- 打开事件详情
- 进入工具 / 命令浮层
```
5. Step 0：用户发送消息
用户发送一条委托型消息后，系统应将其识别为一次 Agent Run 的开始。
示例：
```
帮我规划一次关西家庭旅行，并生成一份完整文档。`
此时界面不应只等待最终回答，而应准备进入任务执行体验。
设计重点：
用户消息保留在主对话流；
Agent 回复区进入运行态；
不要立即输出长篇假结果；
不要只显示空泛的“Thinking...”。
6. Step 1：创建 Agent Run
Agent Run 创建后，应立即给用户明确反馈。
6.1 推荐展示
`正在处理你的任务
已开始理解需求 · 已用 00m03s
```
或：
```
正在生成旅行方案
当前：理解任务与约束 · 已用 00m12s
```
6.2 必须表达
任务已开始；
当前阶段；
时间感；
可继续观察；
必要时可停止或补充要求。
6.3 不推荐
`Thinking...`
```
正在处理...`
这类表达缺少状态信息，无法支撑长任务等待。
7. Step 2：任务理解 / 规划
Agent 开始理解用户目标时，可以展示任务理解或规划过程。
这里要注意：展示的是**产品化的任务理解**，不是原始思考。
7.1 推荐节点名称
任务理解与分解
```
`确认目标与约束`
```
生成执行计划`
7.2 运行中展示
`任务理解与分解 · 进行中
正在识别目标、约束和交付物...
```
7.3 完成后展示
```
✓ 任务理解与分解
已明确目标、关键约束和后续执行步骤
```
7.4 展开后可展示
```
目标：
生成一份可直接查看的旅行方案文档。
关键约束：
- 家庭出行
- 行程不要过度紧张
- 需要交付文档
阶段产出：
已将任务拆分为信息补充、路线规划、预算整理和文档生成。
```
7.5 不应默认展示
原始模型思考；
未整理的推理过程；
大段内部分析；
中英文混杂的 debug 文本。
8. Step 3：执行计划形成
当任务被拆解后，可以展示计划中的主要阶段。
8.1 阶段可以预先出现
适合长任务，让用户知道接下来会发生什么。
```
执行计划
○ 任务理解与分解
○ 补充搜索相关信息
○ 整理方案内容
○ 生成交付文档
```
8.2 阶段也可以逐步出现
适合不确定性较高的任务。
```
✓ 任务理解与分解
● 补充搜索相关信息
```
后续阶段在 Agent 确认需要时再出现。
8.3 建议规则
简单任务：不必展示完整计划；
中等任务：展示当前阶段 + 下一阶段；
长任务：展示完整阶段列表；
不确定任务：阶段逐步出现，避免承诺过早。
9. Step 4：执行节点逐步运行
执行节点是动态过程中的核心结构。
节点状态应随着执行进度不断更新。
9.1 节点状态
体验层建议使用以下状态表达：
```
未开始
进行中
已完成
部分完成
失败
重试中
已恢复
已跳过
等待用户
需要确认
```
9.2 状态展示权重
不同状态展示强度不同：
```
已完成：弱展示
进行中：中强展示
等待用户：强展示
失败：强展示
重试中：中强展示
已恢复：轻提示
已跳过：轻提示
```
9.3 节点运行中
```
● 补充搜索相关信息
正在查询交通、景点和天气信息...
```
9.4 节点完成后
```
✓ 补充搜索相关信息
已补充交通、景点和天气信息
```
9.5 节点部分完成
```
◐ 补充搜索相关信息
已完成交通和景点查询，天气信息使用历史参考
```
9.6 节点失败
```
× 生成交付文档
文档生成失败，可重试或查看原因
```
9.7 节点恢复后完成
```
✓ 生成交付文档
生成过程中遇到格式问题，已自动修复
```
10. Step 5：节点内容如何展开
节点默认应以摘要形式展示。
用户点击节点后，展开节点详情。
10.1 默认收起时展示
```
✓ 任务理解与分解
已明确目标、约束和执行步骤 >
```
10.2 展开后展示
```
任务理解与分解
目标：
...
关键约束：
...
子任务：
...
```
10.3 展开内容应包括
节点目标；
关键判断；
阶段产出；
发生的异常摘要；
是否可以继续下钻。
10.4 展开内容不应包括
全量工具日志；
完整命令输出；
复杂错误堆栈；
未整理的原始思考。
11. Step 6：复杂节点的事件流
当一个节点内部包含多种动作时，不应把所有细节摊开。
应先展示事件摘要。
11.1 适合形成事件的动作
```
调用技能
执行命令
创建文件
读取文件
编辑文件
搜索网页
检索文件
生成图片
检查结果
修复错误
```
11.2 事件摘要展示
```
整合信息并输出文档
已调用文档技能 >
已创建文件 >
已读取并编辑文件 >
已检查并修复格式问题 >
```
11.3 事件摘要规则
事件摘要应表达：
做了什么；
是否完成；
是否可下钻；
是否影响结果。
事件摘要不应默认展示：
命令全文；
工具参数；
输出全文；
文件全文；
错误堆栈。
11.4 事件语言
L3 可以使用事件语言，例如：
```
已调用技能
已创建文件
已执行命令
已编辑文件
```
但仍应避免变成工具日志流。
12. Step 7：工具 / 技能详情浮层
当用户点击事件摘要时，进入工具或技能详情浮层。
12.1 触发方式
用户点击：
```
已调用文档技能 >`
打开浮层。
12.2 浮层内容
`过程
调用技能：docx
用途：创建和编辑 Word 文档
相关动作：
- 检查文档能力
- 创建文档
- 编辑文档内容
查看命令详情 >
```
12.3 浮层承载原则
浮层用于承载高密度过程信息。
适合放：
工具名称；
技能名称；
技能用途；
动作摘要；
命令入口；
文件操作入口。
不适合放：
最终结果正文；
用户主要结论；
大段完整文档内容。
12.4 返回规则
用户应能明确返回上一级。
```
命令详情
← 返回过程
```
或关闭浮层回到对话流。
13. Step 8：原始命令 / 输出详情
当用户继续点击命令或原始记录时，进入更深层详情。
13.1 展示内容
```
命令：
which node && node -v
输出：
/root/.nvm/versions/node/...
v22.22.2
```
13.2 适合展示
原始命令；
原始输出；
原始错误；
文件路径；
环境信息；
执行结果。
13.3 交互建议
可以提供：
```
复制命令
复制输出
查看完整日志
```
13.4 展示边界
原始命令和输出不应进入主对话流。
它们只应该在用户主动深层追溯时展示。
14. 执行过程到结果交付的切换
任务完成后，界面应发生一次明显的主次切换。
14.1 切换前
执行过程态中，用户看到：
```
正在生成旅行方案
当前：整合信息并输出文档
已完成 3/4 个阶段
```
14.2 切换时
系统应收束执行过程，并提示结果正在生成。
```
所有阶段已完成，正在整理最终结果...`
14.3 切换后
进入结果交付态。
`总结
所有任务已完成。
交付物
查看旅行方案 v1.0
方案概要
...
```
执行过程折叠为入口：
```
执行过程 · 19m40s · 已完成 >`
14.4 核心规则
完成后不应继续把过程流挂在结果前面。
结果应该成为主内容，过程成为可追溯证据。
15. 完成态后的过程追溯
任务完成后，用户仍然可以展开过程。
15.1 默认状态
`结果区
执行过程 · 19m40s · 已完成 >
```
15.2 点击执行过程后
```
执行过程 · 19m40s
思考与规划 >
✓ 任务理解与分解 >
✓ 补充搜索相关信息 >
✓ 生成地点图片 >
✓ 整合信息并输出文档 >
```
15.3 点击节点后
```
任务理解与分解
目标：
...
关键约束：
...
阶段产出：
...
```
15.4 点击复杂事件后
打开浮层：
```
过程
调用技能：docx
执行命令 >
```
15.5 点击命令后
进入原始记录：
```
命令
...
输出
...
```
16. 错误、重试与恢复的动态展示
错误是 Agent 执行过程的一部分，不应隐藏。
但错误展示需要分层。
16.1 运行中发生错误
如果错误正在影响当前节点，应在当前节点轻量提示。
```
● 生成文档
文件生成遇到问题，正在自动修复...
```
16.2 重试中
```
↻ 生成文档
第一次生成失败，正在重试...
```
16.3 已恢复
```
✓ 生成文档
生成过程中遇到格式问题，已自动修复
```
16.4 未恢复
```
× 生成文档
文档生成失败，可以重试或查看原因
```
16.5 完成态中的错误表达
如果错误已恢复且不影响结果：
```
执行过程曾出现格式问题，已自动修复，最终文档已生成。`
如果错误导致部分完成：
`部分完成：
天气信息未能获得实时数据，已使用历史气候参考。
```
如果错误导致失败：
```
失败或受限：
文档生成失败，当前仅提供文本方案。
```
16.6 原始错误
原始错误不进入结果层。
应进入深层追溯：
```
错误详情 >
命令输出 >
原始日志 >
```
核心规则：
运行中说明正在处理什么问题；完成后说明问题是否影响结果；原始错误进入深层追溯。
17. 等待用户确认
当 Agent 需要用户确认时，状态应从自动执行切换为等待用户。
17.1 触发场景
包括：
发送邮件；
覆盖文件；
删除内容；
发布内容；
创建日历；
下单或支付；
修改第三方系统数据；
访问敏感内容。
17.2 展示方式
```
需要确认
即将创建日历草稿。
这会在你的日历中新增 7 天行程安排。
操作：
允许
先预览
修改
拒绝
```
17.3 运行状态
等待用户时，应明确阻塞关系。
```
等待用户确认 · 后续步骤将在确认后继续`
17.4 确认后
`✓ 已确认
继续创建日历草稿...
```
17.5 拒绝后
```
已跳过创建日历草稿
继续生成旅行方案文档
```
核心规则：
信息型任务可以继续执行；行动型任务必须确认后执行。
18. 用户运行中控制
运行中，用户可以有有限控制权。
18.1 可提供操作
```
停止
补充要求
查看过程
```
视具体产品复杂度，也可以提供：
```
暂停
继续
```
18.2 不建议常驻堆满
不要在所有状态下长期显示大量控制按钮。
控制项应按场景出现。
18.3 用户补充要求
用户补充要求后，Agent Run 可以进入调整状态。
```
已收到补充要求
正在调整后续方案...
```
如果补充要求影响已完成节点，应明确说明：
```
新的要求会影响已生成的路线规划，正在重新整理相关部分。`
19. 部分完成状态
不是所有任务都只有成功或失败。
部分完成需要明确表达。
19.1 运行中部分完成
`◐ 补充搜索相关信息
交通和景点信息已完成，天气信息暂不可用
```
19.2 完成态部分完成
```
部分完成：
天气信息未能获得实时数据，已使用历史气候参考。
```
19.3 过程层说明
```
补充搜索相关信息 · 部分完成
天气查询失败，已使用历史气候数据替代。
```
19.4 原始追溯
```
天气 API 超时
使用历史气候来源替代
```
20. 跳过状态
当某个步骤被跳过时，应说明原因。
20.1 自动跳过
```
已跳过创建日历草稿
原因：该动作需要用户确认，当前仅生成文档。
```
20.2 用户选择跳过
```
已跳过图片生成
继续生成文本方案。
```
20.3 展示原则
跳过不一定是失败，但应可追溯。
21. 取消状态
用户停止任务时，应进入取消状态。
21.1 取消中
```
正在停止任务...`
21.2 已取消
`任务已取消
已完成：
- 任务理解与分解
- 部分信息搜索
未完成：
- 文档生成
- 最终方案整理
```
21.3 已有部分产物
如果已有部分结果，应展示：
```
可用内容：
查看已整理的信息摘要
```
取消态也应支持过程追溯。
22. 信息加载规则
Agent 运行中，信息应逐步出现，而不是一次性铺满。
22.1 推荐加载顺序
```
1. Run 状态
2. 当前阶段
3. 阶段列表
4. 当前节点摘要
5. 节点内事件
6. 工具 / 技能详情入口
7. 原始记录入口
8. 最终结果
```
22.2 节点加载
节点可以在两种模式下加载：
模式 A：计划先行
适合可预期任务。
```
○ 任务理解
○ 信息搜索
○ 方案整理
○ 文档生成
```
模式 B：过程生长
适合探索型任务。
```
✓ 任务理解
● 正在补充搜索
```
后续节点随着执行逐步出现。
22.3 内容加载
节点内容不应在列表层全部展开。
默认只展示节点标题和一句摘要。
点击后再展示详情。
23. 折叠规则
折叠的目的不是隐藏，而是维持主阅读路径。
23.1 完成前折叠
运行中，已完成节点可以自动收起为摘要。
```
✓ 任务理解与分解
已明确目标、约束和执行步骤 >
```
当前运行节点保持展开或半展开。
23.2 完成后折叠
任务完成后，整个执行过程默认折叠。
```
执行过程 · 19m40s · 已完成 >`
23.3 异常节点折叠
已恢复异常可折叠为轻提示。
`✓ 生成文档
曾遇到格式问题，已恢复 >
```
未恢复异常应保持显著。
```
× 生成文档
失败，可重试或查看原因
```
24. 展开规则
展开应遵循逐级披露。
```
执行过程
→ 阶段节点
→ 节点详情
→ 节点事件
→ 工具详情
→ 原始记录
```
24.1 不允许跨级暴露
不建议从 L1 直接展示 L5 原始命令。
例如不推荐：
```
执行过程列表中直接显示完整命令输出`
24.2 允许快捷入口
对于高级用户，可以在合适位置提供：
查看原始记录
```
但仍应进入浮层或详情页，而不是直接展开在主流。
25. 浮层下钻规则
浮层用于承载高密度信息。
25.1 一级浮层
承载：
工具详情；
技能详情；
文件操作详情；
事件详情。
25.2 二级浮层
承载：
原始命令；
原始输出；
错误堆栈；
原始日志。
25.3 浮层关系
```
对话流
→ 事件详情浮层
→ 命令 / 输出详情浮层
```
25.4 返回规则
必须保证用户能回到上一层：
```
命令详情
← 返回过程
```
或关闭回到主对话流。
26. 结果交付态渲染规则
结果交付态应优先渲染结果，而不是过程。
26.1 推荐顺序
```
1. 总结
2. 交付物
3. 关键结果 / 方案概要
4. 部分完成 / 失败 / 受限
5. 需要确认
6. 下一步
7. 执行过程入口
```
26.2 简单任务
简单任务可以压缩：
```
已完成。
这是整理后的摘要：
...
执行过程 · 01m12s >
```
26.3 复杂任务
复杂任务应使用验收结构：
```
总结
已完成：
...
部分完成：
...
失败或受限：
...
交付物：
...
下一步：
...
```
26.4 执行过程入口位置
执行过程入口可以放在：
Agent 回复顶部的状态区域；
结果区之后；
交付物附近的辅助信息区。
但不应抢占结果正文。
27. 交付物出现规则
交付物是结果对象，应在生成后明确出现。
27.1 运行中生成
如果交付物在执行中已生成但仍需完善：
```
文档草稿已创建，正在补充内容...`
27.2 完成后生成
`交付物
查看旅行方案 v1.0
```
27.3 多交付物
```
交付物
- 旅行方案文档
- 预算表
- 邮件草稿
```
27.4 交付物状态
交付物应表达：
```
草稿中
已生成
已更新
部分生成
生成失败
```
28. “思考过程”的展示规则
“思考过程”容易被误解，需要谨慎命名和分层。
28.1 推荐命名
优先使用：
```
任务理解
执行计划
关键判断
```
而不是默认使用：
```
原始思考`
28.2 可见内容
可以展示：
目标理解；
约束识别；
任务拆分；
选择依据摘要。
28.3 不默认展示
不默认展示：
未整理的推理；
原始模型思考；
中英文混杂内部记录；
和用户结果无关的尝试过程。
28.4 深层追溯
如果产品需要提供原始思考，应放入深层追溯，并与执行日志、最终结果分开。
29. 动态文案原则
动态过程中的文案要服务状态理解。
29.1 避免空泛
不推荐：
`请稍候...
正在处理...
Thinking...
```
推荐：
```
正在补充交通与景点信息 · 第 2/4 步 · 已用 03m12s`
29.2 状态 + 动作 + 进度
好的动态文案通常包含：
`当前动作
当前阶段
进度
耗时
是否需要用户参与
```
29.3 异常文案
异常文案要说明影响。
```
文件生成遇到格式问题，正在自动修复。`
比：
Error
```
更适合上层展示。
30. 典型交互链路
以下是一个标准追溯链路。
```
完成态
用户看到总结和交付物
点击执行过程
展开过程总览
点击节点
展开节点摘要
点击复杂事件
打开工具 / 技能浮层
点击命令详情
打开原始命令 / 输出
关闭浮层
回到节点
收起执行过程
回到结果
```
这个链路对应的设计目标是：
结果型用户不用看过程，审核型用户可以看节点，高级用户可以追到原始记录。
31. 动态体验验收 Checklist
设计或评审 Agent Run 动态流程时，可以检查：
```
1. 用户发起任务后，是否立刻知道任务已开始？
2. 运行中是否能看到当前阶段，而不是只有 Thinking？
3. 长任务是否能感知进度、耗时或阶段推进？
4. 执行节点是否逐步出现，而不是一次性堆满？
5. 当前运行节点是否突出？
6. 已完成节点是否能弱化或收起？
7. 复杂节点是否先展示事件摘要，而不是直接展示日志？
8. 工具、技能、命令是否通过浮层下钻？
9. 发生错误时，用户是否知道是否影响结果？
10. 已恢复错误是否轻提示，而不是抢占主流程？
11. 等待用户确认时，是否明确阻塞关系和可选动作？
12. 任务完成后，是否切换为结果优先？
13. 完成后执行过程是否默认折叠？
14. 用户是否能从结果逐级追溯到过程、节点、事件、原始记录？
15. 交付物是否在生成后被明确呈现？
```

33. 总结
Agent Run 的动态体验不是简单地“边想边输出”，而是一个有秩序的信息生成与收束过程：
运行中，逐步展示任务推进；
复杂处，先摘要再下钻；
出错时，说明影响并保留追溯；
需要用户时，明确等待与选择；
完成后，过程退后，结果前置；
想追溯的人，可以一层一层查到底。
