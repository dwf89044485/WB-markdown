# AskQuestion 交互设计文档

> 组件：AskQuestion · 询问用户
> 状态：v1 草稿（待审查）
> 最后更新：2026-06-15

---

## 1. 概述

### 1.1 定义

AskQuestion 是 agent 在执行任务过程中遇到不确定时，**暂停输出并向用户发起结构化提问**的对话内嵌组件。

### 1.2 使用场景

- 用户初始指令不完整，agent 需要补全关键信息再继续
- agent 面临两个及以上合理执行路径，选错代价高
- 用户输入存在歧义，agent 不愿擅自"翻译"成熟悉的意图

### 1.3 不适用场景

- 信息可以从上下文/工具调用中获取，无需打扰用户
- 决策可逆且代价低（agent 应自行判断）
- 仅为确认意图（用陈述式输出 + 用户被动否认更轻）

### 1.4 设计目标

让 agent 的"不确定"成为一种**可感知、可结构化、低打扰**的协作信号。让用户用最少操作完成确认，让 agent 拿到能直接驱动决策的结构化输入。

## 2. 构成

AskQuestion 卡片自上而下三层结构：

```
┌─────────────────────────────────────┐
│ ① 顶栏  ←  2 / 4  →             ✕  │
├─────────────────────────────────────┤
│ ② 问题区  [多选]  你想要哪几种...    │
├─────────────────────────────────────┤
│ ③ 选项列表                          │
│   1  React          □              │
│   2  Vue            ☑              │
│   3  Angular        □              │
│                                    │
│ ④ 输入栏  我来额外补充说明          │
│ ⑤ 操作按钮              [ 跳过 ]   │
└─────────────────────────────────────┘
```

| 编号 | 部件 | 内容 |
|---|---|---|
| ① | 顶栏 | 左/右导航箭头、步骤指示器（`当前 / 总数`）、关闭按钮 |
| ② | 问题区 | 题型标签（多选/排序题有，单选无）+ 问题文字 |
| ③ | 选项列表 | 选项行（序号 + 文字 + 右侧状态图标） |
| ④ | 输入栏 | 自由文本输入，placeholder 随题型变化 |
| ⑤ | 操作按钮 | 文案与样式随作答状态变化（详见第 8 节）|

## 3. 类型

AskQuestion 支持三种题型，由 agent 在生成问题时声明，用户不可切换。

| 题型 | 用途 | 视觉特征 |
|---|---|---|
| **单选** | 用户从互斥选项中选一个；最常见 | 选项右侧无图标；选中显示 `✓` |
| **多选** | 用户从可叠加选项中选多个；问题区带「多选」药丸 | 选项右侧有方框复选符；选中变实心 ☑ |
| **排序** | 用户对选项排优先级；问题区带「排序」药丸 | 选项右侧有 `≡` 拖拽手柄；序号动态跟随位置 |

### 3.1 题型选择原则（给 agent 的指引）

- **单选 vs 多选**：选项之间互斥用单选，可叠加用多选
- **多选 vs 排序**：只关心"选了什么"用多选，关心"先后/优先级"用排序
- **排序题不出现"跳过"**：选项顺序始终存在，没有"未答"的状态

## 4. 状态

### 4.1 选项行（option）

#### 单选

| 状态 | 行背景 | 序号字重 | 文字字重 | 右侧 |
|---|---|---|---|---|
| 未选 | `#FAFAFA` | Regular | Regular | 无 |
| 选中 | `#F2F2F2` | Semibold | Semibold | `✓` |

#### 多选

| 状态 | 行背景 | 序号字重 | 文字字重 | 右侧 |
|---|---|---|---|---|
| 未选 | `#FAFAFA` | Regular | Regular | □（白底，`#D5D5D5` 边框，8px 圆角） |
| 选中 | `#F2F2F2` | Semibold | Semibold | ☑（`#3D3D3D` 填充，白色 ✓） |

#### 排序

| 状态 | 行背景 | 序号 | 文字字重 | 右侧 |
|---|---|---|---|---|
| 默认 | `#FAFAFA` | 动态序号（跟随位置） | Regular | `≡` 拖拽手柄 |
| 拖拽中 | 提升阴影 + 半透明 | 动态序号 | Regular | `≡` |
| 落定后 | `#F2F2F2` | 动态序号（已重排） | Regular | `≡` |

### 4.2 操作按钮

| 条件 | 文案 | 样式 |
|---|---|---|
| 未答 + 非最后题 | 跳过 | 浅灰 `#F4F2F2`，深字 |
| 未答 + 最后题 | 跳过 | 浅灰，深字 |
| 已答 + 非最后题 | 下一步 | 深色 `#3D3D3D`，白字 |
| 已答 + 最后题 | 提交 | 深色，白字 |
| 排序题 + 非最后题 | 下一步 | 深色，白字 |
| 排序题 + 最后题 | 提交 | 深色，白字 |

**"已答"判定**（排序除外）：选项已选中 或 输入框非空。

### 4.3 步骤指示器与导航箭头

- **指示器**：`当前题序号 / 总题数`
- **左箭头**：当前为第 1 题时不可点（视觉降饱和度）
- **右箭头**：当前为最后题时不可点

## 5. 交互行为

### 5.1 单选

| 操作 | 反馈 |
|---|---|
| 点未选项 | 选中该项 → 其他项取消 → 输入框文字清空 → **非最后题自动前进到下一题** |
| 点已选项 | 取消选中，回到未选状态，留在当前题 |
| 在输入框打字 | 已选选项清空（互斥）→ 不自动前进 → 需手动按按钮 |

**自动前进只发生在"点击选中"瞬间**；从输入栏切到选项、或修改已选项不触发。

### 5.2 多选

| 操作 | 反馈 |
|---|---|
| 点选项 | toggle 选中/取消，可同时多选 |
| 点已选项 | 取消该项 |
| 在输入框打字 | 已选选项**保留**（共存），不自动前进 |

**多选不自动前进**——因为系统无法判断用户是否已选完，由用户主动按"下一步"。

### 5.3 排序

| 操作 | 反馈 |
|---|---|
| 按下选项并位移 ≥ 3px | 进入拖拽模式（选项浮起、原位透明占位） |
| 拖动 | 其他项让位，序号实时跟随位置更新 |
| 松手 | 200ms 缓动落位（cubic-bezier(0.2, 0, 0, 1)） |
| 在输入框打字 | 排序结果保留，不自动前进 |

**桌面端与移动端拖拽起始方式一致**——都是"按下后位移 ≥ 3px 即触发"，**不需要长按**。3px 容差防止误触（用户在选项行内点击或滑动屏幕时不会误触发拖拽）。

**首次进入排序题时**，会出现循环 pop 动效引导用户拖拽（"拖动我"提示）。**用户首次拖动后，提示永久消失**——这是"教学一次后即退出"的引导原则。

### 5.4 题间导航

| 操作 | 效果 |
|---|---|
| 左箭头 | 上一题（边界时不可点） |
| 右箭头 | 下一题（边界时不可点） |
| 关闭 ✕ | 退出问答，**所有题视为跳过**，agent 拿到空答案继续 |

**切题保留状态**：用箭头切走再切回来，之前的选择/输入/排序顺序全部保留。这一点对多题问答的体验至关重要——用户来回核对答案不丢数据。

### 5.5 提交与结束

三种结束方式，agent 收到的数据形态都是统一格式（详见附录），区别在于答案的"完整度"：

| 结束方式 | 数据特征 |
|---|---|
| 最后一题点"提交" | 各题答案如实回传，未答题字段为 null/空 |
| 任意时点"关闭 ✕" | 所有题视为跳过，所有字段为 null/空 |
| 跳过到最后再提交 | 等同于 1，未答的为空 |

## 6. 使用流程

```
agent 输出中
   │
   ▼
遇到不确定 → 暂停输出 → 对话流底部展开问答卡片
   │
   ▼
逐题作答（任意顺序、任意跳过）
   │
   ├─ 单选：点选项自动前进（最后题除外）
   ├─ 多选：点选项 toggle，手动按"下一步"
   └─ 排序：按下即拖（3px 触发，无需长按），手动按"下一步"
   │
   ▼
最后题作答完 → 按钮文案变"提交"
   │
   ├─ 点提交 → 卡片消失 → agent 收到结构化答案 → 继续输出
   └─ 点关闭 → 卡片消失 → agent 收到空答案 → 继续输出
```

## 7. 边界与异常

### 7.1 内容相关

| 情况 | 处理 |
|---|---|
| 问题文字过长 | 自然换行，问题区高度自适应 |
| 选项过多（≥ 8 项） | 选项列表内部纵向滚动，顶栏与按钮固定 |
| 单个选项文字过长 | 选项行内自然换行，序号顶部对齐 |
| 选项数 = 0 | 不应渲染（agent 出题责任） |
| 选项数 = 1 | 单选退化为"确认"，仍可正常作答 |

### 7.2 用户行为相关

| 情况 | 处理 |
|---|---|
| 中途关闭页面 | 不保存草稿，下次进入相当于全部跳过 |
| 误触关闭按钮 | 无二次确认（轻量打扰原则）—— 内容损失代价低，相比每次都拦截，让误触承担一次成本更合理 |
| 切题后回来发现状态丢失 | 不应发生（见 5.4），若发生为 bug |
| 输入框输入超长文字 | 输入框自适应高度，最多展开 4 行后内部滚动 |

### 7.3 输入与选项的互斥规则

| 题型 | 用户输入文字时 | 用户点选项时 | 提交结果 |
|---|---|---|---|
| 单选 | 已选项**清空** | 输入框**清空** | 选项 / 输入二选一 |
| 多选 | 已选项**保留** | 输入框**保留** | 选项 + 输入并存 |
| 排序 | 排序结果**保留** | — | 顺序 + 输入并存 |

**理由**：
- 单选语义本身互斥——"选项"与"自定义输入"是同一题的两种回答路径
- 多选/排序的"自定义输入"是补充说明，不替代选项

## 8. 文案规范

### 8.1 问题区文案

由 agent 生成。设计层不规定句式，但建议：
- **避免双重否定**："不要不告诉我..."→"请告诉我..."
- **题干自闭合**：不依赖前文上下文也能读懂
- **给出选项的语境**：必要时在题干后加一行说明

### 8.2 输入栏 placeholder

| 题型 | placeholder |
|---|---|
| 单选 | `以上都不是，我来告诉你` |
| 多选 | `我来额外补充说明` |
| 排序 | `我来额外补充说明` |

**单选 placeholder 强调"以上都不是"**——明确告诉用户这是 escape hatch，避免用户在选项里硬选一个不满意的。

### 8.3 操作按钮文案

随状态变化，详见 4.2 节状态表。文案逻辑：
- **跳过** = 用户没作答，按钮提示"你可以不答，我们继续往下"
- **下一步** = 用户已作答，按钮承诺"答案已记录，我们前进"
- **提交** = 已是最后题，按钮承诺"全部完成，agent 继续工作"

文案随状态切换是无感的——背景色变化是主信号，文案变化是辅助。

### 8.4 关闭按钮无文案

仅 ✕ 图标。点击行为是"全部跳过"，但**不在按钮上写"跳过全部"**——避免与"跳过"按钮的语义混淆。用户预期 ✕ = 关闭/退出，符合通用 UI 直觉。

## 9. 响应式 / 适配

### 9.1 卡片宽度

- 在 demo 内嵌 iPhone 壳里渲染，宽度跟随对话气泡宽度（375px 容器内自适应）
- 卡片左右各保留 12px 安全边距

### 9.2 高度策略

- 默认高度自适应内容
- 选项数过多时（详见 7.1），选项列表区内部滚动，顶栏和按钮始终可见

### 9.3 键盘弹起

输入框获得焦点时，**输入栏与按钮必须保持完全可见**，不被软键盘遮挡。

**设计层约束（必须满足）：**
- 输入栏底部至软键盘顶部 ≥ 16px 的可视边距
- 题目文字、当前选中项、操作按钮均不被遮挡
- 卡片移动过程平滑（不闪、不跳）

**实现层建议方案**（三选一，由前端实现层结合容器结构定夺）：
- 方案 A：监听 `visualViewport.resize`，键盘弹起时整张卡片向上位移
- 方案 B：聚焦时调用 `inputEl.scrollIntoView({ block: 'center' })`
- 方案 C：外层容器使用动态 `padding-bottom` 留出键盘高度

设计层不锁定具体方案，但**必须验收"输入栏与按钮始终可见"** 这一硬约束。

## 10. 动效

> 这一节规定动效的**设计意图与节奏分级**，不规定具体 easing / duration 参数（参数由视觉规范层定夺）。

### 10.1 动效节奏分级

将本组件的所有动效按"用户感知优先级"分为三档：

| 档次 | 用途 | 节奏 | 示例 |
|---|---|---|---|
| **快**（瞬时反馈） | 用户操作的即时回应——必须感觉"零延迟" | 100-150ms | 选项点击的背景色变化、按钮按下态、复选框打勾 |
| **中**（状态过渡） | 题与题切换、卡片内容变化——需要让用户"看懂"变化路径 | 200-300ms | 切题时的卡片淡入淡出、排序拖拽落位（当前实现 200ms）、按钮文案与底色切换 |
| **慢**（引导动效） | 教学性、引导性动效——需要被注意到 | 600-1000ms | 排序题首次的 pop 拖拽提示、卡片首次出现的展开动效 |

### 10.2 关键动效的设计意图

| 动效 | 意图 |
|---|---|
| **卡片首次展开** | 让用户感知"agent 主动停下并提问"——不是闪现，是缓缓展开。让"被打断"变成被引导，而非被打扰 |
| **单选自动前进的切题动画** | 让用户看见"下一题被推到面前"，而不是题目无声替换。建议方向上一致（如向左滑出旧题、向右滑入新题），形成一致的方向感 |
| **多选 toggle 反馈** | 必须"快"——用户连续点选多个时，慢动效会累积成卡顿感 |
| **排序拖拽落位** | 用阻尼缓动表达"重量感"——选项不是瞬移到位，是带惯性地落定，强化拖拽的物理直觉 |
| **排序首次 pop 提示** | 节奏要"足够慢、足够大"——这是教学性动效，必须被看到。但**只播一轮，用户操作后立即停止** |
| **按钮"跳过"→"下一步/提交"切换** | 文案与底色同步过渡，**底色变化是主信号、文案变化是辅助**（详见第 8.3 节）。视觉切换平滑但不要太慢，避免用户在快速作答时觉得拖沓 |

### 10.3 动效的反原则

- **不为了动而动**——AskQuestion 本身已经是一次打断，过多装饰性动效会加重打扰感
- **快档动效不允许超过 200ms**——否则点击感会"粘滞"
- **教学性动效绝不重复**——首次播完一轮后永久消失，重复播放是噪音
- **不允许多个动效同时进行**（除非语义关联）——避免视觉混乱

## 11. 可访问性

### 11.1 键盘操作（桌面端）

- `Tab` / `Shift+Tab`：在选项、输入栏、按钮间循环聚焦
- `Space` / `Enter`：选中当前聚焦的选项
- `Esc`：关闭卡片（等同点 ✕）
- `←` / `→`：题间导航（聚焦在选项时不响应，避免误触）

### 11.2 屏幕阅读器

- 题型作为标签朗读："多选题，2 / 4，[问题文字]"
- 选项朗读时带序号："选项 1，React，未选中"
- 状态变化即时朗读："已选中 / 已取消"

**语义标记建议**（实现层参考）：
| 部件 | 语义角色 |
|---|---|
| 单选选项行 | `role="radio"`，外层容器 `role="radiogroup"` |
| 多选选项行 | `role="checkbox"`，外层容器 `role="group"` |
| 排序选项行 | `role="listitem"` + `aria-grabbed`，外层 `role="list"` |
| 步骤指示器 | `aria-label="第 2 题，共 4 题"` |
| 关闭按钮 | `aria-label="关闭问答，全部跳过"` |

设计层规定**语义角色**，具体 attribute 写法由前端实现规范层定夺。

### 11.3 对比度

- 文本与背景对比度 ≥ 4.5:1（WCAG AA）
- 选中态的视觉差异不仅依赖颜色（同时有字重 + 图标）

## 12. 数据埋点（建议）

> 本节为**设计意图沉淀**，不强制实现。如团队接入了数据分析体系，建议追踪以下事件以观测 AskQuestion 的真实使用情况。

### 12.1 关键事件

| 事件名 | 触发时机 | 关键属性 |
|---|---|---|
| `askquestion_shown` | 卡片展示完成 | 题数、题型分布（单/多/排）、本次会话内第几次 ask |
| `askquestion_answered` | 用户点"提交" | 完整率（已答题数/总题数）、自定义输入使用率、用时 |
| `askquestion_skipped` | 用户在某题点"跳过" | 题序号、题型 |
| `askquestion_closed` | 用户点 ✕ 关闭 | 已答题数、关闭时停留题序号 |
| `askquestion_option_selected` | 用户点选项 | 题序号、题型、选项索引、是否触发自动前进 |
| `askquestion_custom_input` | 自定义输入栏 blur 时非空 | 题序号、题型、输入字符数（不上报内容） |
| `askquestion_sort_dragged` | 排序题首次拖拽 | 题序号、是否首次（用于评估首次引导动效效果） |
| `askquestion_step_navigated` | 用户用箭头切题 | 方向（前/后）、当前题序号 |

### 12.2 关键观测指标

埋点的目的是回答这些问题：

- **完成率** = 提交事件 / 展示事件——衡量 AskQuestion 的整体可用性
- **跳过率分布** = 各题被跳过的占比——找出"问得不好"的题目
- **自定义输入使用率** = 用了输入框的题数 / 总题数——衡量"以上都不是"出口的真实价值
- **关闭率分位** = 关闭时已答题数的分布——理解用户在第几题放弃
- **排序题首次引导转化** = 拖拽过的排序题数 / 排序题展示数——评估引导动效是否有效

### 12.3 不追踪的内容

- **不上报用户的具体回答内容**——只统计行为，不收集语义内容
- **不上报问题文字**——agent 生成的问题可能含隐私

## 13. 设计原理

> 这一节解释关键决策的"为什么"，是交互文档与开发文档最核心的差别。

### 13.1 为什么单选自动前进、多选不自动前进

**单选有明确的"作答完成"信号**——选了一个就是答完。多选没有，系统不知道用户是想选 1 个还是 5 个，必须由用户主动声明"我选完了"。

强行让多选自动前进会出现：用户想选 3 个，点完第 1 个就被推到下一题。这是"系统替用户做决定"，违反用户主导原则。

### 13.2 为什么排序题没有"跳过"按钮

排序题的初始状态本身就是一种顺序（agent 给定的原始顺序）。没有"未答"的概念——用户不动，等于接受默认顺序。

把它跟单选/多选一样设"跳过"会造成认知错配："我没拖动过，那我是答了还是没答？"——把这种困惑直接消除，按钮恒定显示"下一步/提交"。

### 13.3 为什么单选选项与输入互斥、多选不互斥

**单选的语义是"在多个互斥项中选一个"**，输入框的"以上都不是，我来告诉你"本身就是一个隐式选项——它和明示选项是互斥关系。

**多选的语义是"在多个可叠加项中选若干"**，输入框是"额外补充"——是叠加的而非替代的。强行互斥会让用户每次输入都丢失已勾选项，体验崩溃。

### 13.4 为什么关闭按钮 = 全部跳过，而不是弹确认框

每多一次确认弹窗，就多一次打断。AskQuestion 本身已经是 agent 对用户的打断，关闭后的二次确认会让"打断"变成"两段式打断"，体验更差。

代价权衡：
- **加确认框**：误触挽回率提升，但每次正常关闭都多一步操作
- **不加确认框**：误触一次损失答题进度（但 agent 会拿到空答案继续，并非灾难）

设计选择**不加**——因为 AskQuestion 的答题成本本身不高（用户花 10-30 秒），误触一次重新答的代价远低于每次都被确认框拦截。

### 13.5 为什么排序题首次有引导动效、之后消失

排序的"长按拖动"对很多用户不是默认认知（尤其桌面端用户习惯点选）。**第一次必须教**，否则用户可能盯着排序题不知道怎么操作。

但**只教一次**——用户拖过一次后即被永久标记"已会用"，再循环引导就是噪音。这是"教学一次后即退出"的引导设计原则。

### 13.6 为什么切题保留状态

多题问答的真实场景：用户答到第 3 题时想回去改第 1 题。如果切走再切回来状态丢失，用户每次切题都要重新答，多题问答就废了。

**保留状态是多题问答能成立的前提**，不是 nice-to-have。

### 13.7 为什么按钮变色 + 改文案两个信号同时给

行动召唤的优先级是视觉 > 文字：
- 用户在快速作答时，**先用余光感知按钮颜色**——浅灰 = "可跳"，深色 = "可前进"
- 真要按之前才会读文案确认

只改文案不改色，用户感知不到状态变化；只改色不改文案，用户不知道点了会发生什么。两个信号叠加，认知负担最低。

## 14. 关联组件 与 Do's / Don'ts

### 14.1 与相似组件的边界

| 组件 | 与 AskQuestion 的差别 |
|---|---|
| 普通输入框（composer） | 用户主动发起；AskQuestion 由 agent 发起 |
| 系统弹窗 / Modal | 全局打断；AskQuestion 在对话流内嵌、不脱离上下文 |
| Inline 选项按钮（如 quick replies） | 单次单选，无多题/排序能力；AskQuestion 是结构化、多题、可结束的会话单元 |
| 表单 Form | 表单是用户主动填写、agent 被动接收；AskQuestion 是 agent 主动询问、用户被动响应。**生命周期不同**：AskQuestion 临时存在（用完即消，不持久化），Form 通常持久化（草稿、历史、可重新打开） |

### 14.2 Do's

- **agent 应在真正不确定时使用**——避免"问以确认"的礼貌性提问
- **题目数量 1-5 题之间**——超过 5 题考虑拆成多轮 AskQuestion 或换成表单
- **选项数控制在 4-6 个**——超过会增加阅读负担
- **题干清晰自闭合**——能脱离上下文独立读懂

### 14.3 Don'ts

- **不要用来确认 agent 的判断**（如"我打算用 React 实现，可以吗？"）—— 这是变相的"确认弹窗"，违反 agent 主导原则
- **不要嵌套 AskQuestion**——一个 AskQuestion 内不再发起新的 AskQuestion
- **不要用单选模拟二元确认**（"继续 / 取消"）——这种应直接用陈述句让用户自然回复，或不问
- **不要让用户在 AskQuestion 中执行复杂任务**（如填长表单）——它是"问询"工具，不是"录入"工具
