## 一、动机

当前 demo 是设计师的交付物，但「单人在会议室演示」和「邮件发出去 20 个人各自看」需要的载体不一样。

后者需要：每个人点开链接，就能看懂做了什么、为什么这么做、怎么实现的，**不需要设计师在旁边解说**。

这是把「口头汇报」升级成「自主阅读的设计交付物」。

---

## 二、读者与场景

| | 设备 | 体验 | 代表谁 |
|---|---|---|---|
| 体验模式 | 手机 | 打开链接直接玩 demo，像真实 app | 上级、产品侧——评判"体验好不好" |
| 研读模式 | 电脑 | 左边玩 demo，右边看说明 | 研发、合作设计师——理解"怎么实现" |

**同一个链接，不同设备自动适配，不部署两份。**

## 三、整体架构

### 1. 布局规则（按屏幕宽度切分，不识别设备类型）

| 屏幕宽度 | 行为 |
|---|---|
| `< 600px` | 纯 demo 模式，手机壳全屏，右侧栏不出现，URL 参数全部忽略 |
| `600 ~ 1440px` | 双栏模式启动。左侧 600px 区（手机壳 550px 在里面居中）+ 右侧 840px 区。**总宽 1440px > 屏幕**，浏览器原生横向滚动条出现，用户拖动横滚条左右切换查看 demo / 说明（不做任何特殊处理） |
| `≥ 1440px` | 双栏模式。左侧固定 600px（手机壳居中）+ 右侧栏自动撑满剩余宽度（最小 840px，无上限） |

**横滚条出现在整个页面**（浏览器底部），不是右侧栏内部。这样用户能感知"右边还有内容，需要往右看"。

**为什么不识别设备类型：** 浏览器没有可靠的"我是平板"信号；屏幕尺寸不等于设备类型；真正决定显示与否的是物理宽度。用 `matchMedia` 监听变化，用户拖窗口或旋转 iPad 自动切换布局。

## 五、URL 与路由

### 1. URL 形态

| URL | 显示内容 |
|---|---|
| `/` | 默认 = 总览 |
| `/?view=overview` | 总览 |
| `/?view=feature&id=<功能id>` | 对应功能详解 tab |

### 2. 边界规则

| 场景 | 处理 |
|---|---|
| URL 无参数 | 进总览 |
| 未知 `id`（如 `id=xxx` 不存在） | 直接回总览，不提示 |
| 手机端打开任意 URL | 参数全部忽略，永远显示纯 demo |

### 3. 导航交互

- **下拉切 tab** → URL 自动更新 + 写入浏览器历史
- **浏览器后退/前进** → 右侧 tab 跟着切，左侧 demo 不动
- 写入历史的理由：研发会在不同 tab 间来回看，后退键当"撤销切 tab"用，符合直觉

## 六、左右联动规则

### 1. 单向联动

| 方向 | 是否联动 |
|---|---|
| 左 → 右 | **完全不联动**。demo 跑到任何画面，右侧不动 |
| 右 → 左 | **单向控制**。右侧"在左侧看演示"按钮把 demo 带到对应画面并暂停 |

**底层原则：左侧的播放/操作权永远在读者手里，右侧只能"引路"，不能"夺鼠标"。**

### 2. 跳转语义

右侧按钮 = "把 demo 带到那一刻 + 暂停"。
不是跳到段落起点；不是继续播放；不是从头播放。

---

## 七、跳转锚点机制

### 1. 锚点定义

每个跳转锚点 = 两个要素：
- **从哪一步开始** —— scenario.js 里的步骤索引
- **跑到什么程度停** —— 一个判断条件（DOM 元素出现、文字打完等）

### 2. 锚点配置位置

**跟内容放一起**——每个功能 tab 自己的文件里同时定义"内容"和"锚点"，加新 tab 只改一处。

### 3. 粒度策略

| 粒度 | 策略 | 范围 |
|---|---|---|
| 粗 | 跳到那一步开头 + 让那一步播完 | 多数 tab 用这个 |
| 细 | 跳到那一步开头 + 写具体条件，达到才停 | v1 限 AskQuestion 6 个锚点 |

### 4. 异常兜底

跳转可能失败（条件错、剧本变了）。处理：
- 设最长等待时间（建议 8 秒），超时强制停在当前位置
- 跳转前先把 demo 重置到那一步起点，保证起点干净
- **不抛错、不弹"跳转失败"提示**——避免设计交付物显得不可靠

## 九、内容文件组织

### 1. 文件结构

```
features/
├── index.js              ← 汇总文件，决定导航顺序、所有 tab 在此报到
├── overview.js           ← 总览「设计思考」（v1 仅占位）
└── ask-question.js       ← AskQuestion（v1 内容完整）
```

**v1 只建 2 个文件**——overview 占位 + AskQuestion 完整。其他 tab 按需在 v2+ 增量加。

**扩展规则：** `features/index.js` 是导航的唯一真相源——它 import 了哪些 tab，下拉菜单就显示哪些。新增功能 tab 时只动两处（加文件 + 加一行 import），不动框架代码。

### 2. 单个文件含什么

每个文件自包含 4 样：
- **id**（URL 用）
- **type**（`overview` 或 `feature`）
- **label**（显示名，下拉菜单看到的中文名）
- **anchors**（跳转锚点定义，可多个）
- **content**（HTML 内容，模板字符串直接写）

### 3. 内容写法

**直接写 HTML，不用 markdown 解析。**

理由：
- 项目无构建步骤（原生 ES Module + python http server），HTML 模板字符串最直接
- 内容里要嵌"在左侧看演示"按钮等交互元素，HTML 表达最自由
- 避免引入 markdown 解析器或复用 demo 内的特化 parser
- AI 加新 tab 时一次写完一个文件即可，路径最短

### 4. 加新 tab 的步骤

1. `features/` 里照抄现有文件，新建 `<新id>.js`
2. 改三处：id、label、anchors
3. 内容（HTML）填进去
4. `index.js` 加一行 import

## 十、单个功能 tab 的章节结构（专业交互设计文档章法）

参考 Material / HIG / Atlassian / Ant Design 等大厂规范，标准章节体系如下。**章节按需出现，不强求齐全；但章节名必须从这套统一名表里挑**，避免每个 tab 自创章节名稀释认知。

### 1. 章节名表

| # | 章节 | 回答什么 |
|---|---|---|
| 1 | 概述 | 一句话定义 + 使用场景 + 设计目标 |
| 2 | 构成 | 组件由哪几块组成，每块叫什么名字（标注图） |
| 3 | 类型 | 有几种变体，分别什么时候用 |
| 4 | 状态 | 每个部件的全部状态枚举（MECE） |
| 5 | 交互行为 | 用户操作 → 系统响应的对照规则 |
| 6 | 使用流程 | 用户进入到完成的完整路径，含分支 |
| 7 | 边界与异常 | 极端情况：超长 / 空状态 / 中途关闭 / 网络异常等 |
| 8 | 文案规范 | 按条件变化的所有文字、tone of voice |
| 9 | 响应式 / 适配 | 不同尺寸下的差异（如适用） |
| 10 | 动效 | 动效节奏分级（快/中/慢）+ 关键动效设计意图 |
| 11 | 可访问性 | 键盘 / 屏幕阅读器 / 对比度 / ARIA 语义建议（如适用） |
| 12 | 数据埋点（建议） | 关键事件清单 + 观测指标（实现层按需采纳） |
| 13 | 设计原理 | 关键决策的为什么——交互文档与开发文档最大的差别 |
| 14 | 关联组件 / Do's and Don'ts | 相似但用途不同的组件，避免误用 |

### 2. 不同复杂度的 tab 用不同子集

- **复杂组件**（如 AskQuestion、工具调用浮层） → 几乎全部章节齐全（参考 `2026-06-15-AskQuestion-交互设计文档.md` 的样板）
- **中等功能**（如 Subagent 调用、技能调用） → 概述、构成、状态、交互行为、设计原理（约 5 章）
- **简单功能点**（如导航按钮） → 概述、交互行为、设计原理（3 章）
- **总览（设计思考）** → 自由组织，不套章法

### 3. 占位模板（未填写 tab 的初始状态）

放 **4 章基础骨架**：概述 / 构成 / 交互行为 / 设计原理。

理由：这 4 章是任何功能"最低限度的完整说明"——讲清楚是什么、由什么构成、用户能做什么、为什么这么设计。其他章节（动效、状态、文案、可访问性、埋点等）按需补充，避免占位模板过重。

每章下面是一段"（占位内容，待补充）"标记，浅灰斜体显示，让读者一眼看出未完成、避免误引用。

## 十二、关键设计决策与理由

| 决策 | 选择 | 理由 |
|---|---|---|
| 顶层架构 | 总览 + 功能详解两层 | URL 自带场景：找原则进总览，找功能进具体 tab |
| URL 形态 | `?view=overview` / `?view=feature&id=xxx` | 一眼看出所在层；扩展性好；query 比 hash 在分享时更稳 |
| 默认页 | 进总览 | 无参数 = 读者目的未明，先看立场；研发会带参数主动进 |
| 联动方向 | 单向（右→左） | 不剥夺读者播放/操作权；左侧任何状态变化不打扰右侧阅读 |
| 跳转语义 | 跳到画面 + 暂停 | 让读者细看那一帧，符合"按钮 = 引路"的定位 |
| 锚点配置位置 | 与内容同文件 | 加新 tab 只改一处，AI 顺手 |
| 粒度策略 | 默认粗 + 重点细 | 框架优先，精细化按需扩展 |
| 异常兜底 | 静默兜底，不报错 | 设计交付物不能显得不可靠 |
| 内容写法 | 直接 HTML | 项目无构建，HTML 模板字符串最直接，AI 写得顺 |
| 章节体系 | 大厂交互设计文档章法 | 章节名统一，认知成本低；研发拿走就能开工 |
| 移动端策略 | 屏幕宽度阈值，不识别设备 | 浏览器没有可靠设备识别；物理约束才是真理由 |
