## 二、事件行统一结构（框架级约定）

所有 toolcall 的事件行遵循 **动作 + 对象** 的固定排版结构：

```
s-line = text(动作) + dim(对象) + [可选扩展]
```

| 字段 | 语义 | 必填 | 典型示例 |
|------|------|------|---------|
| `text` | **动作描述**（做什么） | ✅ | "调用技能"、"搜索网页"、"执行命令" |
| `dim` | **动作对象**（目标/参数） | 可选（11/14 类型有） | `"docx"`、`"/sessions"`、`"README.md"` |
| `card` | **动作详情**（补充内容块） | 可选（4 种类型有） | 技能描述、Edit patch、Subagent result |
| `detail` | **二级 Sheet 入口** | 仅「执行命令」有 | chevron `›` 点击展开 |
| `outputs` | **操作步骤子行** | 搜索类 + 浏览器操作 | 搜索结果 / 文件路径 / 浏览器步骤列表 |

**渲染变体**：`dim` 的展示位置不固定——大部分类型内联在 `s-line` 里，但「读取文件」的 `dim` 作为 **file-ref 子行** 独立展示（见下方「三.4 子行」节）。

### 二.1 文案规范

**正常态**：动词 + 名词，表示「执行了某动作」
- `创建文件`（✏️ 正常执行中/已执行）
- `读取文件`（👀 正常执行中/已执行）
- `执行命令`（🖥️ 正常执行中/已执行）

**异常态**：动词 + 名词 + 状态后缀，表示「动作执行异常」
- `创建文件失败`（⚠️ 异常）
- `调用工具超时`（推测其他异常类型）

**原则**：
1. `text` 文案本身携带语义状态——异常态无需额外 `status` 字段，直接从文案后缀推断。
2. 正常态不需要「成功」后缀——成功是默认态，无需声明。
3. **异常态不是独立工具类型**——它只是同类型在异常场景下的文案变体，数据字段签名保持一致。

### 二.2 核心规则

1. `text` 永远是动作的标识——文案决定工具类型的分类归属。
2. `dim` 永远代表动作的对象（操作目标）——不是 "说明"，不是 "副标题"。
3. `card` 的 `title` 可能复用 `dim` 的值（如调用技能的 `docx`），也可能是独立文本（如思考过程的 "思考过程"）。
4. 扩展字段（card/detail/outputs）按需出现，不叠加——每种类型有明确的数据字段签名。

| **浏览器操作** | **`浏览器操作`** | **`浏览器操作失败`** | ⚠️ | 导航失败/截图失败/元素未找到 | **高**（截图已验证） |

#### 「执行命令」异常态详细分析

截图展示的是**正常态**：`text="执行命令"` + `dim=命令内容` + `›` 展开二级 Sheet。以下推断异常态的数据形态：

| 异常场景 | text | dim | detail | 二级 Sheet 变化 |
|---------|------|-----|--------|---------------|
| **命令执行失败（非零退出码）** | `执行命令失败` | 命令内容 | ✅ | `sections` 中新增 `stderr` section，或 `输出` section 含错误信息 |
| **命令执行超时** | `执行命令超时` | 命令内容 | ✅ | `sections` 中 `输出` section 可能含超时提示 |
| **命令不存在** | `执行命令失败` | 命令内容 | 🚫 | 可能不渲染二级 Sheet（无输出可展示） |

**关键推断**：
1. **异常态保留 `detail`**：截图中正常态有 `›`，异常态应同样保留（因为用户需要查看 stderr/错误输出）。
2. **异常态可能新增 section**：除了 `命令` 和 `输出`，可能增加 `错误`（stderr）或 `退出码` section。
3. **二级 Sheet 的 section label 是语义化的**：不固定为「命令/输出」，而是根据实际场景动态生成（如「错误输出」「退出码」等）。
4. **异常态的 `icon` 推断为 `⚠️`**：沿用与「创建文件失败」相同的 `ICONS.warn` 机制，`inferToolIconKey` 会匹配 `失败|异常` 正则返回 `debug` key。

> ⚠️ **注意**：异常态的二级 Sheet schema（`{ sections: [...] }`）与正常态完全一致，差异只在于 sections 的内容和数量。这是执行命令类型的独特之处——它是目前唯一在异常态下仍保留 detail 的类型。

## 三、渲染路径对照

### 一级 Sheet：`renderEvent()` → `s-row`

所有 14 种类型走同一入口 `renderEvent()`，结构统一：

```
s-row.tool-{key}
  ├── s-ico          # renderToolIcon() → SVG / ICONS.warn
  └── s-content
        ├── s-line
        │     ├── s-text          # event.text
        │     ├── s-text.dim      # event.dim（可选）
        │     └── s-row-chevron › # event.detail 存在时（仅执行命令）
        └── event-card           # event.card 存在时（可选）
              ├── event-card-title   # 可能复用 event.dim，也可能是独立文本
              └── event-card-body
```

**差异点只取决于 event 对象上存在哪些字段**：
- `event.card` → 渲染 `event-card` div
- `event.detail` → 渲染 chevron `›`，点击进二级 Sheet
- `event.outputs` → 在事件行**下方**追加 s-sub 子行
- `isWarningEvent(event)` → icon 区域渲染 `ICONS.warn` 代替图标

**特殊规则**：「读取文件」的 `event.dim` 虽然在数据层面存在，但渲染时**不内联到 `s-line`**，而是作为 **file-ref 子行**独立展示（含文件类型图标）。这是一种渲染策略差异，不是数据字段差异。

### 二级 Sheet：`renderDetailContent()` → `sd-container`

仅当 `event.detail` 存在时触发。当前仅「执行命令」有：

```
sd-container
  └── sd-section × N
        ├── sd-label          # section.label
        └── sd-card             # section.content
              └── .sd-variant-code  # variant === 'code' 时
```

固定 schema：`{ sections: [{ label, variant: "code"|"text", content }] }`

### 子行：`renderSearchItem()` → `s-sub`

#### 搜索网页子行（有图标）

仅当 `event.outputs[].type === 'search'` 时：

```
s-sub
  ├── s-sub-ico   # wb-website.svg
  └── s-sub-txt   # output.text
```

**设计原理**：搜索网页的结果（网页标题+摘要）是用户核心关注点——agent 搜索了什么？搜到了什么？所以结果必须逐条展示，每条带网站图标以区分不同来源。

#### 搜索文件子行（纯文本，无图标）

仅当 `event.outputs[].type === 'search_file'`（或 `type === 'text'`）时：

```
s-sub
  └── s-sub-txt   # output.text（纯文本，无图标）
```

**关键设计决策**：搜索文件的**过程不重要，结果也不重要**——搜索文件是 agent 内部的"定位"操作，找到文件后立刻执行读取/编辑/删除等后续动作，匹配到的文件列表无需展示给用户。`outputs` 仅在**无匹配**时出现，作用是提示用户"没找到"，文案固定为 `"No matches result"`。

**与搜索网页的本质差异**：

| 维度 | 搜索网页 | 搜索文件 |
|------|---------|---------|
| **结果价值** | 用户需要看结果决定下一步 | agent 内部用，用户不需要 |
| **outputs 用途** | 展示搜索到的网页列表 | **仅无匹配时提示** |
| **每条子行** | 网页标题+摘要+URL | 无匹配时：单行提示文案 |
| **图标** | ✅ wb-website.svg | ❌ 无图标 |
| **数量** | 最多 10 条 | 0 或 1 条（无匹配提示） |
| **有匹配时的行为** | 展示全部结果 | **不展示 outputs，直接进入下一步操作** |

> ⚠️ **注意**：搜索文件的 `No matches result` **不是异常**——它是正常状态（"搜索到了零个结果"），因此不需要 `⚠️` 图标，不需要变文案为"搜索文件失败"。只有搜索引擎本身的错误（如正则语法错误、遍历权限受限）才应使用 `text = "搜索文件失败"` 的异常态。

#### 浏览器操作子行（纯文本，无图标）

仅当 `event.outputs[].type === 'browser_step'`（或 `type === 'text'`）时：

```
s-sub
  └── s-sub-txt   # output.text（纯文本，无图标）
```

**内容格式**：每条子行描述一个浏览器操作步骤，中文示例：
- `导航至 http://localhost:8765/关西家庭旅行手...`
- `截取页面截图`
- `向下滚动页面`
- `解锁页面元素`

**来源推断**：浏览器操作的 `outputs` 本质上是将浏览器自动化的 `action log`（操作日志）逐条展示，与搜索类的 `outputs` 不同——浏览器子行**不携带图标**，因为步骤类型不需要网站/文件类图标区分。

#### 文件引用子行（file-ref，带文件类型图标）

仅当事件为「读取文件」类型，且 `event.dim` 包含文件路径时：

```
s-sub
  ├── s-sub-ico   # 文件类型图标（由扩展名推断：.md→📄, .xlsx→📊 等）
  └── s-sub-txt   # 文件路径
```

**渲染规则**：
- 文件类型图标由扩展名动态推断，不是工具图标
- 文件路径可能截断显示（`.../workspace/文件名.md`），点击可展开全路径
- 这是「读取文件」的特化渲染——`dim` 不在 `s-line` 内联，而是作为独立子行展示

### 8.1 文件操作三元组：search_file / read_file / edit_file

#### 推导起点

竞品截图中，「读取文件」展示出两个关键特征：
1. `dim`（文件路径）不在事件行内联，而是作为**独立子行**展示
2. 子行携带**文件类型图标**（📄 / 📊 等）

这与此前假设的「动作➕对象统一 inline」模式冲突。需要回答三个问题：
1. `dim` 到底放哪儿——是数据结构变了，还是渲染策略变了？
2. 为什么「读取文件」和「搜索网页」的对象展示方式不同？
3. 一次读几个文件？「读取文件」和「搜索文件」有什么关系？

#### 步骤1：确定动作的本质

| 动作 | 本质 | 对象是谁？ |
|------|------|-----------|
| `search_file` | **定位**——找到目标文件 | 搜索 pattern |
| `read_file` | **获取内容**——读取已定位的文件 | 具体文件路径 |
| `edit_file` | **修改内容**——变更已定位的文件 | 具体文件路径 |

`search_file` 是**前置操作**，`read_file` 和 `edit_file` 是**后续操作**。在 agent 工作流中，典型的链路是：

```
search_file("**/*.md")  →  read_file("src/intro.md")  →  edit_file("src/intro.md")
     （定位）                 （读取内容）                  （修改内容）
```

#### 步骤2：推导对象数量

从代码实现角度分析（训练知识）：

| 动作 | 对象数量 | 原因 |
|------|---------|------|
| `search_file` | **批量匹配** | 一个 pattern 可能匹配多个文件 |
| `read_file` | **一次一个** | 工具签名通常是 `read_file(path: string)` |
| `edit_file` | **一次一个** | 工具签名通常是 `edit_file(path: string, new_content: string)` |

如果 agent 需要读取 3 个文件：
- 不是一次调用传入 3 个路径
- 而是**循环调用 3 次** `read_file`
- Sheet 中展示 3 行独立的事件行

**关键推论**：`read_file` 和 `edit_file` 的 `dim` 永远是**单个文件路径**，数据结构上和 `create_file` 一致（都是文件路径）。

#### 步骤3：分析信息展示的价值链

为什么有些动作的结果展示给用户，有些不展示？

| 动作 | 结果价值 | 用户是否需要看？ | 展示策略 |
|------|---------|---------------|---------|
| `搜索网页` | 搜索结果决定用户是否继续浏览 | ✅ 需要 | `outputs` 逐条展示（10 条上限） |
| `搜索文件` | 匹配结果只是 agent 内部定位用 | ❌ 不需要 | **不展示匹配结果**，找到就继续读/改 |
| `读取文件` | 文件内容会作为上下文传给后续推理 | ❌ 不需要在 Sheet 展示 | `card` 无，`outputs` 无，仅在气泡中展示内容 |
| `编辑文件` | 修改了什么，改了哪些内容 | ✅ 需要高亮 | `card` 展示 diff preview |

#### 步骤4：得出「搜索文件」的独特设计

搜索文件的结果（匹配到的文件列表）**对用户没有信息价值**——因为：
- 匹配到了 → agent 自动读取/编辑，用户不需要关心"匹配到了谁"
- 匹配不到 → 用户需要知道"没找到，所以后续操作无法进行"

因此 `search_file` 的 `outputs` 设计为：

```
有匹配时 → outputs = undefined（不展示任何内容）
无匹配时 → outputs = [{ text: "No matches result" }]
```

> ⚠️ **关键定性**：`No matches result` **不是异常**——它是搜索的正常结果（"搜索到了零个"）。异常是搜索引擎本身的错误（如正则语法错误），那种情况才用 `text = "搜索文件失败"`。

#### 步骤5：统一 dim 的语义

所有的文件操作，`dim` 的语义都是一致的：

| 类型 | dim 语义 | 示例 |
|------|---------|------|
| `search_file` | 搜索 pattern | `**/*.md` |
| `read_file` | 文件路径 | `src/intro.md` |
| `edit_file` | 文件路径 | `src/intro.md` |
| `create_file` | 文件路径 | `plan.md` |

**核心原则**：`dim` 的数据语义永远是"动作的对象"，不因类型而异。差异只在**渲染位置**——`read_file` 的长路径 + 文件图标需求导致 `dim` 以子行形式展示，但数据层面 `dim` 始终存在。

#### 最终结论

| 维度 | search_file | read_file | edit_file | create_file |
|------|------------|-----------|-----------|-------------|
| **动作本质** | 定位匹配 | 获取内容 | 修改内容 | 新建内容 |
| **dim 语义** | 搜索 pattern | 文件路径 | 文件路径 | 文件路径 |
| **对象数量** | 批量（pattern 匹配） | **一次一个** | **一次一个** | 一次一个 |
| **多文件场景** | 一个 pattern → 多个结果 | **多次独立调用** | **多次独立调用** | 多次独立调用 |
| **outputs 用途** | **仅无匹配时提示** | ❌ 无 | ❌ 无 | ❌ 无 |
| **card 用途** | ❌ 无 | ❌ 无 | ✅ diff preview | ❌ 无 |
| **dim 渲染位置** | inline（pattern 通常短） | **子行（长路径+图标）** | 子行（长路径+图标） | inline / 子行 |
| **子行图标** | ❌ 无 | ✅ 文件类型图标 | ✅ 文件类型图标 | ❌ 无 |

### 8.2 异常态的文案规范

#### 推导过程

竞品截图呈现的异常文案是"文件创建失败"——名词在前。而我们的制品要求是"动词➕名词➕状态"，即"创建文件失败"。

统一规范推导：

**正常态 = 动作本身（不言说成功）**
- `创建文件` —— 表示这个动作被执行了
- `读取文件` —— 表示这个动作被执行了
- 无需加「成功」「已完成」等后缀——成功是默认假设

**异常态 = 动作 + 状态后缀（必须言说异常）**
- `创建文件失败` —— 动作 + 失败
- `执行命令超时` —— 动作 + 超时
- `调用技能失败` —— 动作 + 失败
- 不能写成「失败：创建文件」——破坏统一扫描模式

**为什么异常要加后缀，正常不加？**

从人机交互的视角：用户快速扫视 Sheet 时，需要**0.5 秒内识别是否有问题**。

- 正常态：所有事件行格式统一（动词+名词），扫描流畅
- 异常态：**文案结构突变**（多出状态 suffix），一眼就能识别
- 如果正常态也加「成功」，异常态加「失败」——两者长度一样，视觉区分度下降

#### 最终结论

| 状态 | 文案格式 | 示例 |
|------|---------|------|
| 正常态 | `动词 + 名词` | `创建文件`、`读取文件`、`执行命令` |
| 异常态 | `动词 + 名词 + 状态后缀` | `创建文件失败`、`执行命令超时`、`调用技能失败` |

### 8.3 dim 渲染策略：inline vs 子行

#### 推导过程

竞品截图呈现的 `dim` 位置不一致：
- `🔍 搜索网页 入境行李` —— inline
- `👀 读取文件` + 子行 `📄 .../路径.md` —— 子行

这不是数据结构的差异，是**信息特征决定渲染位置**。

推导规则：

```
if (dim.length > ~20 字符) → 子行（避免 inline 折行）
else if (需要可视化辅助图标) → 子行（独立空间放图标）
else if (多条同类列表) → 子行（outputs[] 列表）
else → inline（简洁紧凑）
```

#### 映射验证

| 类型 | dim 特征 | 规则命中 | 实际位置 |
|------|---------|---------|---------|
| 搜索网页 | 短关键词（~4-10 字符） | inline ✅ | inline ✅ |
| 调用技能 | 短技能名（~4-8 字符） | inline ✅ | inline ✅ |
| 创建文件 | 中短路径（~10-20 字符） | inline ✅ | inline ✅ |
| 读取文件 | **长路径 + 需文件图标** | **子行** ← | 子行 ✅ |
| 搜索文件 | 短 pattern（~5-15 字符） | inline ✅ | inline ✅ |
| 浏览器操作 | URL 长 + 步骤多 | 子行 ← | 子行 ✅ |

#### 最终结论

> **不是"类型决定位置"，而是"信息特征决定渲染策略"。**

代码层面建议：

```javascript
function shouldExtractDimToSubline(event) {
    const dim = event.dim || '';
    if (dim.length > 20) return true;
    if (needsFileIcon(event.type)) return true;
    if (event.outputs?.length > 0) return true;
    return false;
}
```

### 8.4 执行命令的二级 Sheet 设计

#### 推导过程

竞品截图展示了正常态的二级 Sheet：
- `命令` section —— 展示执行了什么命令
- `输出` section —— 展示命令的 stdout
- 点击 chevron `›` 展开

异常态的推断（基于训练和通用 CLI 工具知识）：

| 异常场景 | 应该展示什么？ | detail 是否保留？ |
|---------|---------------|-----------------|
| 命令返回非零退出码 | stderr + exit code | ✅ 保留 —— 用户需要看错误输出 |
| 命令超时 | 超时提示 + 已输出内容 | ✅ 保留 —— 用户需要看超时前输出 |
| 命令不存在 | "command not found" | 🚫 可能不保留 —— 无输出可展示 |

**关键独特性**：执行命令是目前**唯一在异常态下仍保留 `detail`** 的类型——因为 stderr/exit code 和 stdout 一样，都是用户诊断问题所必需的信息。

#### 最终结论

执行命令的异常态数据形态：

```javascript
// 正常态
{
    text: "执行命令",
    dim: "python generate_plan.py",
    detail: {
        sections: [
            { label: "命令", variant: "code", content: "..." },
            { label: "输出", variant: "code", content: "..." }
        ]
    }
}

// 异常态（非零退出码）
{
    text: "执行命令失败",
    dim: "python generate_plan.py",
    detail: {
        sections: [
            { label: "命令", variant: "code", content: "..." },
            { label: "输出", variant: "code", content: "..." },
            { label: "错误", variant: "code", content: "...stderr..." },
            { label: "退出码", variant: "text", content: "1" }
        ]
    }
}
```

section label 是**语义化动态生成**的，不固定硬编码。
