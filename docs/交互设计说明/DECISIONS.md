# DECISIONS.md: 右侧交互设计说明文档决策记录

本文件记录右侧 Feature Panel 说明文档系统的关键取舍。它服务后续维护和 AI 协作，避免把已确认的边界重新讨论或误解。

## 2026-06-22

### 两套 design.md 绝对分开

**决定：** 项目里有两套不同对象的 design.md：Agent 产品本体 design.md，以及右侧交互设计说明文档 design.md。当前目录只服务后者。

**原因：** Agent 产品本体规范关注产品如何工作；右侧说明文档规范关注如何把这些设计讲清楚。两者混写会导致读者、评审标准、内容粒度全部错位。

**影响：** 后续需求里出现“右侧说明区”“交互设计说明”“说明文档 design.md”“文档设计语言”时，默认进入右侧说明文档语境。只有明确说“Agent 产品本身”“左侧 Demo”“产品体验规范”时，才进入 Agent 产品本体语境。

### 采用 DESIGN.md + EXPERIENCE.md 双 spine

**决定：** 右侧说明文档拆成两根 spine：`DESIGN.md` 管视觉表达，`EXPERIENCE.md` 管阅读体验和信息组织。

**原因：** 当前说明区同时包含视觉语言和阅读路径。如果全部放在一份文件里，后续会把字体、色彩、组件外观和读者分层、页面模板、状态说明混在一起。

**影响：** 视觉问题先查 `DESIGN.md`；内容结构、读者路径、页面模板、状态说明先查 `EXPERIENCE.md`。

### 现有实现不是直接等于规范

**决定：** 当前 Feature Panel 的实现只能作为素材和证据，不能未经审查直接升格为规范。

**原因：** 现有页面里既有稳定设计模式，也有临时实现和产品本体说明。标准流程应该是 Audit → 提炼 → 决策 → 写入 spine。

**影响：** 后续修改规范前，先判断内容来源：用户明确判断、当前实现事实、AI 推断。AI 推断需要标记或等待确认。

### 说明文档不写工程实现逻辑

**决定：** 右侧说明文档可以解释交互逻辑和产品规则，但不写具体工程实现路径。

**原因：** 文档面向设计团队决策层、设计同行、规范维护者和执行层阅读者，不是研发实现说明。

**影响：** 应写“点击状态行后进入详情层”，不写“在 engine/sheet.js 中绑定事件”。

### 图文并茂是默认标准

**决定：** 描述外观、行为、状态、流程时，必须使用表格、流程图、组件快照、标注图、Do / Don't 对比等视觉化表达。

**原因：** 用户明确要求交互设计说明/设计交付物必须图文并茂，纯文字字符串不构成设计文档。

**影响：** 纯文字只适合“为什么”类设计原理章节；功能构成、状态变化、流程说明、正反例必须有视觉承载。

### 采用 Validate + Update 工作流

**决定：** 当前任务不是从零 Create，而是 Validate + Update。先审查现有页面，再修订 spine，再试改页面。

**原因：** 右侧说明区已经有 6 个 feature 页面、样式和源文档。直接重写会丢失现状资产，也容易把偶然实现误认为规范。

**影响：** 下一步优先补审查清单，并用 Ask Question 或 Approve Permission 作为试点页面验证标准。

### Ask Question 和 Approve Permission 是边界风险重点

**决定：** 后续页面改造优先检查 Ask Question 和 Approve Permission，因为它们最容易混入 Agent 产品本体规范。

**原因：** 这两页天然会讲“Agent 什么时候问用户”“Agent 什么时候请求权限”，容易从说明文档语境滑向产品本体语境。

**影响：** 改造时需要把表达重心放在“这一页如何帮助读者理解该设计点”，而不是重新定义 Agent 产品应该如何工作。
