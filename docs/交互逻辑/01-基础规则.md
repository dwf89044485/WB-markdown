## 一、整体观

这是一段「AI Agent 跑长任务」的回放。一次完整跑分六块、严格串行：

```
用户气泡 → Agent 进场 → 思考过程（独立大段，不属于任何节点）
        → 节点1（创建待办、输出节点内 markdown、联网搜索）
        → 节点2（生成产物、更新待办）
        → 节点3（调用技能、文件操作、异常处理、执行命令、委派 Subagent、更新待办）
        → 收尾段（任务耗时 + 总结 + 成果链接）
```

**核心隐喻**：每个「节点」是一个会自己生长、自己塌缩的活节点。它一旦开始就保持展开、内部不断长出新的子事件；跑完才自动塌缩、下一个节点接力出现。

**这套 demo 的真正意图**：通过「关西旅行」这个具体故事，**枚举一遍 Agent 系统所有的过程类型**——思考、创建待办、输出节点内/外层 markdown、联网搜索、待办流转、生成产物、更新待办、调用技能、文件操作、异常处理、执行命令、委派 Subagent、输出成果链接。具体内容是载体，过程类型才是观众要带走的东西。共 **13 个过程类型**，详见 [03-评审与差异.md § 12.1](./03-评审与差异.md#121-评审-rail--agent-过程类型清单-)。

**关于「待办流转」**：固定一份待办清单 ① ~ ⑦，从节点1 创建之后**顺序不变、不重排**。Agent 按列表顺序执行——节点1 跑 ① ~ ⑤，节点2 跑 ⑥（生成图片），节点3 跑 ⑦（整合信息）。每个节点都对应清单里某条/某几条的执行；这就是「待办流转」。

## 二、核心元素与命名

| 元素                      | 用途                            | 备注                                                      |
| ----------------------- | ----------------------------- | ------------------------------------------------------- |
| **user-bubble**         | 用户消息气泡                        | 灰底圆角，瞬间出现                                               |
| **agent-header**        | WorkBuddy 头像 + 名字             | AI 回复开始时立刻出现                                            |
| **思考过程行**               | 一行可点击灰文字「正在思考 ›」/「思考过程 ›」     | 独立状态行，挂在 agent-header 之后、节点1 之前；不属于任何节点                 |
| **节点（step）**            | 大节点容器                         | 含「头部 + 内部 detail」两层                                     |
| **节点头**                 | spinner / 绿钩 + 标签 + chevron   | spinner = 跑中，绿钩 = 已完成                                   |
| **状态行**                 | 可点击的灰行（节点 detail 内 / 思考过程独立行） | 文字遵循 **「正在 X ›」（跑中，扫光）/「X ›」（完成，无扫光）** 模式               |
| **节点内 markdown**        | 节点 detail 内的正文段落              | 标题、段落、列表、表格、链接，DOM 节点级打字机出现；归属该节点                       |
| **外层正文 markdown**       | 收尾段的正文段落                      | 样式跟节点内 markdown 完全一致，但归属是 Agent 整体回复，不属于任何节点            |
| **链接卡片**                | 收尾段的成果链接                      | 「查看日本关西家庭旅行方案 v1.0」蓝色链接                                 |
| **过程浮层 (bottom-sheet)** | 唯一一个浮层 DOM                    | 标题 = 该状态行同名；内容 = **当前状态行自己的事件块（不累积）** + 可选**全局共享的待办列表** |
| **timing-bar**          | 「任务耗时 19m 40s」一行 + chevron    | **全部节点跑完才出现**，作为收尾段封顶                                   |

## 三、节点的状态机（所有大节点共用）

```
        next 进入                   全部 detail 跑完
 IDLE ───────────► RUNNING ──────────────────────► DONE
                    │  │                              │
            手动点头 │  │ 自动跑                       │ 手动点头
                    ▼  │                              ▼
            USER_COLLAPSED                      USER_EXPANDED
            （展开态被收起,                      （收起态被展开,
              内部还在生长）                       内部内容静态）
```

四态语义：

| 状态             | 节点头视觉                        | detail 是否可见 | 触发                   |
| -------------- | ---------------------------- | ----------- | -------------------- |
| IDLE           | 不存在                          | 不存在         | 还没轮到它                |
| RUNNING        | spinner（蓝） + 标签 + chevron 朝下 | 展开 + 内部还在生长 | 上一个节点塌缩后自动           |
| DONE           | 绿钩 + 标签 + chevron 朝下         | 收起          | 节点最后一个子事件完成后**自动塌缩** |
| USER_COLLAPSED | spinner + 标签 + chevron 朝下    | 收起          | RUNNING 时用户手动点头      |
| USER_EXPANDED  | 绿钩 + 标签 + chevron 朝上         | 展开（静态历史内容）  | DONE 后用户手动点头         |

**关键规则**：

- 节点头**永远不会出现「未开始的灰圆」**。要么 IDLE（不渲染），要么 RUNNING/DONE。
- 同一时刻**最多一个节点处于 RUNNING**。
- DONE 自动塌缩**只在该节点首次完成时**触发，以后用户怎么开关都不再自动。

## 四、状态行的状态机

状态行 = 可点击的灰文字行（含 chevron `›`），出现在两类位置：

- 思考过程那一条（独立，挂在 agent-header 之后）
- 各个节点 detail 内部

**文字态规则**（统一）：

- 跑中：**「正在 X ›」** + 扫光开
- 完成：**「X ›」** + 扫光关

```
        出现                 后台跑完
   ─────────────► 正在 X ›  ───────────────► X ›
                  扫光 开                     扫光 关
```

**全部 11 个状态行字典**（贯穿整个 demo）：

| 状态行 ID      | 跑中态（扫光开）        | 完成态（无扫光）      | 出现位置       |
| ----------- | --------------- | ------------- | ---------- |
| 思考过程        | 正在思考 ›          | 思考过程 ›        | 独立（节点1 之前） |
| 创建待办        | 正在创建待办 ›        | 创建待办 ›        | 节点1        |
| 搜索网页        | 正在搜索网页 ›        | 搜索网页 ›        | 节点1        |
| 生成图片        | 正在生成图片 ›        | 生成图片 ›        | 节点2        |
| 更新待办（节点2 末） | 正在更新待办 ›        | 更新待办 ›        | 节点2        |
| 调用技能        | 正在调用技能 ›        | 调用技能 ›        | 节点3        |
| 创建文件        | 正在创建文件 ›        | 创建文件 ›        | 节点3        |
| 搜索文件        | 正在搜索文件 ›        | 搜索文件 ›        | 节点3        |
| 执行命令        | 正在执行命令 ›        | 执行命令 ›        | 节点3        |
| 委派 Subagent | 正在委派 Subagent › | 委派 Subagent › | 节点3        |
| 更新待办（节点3 末） | 正在更新待办 ›        | 更新待办 ›        | 节点3        |

**关键规则**：

- 扫光只覆盖**文字本身这一行**（含 chevron），不是整个 row。
- 状态行**任何态都可点击**，点击拉起浮层。**浮层标题 = 该状态行同名**（"正在思考 ›" 和 "思考过程 ›" 都打开标题为「思考过程」的浮层）。
- 节点塌缩到 DONE 后，状态行不会消失——它属于该节点的 detail，下次用户手动点开节点头还能看到，仍可点击。

### 浮层多帧模型

> 状态行的「文字态」是**粗粒度**的（每行 2 个文字态：跑中 / 完成）；
> 但**同一文字态内部，浮层可以有多帧**——后台进度推进时，浮层里某条待办从 ⭕→🔄→✅，或某个事件块从无到有，是渐进发生的。

举例：「正在搜索网页 ›」这一行的生命周期

```
[1] 正在搜索网页 ›   浮层快照 A：4 条联网搜索全空圈，第 1 条转 spinner
[2] 正在搜索网页 ›   浮层快照 B：第 1 条 ✓，第 2 条 spinner
[3] 正在搜索网页 ›   浮层快照 C：第 1-2 条 ✓，第 3 条 spinner
[4] 正在搜索网页 ›   浮层快照 D：第 1-3 条 ✓，第 4 条 spinner
[5] 搜索网页 ›       浮层快照 E：第 1-4 条全 ✓
```

**[1]~[5] 是 5 个最小子事件 = 5 个 beat**。
状态行文字只切换 1 次（[4]→[5]），但浮层逐帧推进。

## 五、过程浮层（bottom-sheet）⭐

> 这是这套 demo 最关键的交互模型，规则不能含糊。

### 5.1 标题

浮层标题 = 该状态行同名：

| 状态行                         | 浮层标题        |
| --------------------------- | ----------- |
| 正在思考 / 思考过程                 | 思考过程        |
| 正在创建待办 / 创建待办               | 创建待办        |
| 正在搜索网页 / 搜索网页               | 搜索网页        |
| 正在生成图片 / 生成图片               | 生成图片        |
| 正在更新待办 / 更新待办               | 更新待办        |
| 正在调用技能 / 调用技能               | 调用技能        |
| 正在创建文件 / 创建文件               | 创建文件        |
| 正在搜索文件 / 搜索文件               | 搜索文件        |
| 正在执行命令 / 执行命令               | 执行命令        |
| 正在委派 Subagent / 委派 Subagent | 委派 Subagent |

### 5.2 浮层内容由两层独立元素构成 ⭐

浮层 = **事件块（私有）** + **待办列表（全局共享）**。两者遵循**完全不同**的累积逻辑：

#### 第一层：事件块 — **不累积，每个浮层只展示自己当下的**

- 每个状态行**只展示自己生命周期内**产生的事件块。
- **跨状态行不累积、跨节点不累积。**
- 例：节点2 的「更新待办 ›」浮层**不会**显示节点1 的「☐ 创建待办」事件块；节点3 的「执行命令 ›」浮层**不会**显示节点 3.2 的「✏️ 创建文件」事件块。
- 每个状态行进入跑中态时，浮层事件块从空开始，按后台推进逐帧累积；**直到该状态行完成态**，事件块停止累积；**用户后续再点击该状态行查看**，看到的就是该状态行最终态时刻的事件块快照。

#### 第二层：待办列表 — **全局唯一一份，状态流转贯穿全 demo**

- **整个 demo 全程只有一份**待办清单（① ~ ⑦ 共 7 条，顺序固定，详见 [附录 B](./04-内容标准库.md#附录-b--演示用待办清单最终定稿)）。
- 每条待办有 3 种状态：⭕ 空圈（未开始）/ 🔄 蓝 spinner（进行中）/ ✅ 绿钩（已完成）。
- 状态在所有「带待办列表的浮层」里**实时同步显示**。当节点1 末尾打勾了 ②，节点2 的「生成图片 ›」浮层一打开，看到的也是 ② 已打勾——因为是同一份清单。
- **这就是「待办流转」**——一份清单流转到各个浮层、各个节点，状态在各处推进。

#### 哪些浮层带待办列表，哪些不带

| 浮层          | 带事件块？                                      | 带待办列表？ | 说明                    |
| ----------- | ------------------------------------------ | ------ | --------------------- |
| 思考过程        | ✓（🧠 思考过程 + markdown）                      | ✗      | 思考还没产生待办              |
| 创建待办        | ✓（☐ 创建待办 + 关联首条名）                          | ✓      | 创建待办的浮层就是这份清单的"诞生现场"  |
| 搜索网页        | ✗（无独立事件块；搜索本身=待办流转）                        | ✓      | 主要看 ②③④⑤ 的状态变化        |
| 生成图片        | ✓（🖼️ 生成图片 ×N，逐帧累积）                        | ✓      | 看 ⑥ 转 spinner 然后打勾    |
| 更新待办（节点2 末） | ✓（☑️ 更新待办 + 关联首条名）                         | ✓      | 看 ⑥ 已打勾 + ⑦ 转 spinner |
| 调用技能        | ✓（📖 调用技能 + 技能描述卡片）                        | ✗      | 跟待办无关                 |
| 创建文件        | ✓（⚠️ 文件创建失败 + ✏️ 创建文件 + 👀 读取文件 + ✏️ 编辑文件） | ✗      | 节点3 内部细节              |
| 搜索文件        | ✓（🔍 搜索文件 + ✏️ 编辑文件）                       | ✗      | 节点3 内部细节              |
| 执行命令        | ✓（🖥️ 执行命令 ×3）                             | ✗      | 节点3 内部细节              |
| 委派 Subagent | ✓（🐱 Sub Coding Agent 卡片 + 嵌套子对话流）         | ✗      | 节点3 内部细节              |
| 更新待办（节点3 末） | ✓（☑️ 更新待办 + 关联首条名）                         | ✓      | 看 ⑦ 打勾 = 全部 ✅         |

### 5.3 「快照」语义（关键）

> **当用户在某个时刻点状态行 X 的时候，浮层显示的是 X 在该时刻这一帧的过程切片：**
> 
> - 事件块：X 自己生命周期内**到该时刻为止**累积出的事件块；
> - 待办列表：**该时刻全局**待办列表的状态。

即便后续节点都跑完了，回头再点节点1 已完成的「搜索网页 ›」，看到的事件块仍然是节点1 那一刻的（无新增），**待办列表也回到那一刻**。

→ 浮层 = 该时刻**全局快照**，包括待办列表。点已完成状态行 = 时光倒流回那一刻。否则跨节点回看的浮层会出现"未来的 ✓"，破坏快照语义。

实现层面：scenario 把每一帧的「(状态行ID, 帧序号) → 事件块 HTML, 待办列表状态」都预先编排好（路线 1）。

### 5.4 思考过程浮层的特殊性

- 跑中（「正在思考 ›」）点：标题「思考过程」+ 🧠 + 一段持续打字机的 markdown
- 跑完（「思考过程 ›」）点：标题「思考过程」+ 🧠 + 完整静态思考 markdown
- 视觉跟其他浮层完全同构

## 六、扫光效果（shimmer）

- 只覆盖**文字 + chevron** 这条 line
- CSS 方案：`background: linear-gradient(...)` + `background-clip: text` + `animation` 横向移动
- 进入「正在 X ›」态时开扫光；状态机推进到「X ›」态时停掉

## 七、思考过程详解（独立大段，不属于任何节点）

「思考过程」是 agent-header 之后、节点1 之前的**独立状态行**。视觉上跟节点 detail 内的状态行完全同构（一行灰文字 + chevron），但**不归属任何节点**——挂在 agent-msg 容器内的最顶部，没有节点头、没有 detail 区。

时序（最小子事件）：

| 序号  | 子事件                                  | UI 变化                                          |
| --- | ------------------------------------ | ---------------------------------------------- |
| T.1 | agent-header 出现                      | WorkBuddy 头像 + 名字                              |
| T.2 | 「正在思考 ›」行出现                          | 灰文字 + chevron；扫光开                              |
| T.3 | （后台思考中——浮层 markdown 持续打字机推进，约 2~3 帧） | 用户在 T.2 ~ T.4 之间任意时刻点击，看到的是该时刻的思考 markdown 截止帧 |
| T.4 | 状态行推进 → 「思考过程 ›」                     | 文字切换；扫光关；浮层内容定格为完整思考 markdown                  |
| T.5 | 紧接进入节点1                              | 「思考过程 ›」行不消失（保留在历史里），节点1 头出现在它下方               |

> T.4 那一帧的标准内容文本见 [附录 A.1](./04-内容标准库.md#a1--思考过程浮层)。
