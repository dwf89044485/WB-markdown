### 0.2 确定新 scenario schema

当前 beat 结构：
```json
{ "id": "step-1-decompose", "phase": "执行", "title": "...", "render": [...], "note": {...} }
```

新 beat 结构（63 个，字段按需出现）：
```json
{
  "id": "b07",                          // beat 编号
  "type": "status-line",                // beat 类型：user-bubble / agent-enter / think / status-line / node-enter / node-collapse / node-md / timing-bar / summary-md / summary-link
  "statusLineId": "create-todo",        // 仅 status-line 类型需要
  "statusLineState": "running",         // running / done
  "mount": ".step-1 .detail",           // DOM 挂载点
  "render": [
    {
      "tpl": "status-line",
      "data": { "text": "正在创建待办 ›", "shimmer": true }
    }
  ],
  "sheetSnapshot": {                    // 可选：该 beat 的浮层快照
    "title": "创建待办",
    "eventBlocks": "<div>☐ 创建待办  任务理解与分解…</div>",
    "todoState": [                      // 可选：7 条待办的状态快照
      { "id": 1, "status": "spinner", "text": "任务理解与分解…" },
      { "id": 2, "status": "empty",   "text": "联网搜索：签证…" },
      ...
    ]
  },
  "note": { ... }                       // 评审模式解说
}
```

**关键设计决策**：
- `sheetSnapshot` 嵌入每条 beat，实现"时光倒流"快照语义——任意 beat 回放时，浮层内容可从该 beat 的 `sheetSnapshot` 直接读取
- `todoState` 是 7 条待办的完整状态帧，不是增量——保证任意时刻都是完整快照
- `statusLineId` 全局唯一标识 11 个状态行，用于浮层标题映射和事件块隔离

**产出**：新 schema 写入本文档（已完成），后续开发以此为据。

## Phase 2 · 核心组件体系（预估 3~4 天）

> **目标**：实现 01-基础规则里的状态机 + 组件体系，每个组件可独立预览。

### 2.1 节点状态机

**当前实现**：4 个节点在 agent-shell 出现时一次性渲染，无状态机。

**目标实现**：
```
IDLE(不渲染) → RUNNING(spinner + 展开detail) → DONE(绿钩 + 收起) 
                                                    ↕ 手动点头
                                              USER_COLLAPSED / USER_EXPANDED
```

**需要改动的代码**：
- `conversation-scene.html`：节点头模板从静态 HTML 改为 `<template>` + 动态渲染
- `player.js`：beat 类型 `node-enter` / `node-collapse` 触发状态转换
- `renderer.js`：新增 `tpl-node-header` 模板渲染，支持 spinner / 绿钩 / chevron 方向切换
- CSS：新增 spinner 旋转动画、绿钩图标、detail 展开/收起过渡

**关键行为**：
- 节点逐个出现（前一个 DONE 后下一个才 IDLE → RUNNING）
- RUNNING 时 detail 展开，内部子事件不断生长
- DONE 时自动塌缩（仅首次完成时触发）
- 用户手动点击节点头：RUNNING → USER_COLLAPSED（收起但内部继续生长）；DONE → USER_EXPANDED（展开静态历史）

**验证方式**：硬编码 3 个节点的进出序列，手动 NEXT 推进，观察状态转换正确。

### 2.2 状态行组件 + 扫光

**当前实现**：每个 detail 末尾一个 `<button class="step-detail-link">`。

**目标实现**：
- 11 个状态行，每个是独立组件 `<div class="status-line">`
- 文字："正在 X ›"（扫光开）/ "X ›"（扫光关）
- 点击拉起浮层（Phase 3 实现，本阶段先打 log）
- 扫光效果：CSS `background: linear-gradient(...)` + `background-clip: text` + `animation`

**模板设计**：
```html
<template id="tpl-status-line">
  <div class="status-line" data-status-line-id="" data-state="">
    <span class="status-line-text" data-bind="text"></span>
    <span class="status-line-chevron">›</span>
  </div>
</template>
```

**扫光 CSS**：
```css
.status-line[data-state="running"] .status-line-text {
  background: linear-gradient(90deg, #8e8e93 40%, #c7c7cc 50%, #8e8e93 60%);
  background-size: 200% 100%;
  background-clip: text;
  -webkit-background-clip: text;
  -webkit-text-fill-color: transparent;
  animation: shimmer 2s infinite;
}

@keyframes shimmer {
  0% { background-position: 100% 0; }
  100% { background-position: -100% 0; }
}
```

**验证方式**：硬编码 3 种状态行（思考过程 / 创建待办 / 搜索网页），手动切换 running/done 状态，观察文字切换和扫光开关。

### 2.3 节点内 markdown 组件

## Phase 3 · 浮层系统（预估 2~3 天）

> **目标**：实现 01-基础规则 § 五的完整浮层模型。这是交互最复杂的部分。

### 3.1 浮层 DOM 结构重构

**当前实现**：`<bottom-sheet>` 一个 DOM，标题永远"过程"，内容一坨累积 HTML。

**目标实现**：
- 唯一一个 `<bottom-sheet>` DOM（保留）
- 标题动态切换（10 种）
- 内容区分为两层：事件块区 + 待办列表区
- 事件块区：`<div class="sheet-events">` — 只渲染当前状态行的事件块
- 待办列表区：`<div class="sheet-todos">` — 全局共享的 7 条待办

**浮层 HTML 结构**：
```html
<bottom-sheet>
  <div class="sheet-header">
    <span class="sheet-title"></span>
    <button class="sheet-close">×</button>
  </div>
  <div class="sheet-body">
    <div class="sheet-events"></div>
    <div class="sheet-todos">
      <!-- 7 条待办，全局共享 -->
    </div>
  </div>
</bottom-sheet>
```

### 3.2 事件块层（不累积逻辑）

**核心规则**：每个状态行只展示自己生命周期内的事件块，跨状态行不累积。

**实现策略**：
- 每个 beat 的 `sheetSnapshot.eventBlocks` 包含该状态行到该时刻为止的全部事件块 HTML
- 点击状态行时，用该 beat 的 `eventBlocks` **整体替换** `.sheet-events` 的 innerHTML
- 不是增量 append，是整体替换——自然实现"不累积"

**状态行 → 浮层映射**：
- 点击"正在创建待办 ›" → 浮层标题"创建待办"，事件块 = 该状态行的事件块
- 点击"搜索网页 ›" → 浮层标题"搜索网页"，事件块 = 搜索网页的事件块（可能为空）
- 不同状态行的事件块互不干扰

### 3.3 待办列表层（全局共享逻辑）

**核心规则**：7 条待办在所有"带待办列表的浮层"里同步流转。

**实现策略**：
- 浮层内的 `.sheet-todos` 只有一份 DOM
- 每个 beat 的 `sheetSnapshot.todoState` 是 7 条待办的完整状态快照
- beat 推进时，用 `todoState` **整体替换** `.sheet-todos` 的 innerHTML
- 部分浮层不显示待办列表（思考过程/调用技能/创建文件/搜索文件/执行命令/委派 Subagent），此时 `.sheet-todos` 隐藏

**待办列表渲染函数**：
```javascript
function renderTodoList(todoState) {
  // todoState = [{ id:1, status:"spinner", text:"任务理解与分解…" }, ...]
  // 整体替换 .sheet-todos innerHTML
}
```

### 3.4 快照语义（时光倒流）

**核心规则**：点击已完成状态行，看到该状态行最末态时刻的全局快照。

**实现策略**：
- 每个 beat 的 `sheetSnapshot` 已经是完整快照
- 用户点击状态行时，找到该状态行**最后一次出现的 beat** 的 `sheetSnapshot`
- 用该快照渲染浮层（事件块 + 待办列表都回到那一刻）

**查找逻辑**：
```javascript
function findSnapshotForStatusLine(statusLineId) {
  // 从当前 beat 往前找，找到该 statusLineId 最后一个含 sheetSnapshot 的 beat
  for (let i = currentBeatIndex; i >= 0; i--) {
    const beat = scenario.beats[i];
    if (beat.statusLineId === statusLineId && beat.sheetSnapshot) {
      return beat.sheetSnapshot;
    }
  }
  return null;
}
```

### 3.5 委派 Subagent 浮层特殊处理

- 嵌套子对话流作为静态 HTML 一帧渲染
- 子状态行用主体系的"X ›"完成态命名
- 子状态行**不可点击**（加 `data-clickable="false"` 或 CSS `pointer-events: none`）

### 3.6 浮层进出场动效

- 底部滑入/滑出动画
- 手势跟随（可选，Phase 6 打磨）

**验证方式**：
- 评审模式下逐 beat 推进，任意时刻点击任意状态行
- 浮层标题正确（10 种）
- 事件块正确（不累积）
- 待办列表正确（全局同步）
- 快照语义正确（时光倒流）

## Phase 4 · 播放引擎适配（预估 2 天）

> **目标**：Player + Renderer 适配 63-beat 粒度和新组件体系。

### 4.1 Player 适配新 beat 结构

**当前实现**：9 个粗粒度 beat，`next/prev/goTo` 按 beat 序号推进。

**目标实现**：
- 63 个细粒度 beat，推进逻辑不变但粒度变细
- beat 类型分发：
  - `user-bubble` → 渲染用户气泡
  - `agent-enter` → 渲染 agent-header
  - `think` → 渲染思考过程行 / 切换状态
  - `status-line` → 渲染/切换状态行
  - `node-enter` → 节点 IDLE→RUNNING
  - `node-collapse` → 节点 RUNNING→DONE + 自动塌缩
  - `node-md` → 节点内 markdown 打字机
  - `timing-bar` → 渲染 timing-bar
  - `summary-md` → 外层正文 markdown 打字机
  - `summary-link` → 链接卡片

**关键改动**：
- Player 内部根据 `beat.type` 分发渲染逻辑
- `node-enter` 和 `node-collapse` 需要维护节点状态机
- `status-line` 需要维护状态行状态机（running↔done）

### 4.2 Renderer 适配新模板

新增模板清单：

| 模板 ID | 用途 | 挂载点 |
|---------|------|--------|
| `tpl-user-bubble` | 用户消息气泡 | `.conversation` |
| `tpl-agent-header` | Agent 头像+名字 | `.agent-msg` |
| `tpl-status-line` | 状态行 | `.step-N .detail` 或 `.agent-msg`（思考过程） |
| `tpl-node-header` | 节点头（spinner/绿钩） | `.agent-msg` |
| `tpl-md-block` | markdown 内容块 | `.step-N .detail .md-content` 或 `.main-content .md` |
| `tpl-timing-bar` | 任务耗时行 | `.agent-msg` |
| `tpl-link-card` | 蓝色链接卡片 | `.main-content .md` |

### 4.3 浮层随 beat 切帧

- 每个 beat 推进时，检查 `sheetSnapshot`
- 如果当前有打开的浮层，且该 beat 属于当前浮层对应的状态行，则更新浮层内容
- 如果 beat 不属于当前浮层的状态行，浮层内容不变

### 4.4 待办列表随 beat 推进

- 每个 beat 推进时，检查 `todoState`
- 如果存在，更新全局待办列表的状态

**验证方式**：
- 评审模式下 NEXT/PREV 逐 beat 推进，三栏联动正确
- 预览模式下自动播放完整 63 beats
- 浮层在自动播放时正确切帧
- 待办列表在自动播放时正确流转

## Phase 5 · 评审模式升级（预估 1~2 天）

> **目标**：评审 rail 从"示例剧情目录"改为"13 个 Agent 过程类型清单"。

### 5.1 评审 rail 重写

**当前实现**：rail 上每行 = 一个粗粒度 beat（9 行）。

**目标实现**：rail 上每行 = 一个 Agent 过程类型（13 行），层级缩进：

```
① 思考过程
节点1
  ② 创建待办
  ③ 输出节点内 markdown
  ④ 联网搜索 + 待办流转
节点2
  ⑤ 生成产物（图片/视频）
  ⑥ 更新待办
节点3
  ⑦ 调用技能
  ⑧ 文件操作
  ⑨ 异常处理
  ⑩ 执行命令
  ⑪ 委派 Subagent
收尾
  ⑫ 输出外层正文 markdown
  ⑬ 输出成果链接卡片
```

**过程类型 → beats 映射表**：

| 过程类型 | beats 区间 | 行数 |
|---------|-----------|------|
| ① 思考过程 | b02~b05 | 4 |
| ② 创建待办 | b07~b08 | 2 |
| ③ 输出节点内 markdown | b09~b12 | 4 |
| ④ 联网搜索 + 待办流转 | b13~b18 | 6 |
| ⑤ 生成产物 | b22~b25 | 4 |
| ⑥ 更新待办 | b26~b27 + b55~b57 | 5 |
| ⑦ 调用技能 | b30~b32 | 3 |
| ⑧ 文件操作 | b33~b38 + b39~b42 | 10 |
| ⑨ 异常处理 | b34 + b43 | 2 |
| ⑩ 执行命令 | b44~b48 | 5 |
| ⑪ 委派 Subagent | b50~b53 | 4 |
| ⑫ 输出外层正文 markdown | b60~b61 | 2 |
| ⑬ 输出成果链接卡片 | b62 | 1 |

点击任意一行 → `player.goTo(区间起始 beat 序号)`。

### 5.2 评审 note 重写

**当前实现**：每条 beat 自带 `note`，内容是"这一帧做了什么"。

**目标实现**：note 区展示的是"当前在演示什么过程类型 + 这类过程的交互特征"。

每个过程类型（①~⑬）需要一段解说文字，结构：
```
【过程类型名】

一句话定义。

关键交互特征：
- 特征1
- 特征2
- ...

在示例中演示的帧：x.y ~ x.z（共 N 帧）。
浮层结构标准内容见附录 A.x。
```

**13 段解说文字**需要逐一编写（数据源：03-评审与差异.md § 12.2 的示例 + 01-基础规则各章节）。

### 5.3 rail ↔ beat 映射维护

- 维护一个 `processTypes[]` 数组，每项含 `{ id, name, beatRange, parentGroup }`
- Player 推进 beat 时，根据当前 beat 序号高亮对应的 rail 行
- 一个 beat 可能同时属于多个过程类型（如 b34 同时属于⑧文件操作和⑨异常处理）——取最细粒度

**验证方式**：
- rail 显示 13 行过程类型（含层级缩进）
- 点击跳转正确
- Player 推进时 rail 高亮正确
- note 内容正确
