# Agent 对话流体验哲学：总原则与设计指南
## 0. 总纲
Agent 对话流不是普通聊天界面。
普通 Chatbot 的体验核心是：
> 用户提问，AI 回答。
Agent 产品的体验核心是：
> 用户委托一个目标，Agent 理解任务、拆解任务、调用工具、处理异常、生成结果，并在必要时让用户确认、追溯或接管。
因此，Agent 对话流设计的本质不是“如何展示一段回复”，而是：
> **如何让用户在一个复杂、异步、可能失败、可能调用外部工具的执行过程中，始终知道结果是什么、过程是否可信、风险是否可控、自己是否仍然掌握主动权。**
一句话总原则：
> **结果优先，过程可查，风险可控，失败可见，细节下钻，交付可验收。**
---
## 1. Agent 是执行系统，不是聊天机器人
Agent 类产品的核心不是“生成文本”，而是“完成任务”。
它可能会：
* 理解目标；
* 拆分步骤；
* 联网搜索；
* 读取文件；
* 写入文件；
* 生成图片；
* 生成文档；
* 创建草稿；
* 调用工具；
* 委派子任务；
* 发生错误；
* 自动修复；
* 重试；
* 等待用户确认；
* 产出可操作结果。
所以对话流 UI 不能只围绕“消息气泡”设计，而要围绕“任务执行”设计。
### 设计含义
对话流里至少有三类信息：
1. **结果信息**：用户真正要的答案、文件、方案、图表、草稿、总结。
2. **过程信息**：Agent 为了得到结果做了什么。
3. **控制信息**：哪些事情需要用户确认、修改、授权或接管。
好的 Agent 对话流，必须同时处理这三类信息，但不能让它们互相污染。
---
## 2. 结果优先，而不是过程优先
绝大多数用户最关心的是结果，而不是 Agent 调用了哪些工具。
用户真正关心的是：
* 方案是什么？
* 文件在哪里？
* 天气结论是什么？
* 路线怎么走？
* 预算够不够？
* 哪些事情完成了？
* 哪些事情失败了？
* 我接下来要做什么？
用户通常不关心：
* 哪个工具先调用；
* API 参数是什么；
* 中间日志是什么；
* 内部如何修复 Unicode 错误；
* Agent 每一步原始想法是什么。
这些过程信息有价值，但它们不是默认主角。
### 原则
> **主对话流默认服务结果，过程信息默认收起。**
### 设计指南
默认视图应该优先展示：
* 任务完成状态；
* 最终总结；
* 关键结论；
* 交付物；
* 下一步操作；
* 需要用户确认的事项。
不应该默认展示：
* 全量工具日志；
* 原始命令执行过程；
* 原始模型思考；
* 详细工具参数；
* 内部修复细节；
* debug trace。
---
## 3. 过程透明，但不能喧宾夺主
Agent 的过程必须透明，因为过程影响信任。
用户需要知道：
* Agent 是否真的执行了任务；
* 是否查过相关信息；
* 是否遇到失败；
* 是否做过重试；
* 是否绕开了某些限制；
* 是否有东西没有完成。
但透明不等于把全部过程默认暴露出来。
### 核心原则
> **透明不是默认裸露，而是需要时可追溯。**
也就是说：
* 普通用户默认看结果；
* 关心过程的用户可以展开任务概览；
* 想看细节的用户可以展开节点；
* 特别较真的用户可以进入原始执行记录；
* 想看模型理解的人可以查看原始思考。
这就是渐进式披露。
---
## 4. 渐进式披露是 Agent 对话流的基础结构
复杂 Agent 对话流不能用单层信息流承载。
单层信息流会导致两个极端：
1. **黑盒**：用户只看到结果，不知道过程是否可靠。
2. **日志流**：用户看到大量过程，找不到结果。
正确方式是分层。
推荐的基础结构是四层：
`txt
L0 结果层
L1 任务概览层
L2 节点摘要层
L3 原始追溯层`
### L0：结果层
面向大多数用户。
回答：
* 完成了吗？
* 结果是什么？
* 文件在哪里？
* 下一步是什么？
### L1：任务概览层
面向想确认过程的用户。
回答：
* Agent 大致做了哪些阶段？
* 哪些步骤完成了？
* 是否有异常？
* 是否可以进一步查看？
### L2：节点摘要层
面向想看某一步的人。
回答：
* 这个阶段具体做了什么？
* 对最终结果有什么贡献？
* 是否发生过失败或修复？
* 是否可以继续下钻？
### L3：原始追溯层
面向较真用户、高级用户、debug 用户。
回答：
* Agent 实际调用了什么？
* 出了什么错？
* 怎么修复？
* 原始思考是什么？
* 原始执行记录是什么？
### 原则
> **越靠上越产品化，越靠下越原始化。**
---
## 5. 用户关注结果，过程服务信任
过程信息的作用不是替代结果，而是支撑结果可信。
例如，用户要的是天气、路线、预算和旅行方案。
这些内容应该出现在结果里，而不是藏在过程里。
过程层只需要说明：
* 查询了天气；
* 查询了路线；
* 做了预算换算；
* 生成了文件；
* 遇到错误并恢复；
* 某些信息使用了替代来源。
### 设计判断
天气趋势、路线建议、预算换算结果：
> 放在结果层。
查询天气、查询路线、预算换算这些动作：
> 放在过程层。
天气 API 超时、网页 404、文件写入失败：
> 放在原始追溯层，必要时在节点摘要层轻量提示。
### 原则
> **用户任务结果归结果区，执行证据归过程区。**
---
## 6. 工具是实现手段，不是用户叙事的主角
Agent 产品会调用很多工具，但用户不一定关心工具本身。
用户说的是：
> 帮我规划一次关西家庭旅行。
不是：
> 请你依次调用 web_search、weather_api、currency_api、file_writer。
所以 UI 不应该把工具名当成主叙事。
### 好的任务节点
`txt
理解任务与约束
补充搜索旅行信息
生成地点图片
整合信息并输出方案`
### 不好的任务节点
`txt
web_search
tool_call_1
run_command
file_write`
工具调用可以存在，但应该作为下钻信息，而不是默认主线。
### 原则
> **对上用任务语言，对下保留工具细节。**
---
## 7. 等待体验的核心是“感知还在推进”
Agent 任务经常不是瞬间完成。
用户可以等待，但不能不知道发生了什么。
等待时用户最需要感知：
* Agent 是否还在运行；
* 当前做到了哪一步；
* 是否卡住；
* 是否出错；
* 是否正在修复；
* 是否需要用户确认；
* 是否已经部分完成。
### 不好的表达
`txt
Thinking...`
`txt
请稍候...`
`txt
正在处理...`
这些表达太空，无法支撑长任务。
### 更好的表达
`txt
正在查询交通与天气 · 第 2/5 步 · 已用 03m12s`
`txt
正在生成旅行手册 · 已完成 3 个步骤，1 个步骤运行中`
`txt
文件生成遇到错误，正在自动修复`
### 原则
> **等待越久，状态越要具体；任务越复杂，过程越要有秩序感。**
---
## 8. 错误、重试、修复是 Agent 过程的一部分
Agent 执行复杂任务时一定会失败。
可能失败的地方包括：
* 搜索失败；
* 网页打不开；
* 文件不存在；
* 没有权限；
* 格式错误；
* 代码执行失败；
* 工具超时；
* 文件生成失败；
* 输出格式错误；
* 自动修复失败。
这些错误不应该被完全隐藏。
否则用户无法理解：
* 为什么任务耗时很长；
* 为什么结果部分缺失；
* 为什么 Agent 做了某些替代；
* 任务是否真的可靠。
### 但错误也不应该污染主结果
错误展示应该分层：
`txt
L0：只展示是否影响结果
L1：展示哪个阶段有异常
L2：展示异常是否已恢复
L3：展示原始错误和修复过程`
### 示例
L0：
`txt
旅行方案已生成。`
L1：
`txt
生成旅行方案文档 · 已完成`
L2：
`txt
生成过程中遇到编码问题，已自动修复，最终文档已生成。`
L3：
`txt
Unicode escape error
使用 Python 修复文本编码
重新生成文档成功`
### 原则
> **错误不隐藏，但分层展示；失败不美化，但不抢占结果。**
---
## 9. 原始透明性比“过度包装”更重要，但要放在正确层级
有些产品会把所有过程都包装成用户友好的表达。
这会带来问题：
* 开发成本高；
* 各类错误都要做映射；
* 原始过程被遮蔽；
* 高级用户无法追溯真实原因；
* 透明性下降。
更合理的策略是：
> **浅层产品化，深层原始化。**
也就是：
* L0：产品化结果；
* L1：产品化任务阶段；
* L2：产品化节点摘要；
* L3：保留原始过程和原始思考。
这允许产品同时服务两类用户：
* 普通用户：只看结果和摘要；
* 较真用户：可以看到真实过程。
### 原则
> **不要为了“看起来友好”而抹掉真实过程。**
---
## 10. 原始思考可以存在，但必须和结果、执行过程分开
模型原始思考不是结果，也不是工具执行。
它是一类独立信息。
它可能包含：
* 任务理解；
* 约束识别；
* 决策依据；
* 内部分析；
* 中英文混合；
* 未整理推理。
如果产品选择展示它，就应该明确标识其原始性。
### 推荐命名
`txt
原始思考
模型思考记录
查看原始思考过程`
### 不推荐
把原始思考伪装成用户友好的解释。
如果没有额外处理成本，不必强行总结原始思考。
但必须默认隐藏，并且和执行过程分开。
### 原则
> **思考是理解过程，执行是行动过程，结果是交付内容。三者不能混在一起。**
---
## 11. Agent 对话流要支持不同深度的用户
不是所有用户都一样。
至少有三类用户：
### 1. 结果型用户
只关心：
* 完成了吗？
* 结果是什么？
* 能不能用？
他们只需要 L0。
### 2. 审核型用户
关心：
* Agent 有没有认真做；
* 是否查了该查的信息；
* 有无失败；
* 结果是否可信。
他们需要 L1 和 L2。
### 3. 较真型用户 / 高级用户
关心：
* 原始过程；
* 具体工具；
* 错误细节；
* 修复方式；
* 模型思考。
他们需要 L3。
### 原则
> **同一个对话流，要同时服务“只看结果的人”和“要查到底的人”。**
这正是渐进式披露的价值。
---
## 12. 风险越高，控制权越要前置
不是所有 Agent 行为都需要用户控制。
如果 Agent 只是搜索信息、生成文档、总结内容，用户可以事后查看。
但如果 Agent 要执行真实外部动作，就必须给用户控制权。
高风险动作包括：
* 发送邮件；
* 创建日历邀请；
* 删除文件；
* 覆盖文件；
* 付款；
* 下单；
* 预订；
* 发布内容；
* 访问敏感文件；
* 修改第三方系统数据。
### 原则
> **信息型任务可以结果优先；行动型任务必须确认优先。**
对于高风险动作，必须明确：
* 即将做什么；
* 影响范围是什么；
* 是否可撤销；
* 是否只是草稿；
* 用户有哪些选择。
---
## 13. 用户控制权应按场景出现，而不是常驻堆满
Agent 产品不应该把所有控制按钮一直放在界面上。
这会制造压力，也会增加复杂度。
控制应该按状态出现。
### 运行中
可以提供：
* 停止；
* 暂停；
* 补充要求；
* 查看过程。
### 失败时
可以提供：
* 重试；
* 跳过；
* 手动补充；
* 查看原因。
### 需要确认时
必须提供：
* 允许；
* 先预览；
* 修改；
* 拒绝。
### 完成后
可以提供：
* 预览；
* 下载；
* 继续修改；
* 分享；
* 生成新版本。
### 原则
> **控制权不是按钮数量，而是在正确时刻给用户正确选择。**
---
## 14. 完成态不是结束语，而是验收界面
复杂 Agent 任务完成后，不应该只输出一句：
`txt
完成了。`
完成态应该帮助用户验收。
它应该回答：
* 哪些完成了？
* 哪些部分完成？
* 哪些失败？
* 哪些需要确认？
* 结果在哪里？
* 下一步可以做什么？
### 推荐完成态结构
`txt
总结
已完成：
- 生成 7 天旅行方案
- 完成预算拆分
- 生成旅行手册
部分完成：
- 天气使用历史气候参考，无法获得远期精确天气
失败或受限：
- 某网页无法访问，已使用替代搜索
需要确认：
- 是否创建日历草稿
交付物：
- 日本关西家庭旅行方案 v1.0
- 预算表
- 邮件草稿`
### 原则
> **Agent 的完成态应该像任务验收，而不是普通回复结尾。**
---
## 15. 交付物要有明确身份
Agent 产出的东西往往不是单纯文本，而是交付物。
例如：
* 文档；
* 表格；
* 图表；
* 图片；
* HTML；
* PDF；
* 日历草稿；
* 邮件草稿；
* 待办清单；
* 代码 patch；
* 数据文件。
交付物应该让用户明确知道：
* 它是什么；
* 是否已生成；
* 是否可预览；
* 是否可下载；
* 是否可继续修改；
* 是否是最新版本。
### 原则
> **把 Agent 的产物当作对象，而不是当作一句文本链接。**
---
## 16. 状态体系要真实表达复杂性
Agent 过程不是只有“完成”和“失败”。
至少应该考虑这些状态：
* 未开始；
* 运行中；
* 已完成；
* 部分完成；
* 失败；
* 超时；
* 重试中；
* 已跳过；
* 等待用户；
* 权限不足；
* 需要确认；
* 已取消；
* 已恢复。
但这些状态不一定都在主界面展开。
### 设计原则
> **状态体系要完整，展示权重按影响决定。**
例如：
* 已完成可以弱展示；
* 运行中需要可感知；
* 失败需要可追溯；
* 等待用户必须突出；
* 原始错误放深层；
* 已恢复的错误可以在节点摘要中轻量提示。
---
## 17. 信息密度要由用户意图驱动
Agent 对话流最容易出现信息过载。
所以每一层都要有明确的信息密度策略。
### L0 结果层
低密度。
只放结果、交付物、关键总结。
### L1 任务概览层
中低密度。
只放阶段和状态。
### L2 节点摘要层
中密度。
放阶段说明、产出、异常摘要。
### L3 原始追溯层
高密度。
可以放原始日志、错误、工具细节、思考记录。
### 原则
> **不是所有信息都要变少，而是不同层级承载不同密度。**
---
## 18. 公开透明不是把所有东西放到台面上
Agent 产品需要公开透明，但“公开透明”不等于“默认全部展示”。
更准确的定义是：
> 用户有需要时，能够追溯到足够真实的信息。
所以透明性的核心不是默认展示量，而是：
* 是否能找到；
* 是否够真实；
* 是否够完整；
* 是否不被过度改写；
* 是否能解释结果来源。
### 原则
> **透明是一种可追溯能力，不是一种默认展示策略。**
---
## 19. Agent 对话流的核心体验目标
一套好的 Agent 对话流，应该让用户产生以下感受：
### 1. 我知道它在帮我完成什么
对应设计：
* 任务理解；
* 目标复述；
* 任务阶段。
### 2. 我知道结果在哪里
对应设计：
* 总结；
* 文件；
* artifact；
* 交付物入口。
### 3. 我知道它不是瞎编
对应设计：
* 执行过程；
* 工具记录；
* 来源；
* 节点摘要。
### 4. 我知道出错时发生了什么
对应设计：
* 错误可追溯；
* 重试记录；
* 修复过程；
* 部分成功说明。
### 5. 我知道什么时候需要我参与
对应设计：
* 审批；
* 权限；
* 等待用户；
* 确认按钮。
### 6. 我知道我可以继续控制
对应设计：
* 停止；
* 重试；
* 修改；
* 继续追问；
* 更新结果。
### 7. 我知道任务已经可以验收
对应设计：
* 完成总结；
* 成功/失败/待确认分区；
* 交付物；
* 下一步操作。
---
## 20. 核心反模式
### 反模式 1：过程污染结果
把所有工具调用、错误、日志直接堆在主对话流里。
问题：
* 用户找不到结果；
* 对话流变成日志流；
* 普通用户被吓退。
---
### 反模式 2：完全黑盒
只显示“正在处理”，最后直接给结果。
问题：
* 用户不知道是否在运行；
* 长等待不可信；
* 出错时无法解释；
* 结果缺乏证据。
---
### 反模式 3：假透明
展示一些看似过程的信息，但无法下钻到真实过程。
问题：
* 用户无法验证；
* 高级用户不信任；
* 过程变成装饰。
---
### 反模式 4：过度包装错误
把真实错误全部改写成模糊提示。
问题：
* 用户不知道真实问题；
* 失败原因不可追溯；
* 修复过程不可见。
---
### 反模式 5：工具名主导叙事
把用户任务拆成一堆 API 名称。
问题：
* 用户无法理解；
* 产品像开发者工具；
* 任务目标被工具细节淹没。
---
### 反模式 6：完成态太弱
复杂任务完成后只给一句“完成了”或一条普通链接。
问题：
* 用户不知道成果范围；
* 无法验收；
* 不知道下一步。
---
### 反模式 7：思考、执行、结果混在一起
把模型思考、工具调用和最终回答混合在同一信息流。
问题：
* 用户不知道哪些是结论；
* 哪些是行动；
* 哪些是内部分析；
* 体验混乱。
---
## 21. 总原则清单
以后设计 Agent 对话流时，可以用这组原则判断。
### 原则 1：结果优先
默认视图服务结果，不服务日志。
### 原则 2：过程可查
过程不能消失，要能逐层追溯。
### 原则 3：渐进披露
不同深度的信息给不同意图的用户。
### 原则 4：浅层产品化，深层原始化
上层易读，下层真实。
### 原则 5：任务语言优先于工具语言
用户看到的是“做了什么任务”，不是“调用了什么 API”。
### 原则 6：等待要有感知
长任务必须让用户知道还在推进。
### 原则 7：错误不隐藏
错误、重试、修复是执行过程的一部分，但要放在合适层级。
### 原则 8：思考、执行、结果分离
三类信息不能混在一起。
### 原则 9：风险越高，确认越前置
涉及真实外部动作时，必须让用户确认。
### 原则 10：完成态即验收态
复杂任务完成后，要帮助用户验收成果。
### 原则 11：交付物是对象
文件、图表、草稿、报告不只是普通链接。
### 原则 12：透明是一种能力，不是默认展示量
用户需要时能查到，才是真透明。
---
## 22. 一句话结论
Agent 对话流设计的核心，不是把每个工具调用做得多漂亮，也不是把全部过程都展示出来，而是建立一套清晰的信息秩序：
> **结果在前，过程在后；摘要在前，原始在后；用户语言在前，工具细节在后；风险动作前置确认；失败过程保留追溯；最终交付能够验收。**
这就是 Agent 对话流体验设计的基本哲学。
