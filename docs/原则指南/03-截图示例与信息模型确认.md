# 截图示例与信息模型确认

## 用户

我给你看看示例吧
a.png就是完成态，展示的执行结果
b.png就是点击“任务耗时”，会展开执行过程，包括思考过程和执行节点
c.png就是点开节点1之后的展示，会展示该节点下ai的执行内容
d.png是比较复杂的工具调用、创建文件之类的节点类型
e.png就是点开“已调用技能，执行命令”，出现的浮层详情，也就是这种颗粒度的节点详情，就已经是用浮层来承载了
f.png则是更细一层颗粒度的详情，则是通过浮层下钻的方式来承载
这一套可能更直观能感受到信息是如何分级处理的，也体现了交互流程逻辑。你来把这套信息框架也梳理出来。

## 助手

这组截图非常关键。它把前面抽象的“结果优先、过程可查、细节下钻”变成了一个可感知的交互模型。
我现在会把它梳理成一套更明确的信息框架。
1. 这套示例的本质：一个 Run 的双态结构
这不是普通消息流，而是一个 **Agent Run 容器**。
一次用户请求之后，系统生成一个 Run。这个 Run 有两个主要状态：

执行中 / 可追踪态
完成后 / 可验收态
截图 a 展示的是完成态：用户默认看到的是最终结果、交付物、方案概要，而不是过程日志。
截图 b 展示的是过程展开态：用户点击“任务耗时 19m40s”后，执行过程展开出来，显示思考过程和执行节点。
所以这套交互的核心不是“展开更多文字”，而是：
**同一个 Agent Run，在完成后默认呈现结果；用户需要追溯时，再展开执行过程。
这和你前面文档里的原则是一致的：主对话流默认服务结果，过程信息默认收起；透明不是默认裸露，而是需要时可追溯。

2. 顶层结构：结果区和过程区分离
从 a / b 可以看出，这个界面有两个大区：

Agent Run
├─ 结果区 Result Area
└─ 过程区 Process Area
结果区
对应 a.png。
它默认展示：

总结
查看交付物
方案概要
正文结果
它的职责是让用户快速知道：
任务完成了吗；
最终交付物在哪里；
结果是什么；
接下来能不能继续追问或修改。
这部分必须干净，不应该混入工具调用、命令、报错、修复过程。
过程区
对应 b.png 之后的内容。
它默认折叠，通过“任务耗时 / 执行过程入口”展开。
它的职责是让用户知道：
Agent 做了哪些阶段；
每个阶段是否完成；
哪些节点可以继续展开；
哪些节点里有工具调用、文件创建、命令执行等细节。
所以完整结构应该是：

用户消息
└─ Agent Run
├─ 完成态结果
│  ├─ 总结
│  ├─ 交付物入口
│  └─ 结果正文
│
└─ 可展开过程
├─ 思考过程 / 任务理解
├─ 执行节点列表
├─ 节点详情
├─ 工具调用详情
└─ 原始命令 / 输出
3. 这套截图里的信息分级
我建议把 a-f 抽象成 6 个层级，而不是简单 4 个层级。前 4 层是主链路，后 2 层是浮层下钻。

L0 结果呈现层
L1 执行过程总览层
L2 节点展开层
L3 节点内事件层
L4 工具 / 技能详情浮层
L5 原始命令 / 原始输出浮层
这比之前的 L0-L3 更贴近你截图里的真实交互。
4. L0：结果呈现层
对应 a.png。
这是用户默认看到的完成态。

总结
所有任务已完成
查看日本关西家庭旅行方案 v1.0
方案概要
正文内容
这一层的目标是：
让结果型用户不用看过程，也能完成验收。
这里应该展示：
任务完成状态；
总结；
交付物；
结果正文；
重要限制或部分失败；
下一步操作。
这里不应该展示：
思考过程；
工具调用；
命令行；
文件写入过程；
Unicode 修复细节；
原始日志。
这一层就是你文档里的“完成态即验收态”：不是说一句“完成了”，而是帮助用户判断成果是否可用。

5. L1：执行过程总览层
对应 b.png。
用户点击“任务耗时 19m40s”之后，出现：

思考过程 >
任务理解与分解：明确需求、约束和输...
补充搜索：关西周游卡 / ICOCA 详情及景...
生成关西主要地点图片
整合信息，输出完整旅行方案文档
这一层的核心是 **执行节点目录**。
它回答：
Agent 大致做了哪些阶段；
每个阶段是否完成；
有没有节点可以展开；
过程是否可信；
是否真的执行过任务。
这一层应该是“任务语言”，不是“工具语言”。
所以这里写：

补充搜索：关西周游卡 / ICOCA 详情
比写：

web_search
browser.open
tool_call_2
更好。
这里的状态表达也很关键：
绿色对勾表示完成；
节点标题表示阶段；
右侧箭头表示可展开；
“思考过程”表示有更高层的任务理解或规划记录；
“任务耗时”表示整个 Run 可追溯。
但我建议把“任务耗时”这个入口稍微改名。
现在它的功能其实不是只看耗时，而是展开过程。因此更准确的入口可以是：

执行过程 · 19m40s
或者：

查看执行过程 · 19m40s
“任务耗时”更像指标，不像入口。
6. L2：节点展开层
对应 c.png。
用户点开第一个节点后，看到：

任务理解与分解
目标：为一家四口规划 2026 年 9 月 18 日-24 日日本关西 7 日旅行完整方案...
关键约束：
- 父亲膝盖不好
- 母亲不吃生食
- 偏好自然风光和城市街区
- 4 人出行，需要考虑家庭友好性
子任务分解：
表格...
这一层不再只是目录，而是节点摘要。
它回答：
这个节点具体做了什么；
Agent 如何理解任务；
识别了哪些约束；
拆了哪些子任务；
这个节点对最终结果有什么贡献。
这个层级非常重要，因为它服务的是“审核型用户”。
审核型用户不一定要看原始工具日志，但他想确认 Agent 没有瞎做。
所以 L2 的内容应该是：

结构化摘要
关键判断
约束识别
子任务拆分
阶段产出
而不是：

完整模型思考
完整 debug log
完整 API 参数
这里有一个需要注意的点：截图 c 里“任务理解与分解”既像思考，也像执行节点。后续规范里可以把它定义为一种特殊节点类型：
**Planning Node / 规划节点
它不是工具执行节点，但它是 Run 的一部分。
7. L3：节点内事件层
对应 d.png。
截图 d 里，“整合信息，输出完整旅行方案文档”这个节点展开后，内部出现了更复杂的过程：

现在整合所有信息，生成完整的旅行方案文档：
已调用技能，执行命令 >
好的，docx 已安装。现在创建完整的旅行方案文档：
已创建文件，执行命令，读取文件，编辑文件 >
Now let me also fix the other issues...
已搜索文件，编辑文件 >
Now let me also check...
这一层已经不是普通节点摘要，而是节点里的事件流。
它包含几类信息：
自然语言执行说明；
技能调用；
命令执行；
文件创建；
文件读取；
文件编辑；
错误检查；
自动修复；
中英文混杂的原始执行痕迹。
这个层级非常接近原始过程，但还没有完全进入原始命令详情。
所以我建议叫：
**节点内事件层
它的作用是承接复杂节点，避免一个节点被压缩成一句“已完成”。
这层的展示规则应该是：

默认展示事件标题 + 轻量摘要
具体命令 / 参数 / 输出进入浮层
也就是说，d.png 里这种：

已调用技能，执行命令 >
已创建文件，执行命令，读取文件，编辑文件 >
已搜索文件，编辑文件 >
就是 L3 事件入口。
它比 L2 更细，但还不直接把所有命令摊开。
8. L4：工具 / 技能详情浮层
对应 e.png。
用户点开“已调用技能，执行命令”后，出现底部浮层：

过程
调用技能 docx
docx
Comprehensive document creation...
...
执行命令 which node && node -v && np...
这一层已经从主对话流进入浮层。
这里有一个非常好的交互判断：
颗粒度进一步变细之后，不再继续撑开主对话，而是用浮层承载。
这可以避免主对话流变成长日志。
L4 的职责是展示：
调用了什么技能；
技能说明是什么；
执行了什么动作；
有哪些可继续下钻的命令或原始事件。
这一层已经开始允许出现工具名，比如 `docx`。
原因是用户已经主动追溯到了工具层，此时再隐藏工具名反而会降低透明度。
所以规则应该是：

L1 / L2：任务语言
L3：事件语言
L4 / L5：工具语言和原始语言
这就是“对上用任务语言，对下保留工具细节”。
9. L5：原始命令 / 原始输出浮层
对应 f.png。
用户继续点开命令后，出现：

命令
which node && node -v && npm list -g docx ...
输出
/root/.nvm/versions/node/...
v22.22.2
...
docx@9.6.1
这一层是最原始的追溯层。
它回答：
实际执行了什么命令；
原始输出是什么；
环境是什么；
工具是否安装；
是否成功；
是否有报错。
这层应该服务：
高级用户；
debug 用户；
内部测试人员；
对结果可信度要求很高的人。
这一层不应该默认显示在主流里。
它适合用：

底部浮层
二级浮层
详情页
日志面板
而不是继续插进聊天正文。

11. 主界面和浮层的分工
这组截图里最有价值的地方，是它已经隐含了一个“承载介质分层”。
不是所有层级都用同一种 UI 展示。

主对话流：结果 + 一级过程 + 节点摘要
主对话内展开：节点详情 + 事件摘要
底部浮层：工具详情
二级浮层：命令 / 原始输出
我会把它定义成：
主对话流承载
适合展示：
最终结果；
任务完成状态；
交付物；
执行过程入口；
大节点列表；
节点摘要。
原因是这些信息和用户任务强相关，应该留在上下文里。
主对话内展开承载
适合展示：
任务理解；
子任务分解；
阶段产出；
事件摘要；
已恢复异常摘要。
原因是这些信息有助于建立信任，但仍然是“产品化过程”。
浮层承载
适合展示：
技能说明；
工具调用；
命令；
原始输出；
文件操作详情；
debug 信息。
原因是这些信息密度高、阅读人群少，不应该污染主流。
12. 信息层级和用户类型的对应关系
这套截图天然对应三类用户。

结果型用户
只看 a.png
完成态结果 + 交付物
审核型用户
看 b.png / c.png
执行过程列表 + 节点摘要
较真型用户 / 高级用户

所以后续规范里可以明确写：

L0 给结果型用户
L1-L2 给审核型用户
L3-L5 给较真型用户
这比“所有人都看同一个过程”要合理很多。

15. 对现有示例的几个优化建议
这个示例方向是对的，但我会做几个小调整。
1. “任务耗时”建议改为“执行过程”
现在“任务耗时 19m40s”承担了展开过程的入口，但语义不够直接。
建议：

执行过程 · 19m40s
或者：

查看执行过程 · 19m40s
这样用户知道点开是看过程，而不是只看耗时。
2. “思考过程”建议拆成“任务理解”和“执行计划”
“思考过程”容易让用户以为里面是模型原始思考。
建议分成：

任务理解
执行计划
关键决策
如果真的要展示原始思考，应该放到更深层，且明确标注为“原始”。
3. d.png 里的英文原始过程不应直接暴露在节点层
例如：

Now let me also fix the other issues...
这类内容更像原始执行痕迹，建议默认收进事件详情。
L3 可以显示成：

检查并修复文档编码问题 · 已恢复
点开后再展示英文原始记录。
4. 技能说明可以更短
e.png 里 `docx` 的技能说明很长。对普通用户来说不重要。
建议默认显示：

调用技能：docx
用途：创建和编辑 Word 文档
完整技能说明可以继续下钻。
5. f.png 的命令详情应该支持复制
原始命令和输出对高级用户有用，因此这里应该提供：

复制命令
复制输出
查看完整日志
16. 最终框架可以这样定稿
我建议最终规范把这套截图总结成一句话：
**Agent Run 完成后默认进入结果交付态；执行过程折叠为可追溯入口。用户可按“过程总览 → 节点摘要 → 节点事件 → 工具详情 → 原始命令输出”逐级下钻。主对话流只承载结果和产品化过程，高密度工具与日志信息进入浮层。
更结构化一点就是：

完成态：
结果优先，过程折叠
展开态：
先看过程总览
节点态：
查看某一阶段具体做了什么
事件态：
查看这个阶段里的动作链
工具态：
查看调用了什么技能 / 工具
原始态：
查看命令、输出、错误、路径、日志
这套已经很接近一个完整的 Agent 对话流信息架构了。下一步可以把它进一步整理成规范文档里的核心章节：

1. Agent Run 容器模型
2. 完成态与执行态
3. 六级信息层级
4. 主流 / 展开 / 浮层的承载规则
5. 节点类型规范
6. 事件类型规范
7. 状态表达规范
8. 追溯下钻规范
9. 错误与恢复展示规范
10. 组件清单
