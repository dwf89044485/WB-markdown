# 文档系统规划

## 用户

现在你来系统性思考，要怎么沉淀成一套文档，把这些东西都细致地承载下来。你建议第一步先做什么

## 助手

我建议第一步**不要直接写大而全的规范文档**，也不要马上做组件说明或 HTML。第一步应该先沉淀一份**“总框架文档 / 北极星文档”**，把这件事的核心对象、生命周期、信息层级、承载方式先定下来。
这份文档可以叫：
**Agent Run 对话流交互框架 v0.1
它不是最终规范全集，而是后面所有规范的“地基”。
1. 你现在要沉淀的不是一篇文档，而是一套文档系统
现在材料已经有三类：
第一类是**哲学原则**：结果优先、过程可查、风险可控、失败可见、细节下钻、交付可验收。你前面的文档已经明确说，Agent 产品不是普通聊天机器人，而是用户委托目标后，Agent 理解任务、拆解任务、调用工具、处理异常、生成结果，并在必要时让用户确认、追溯或接管；对话流也至少要处理结果信息、过程信息、控制信息三类内容，且不能互相污染。

第二类是**交互样例**：你刚才给的 a-f 截图。它们把抽象原则落成了具体体验：完成态默认展示结果，点击执行过程展开节点，再通过节点、事件、浮层、命令详情逐级追溯。
第三类是**未来要指导设计和研发的规范**：状态、节点类型、事件类型、浮层规则、错误展示、控制权、交付物卡片、文案、组件等。
所以最终不是一份文档，而应该是一套分层文档：

00 总框架文档
01 生命周期与状态规范
02 信息层级与追溯规范
03 结果交付规范
04 执行过程展示规范
05 节点与事件类型规范
06 工具调用与原始日志规范
07 错误 / 重试 / 恢复规范
08 用户控制与确认规范
09 组件与交互模式规范
10 场景案例与验收 checklist
但第一步不能直接写 10 份。第一步要先把最核心的“骨架”定下来。
2. 第一份文档应该解决什么问题
第一份文档不应该陷入按钮、间距、颜色、卡片样式。
它应该先回答 6 个根问题。
问题 1：这个系统的核心对象是什么？
我建议核心对象叫：
**Agent Run
也就是一次用户委托触发的一次完整执行。
不是一条 Assistant Message，也不是一组工具日志，而是一个完整任务容器：

Agent Run
├─ 用户目标
├─ 任务理解
├─ 执行计划
├─ 执行过程
├─ 工具 / 技能 / 文件操作
├─ 异常 / 重试 / 恢复
├─ 最终结果
├─ 交付物
└─ 追溯记录
这个概念必须先定下来。否则后面会一直混淆：到底是在设计“消息”，还是在设计“任务执行对象”。
问题 2：Agent Run 有哪两个大阶段？
我建议第一份文档明确写：

阶段一：执行过程态
阶段二：结果交付态
执行过程态的目标是：
让用户感知任务正在推进，并在需要时可以干预。
结果交付态的目标是：
把执行过程折叠起来，干净地呈现可验收结果。
这就是你现在最关键的判断：
运行中，过程在前；完成后，结果在前，过程退到可追溯入口。
这个原则应该成为所有后续设计的基础。
问题 3：完成态和展开态是什么关系？
a.png 和 b.png 其实已经给了答案。
完成态不是“另一条消息”，而是同一个 Run 的默认视图。

默认：
Agent Run → Result View
点击执行过程：
Agent Run → Result View + Process View
也就是说：

完成态 = 结果优先
展开态 = 结果 + 可追溯过程
这点很重要。它避免把过程日志直接堆进主对话流，也避免变成完全黑盒。
问题 4：追溯应该分几层？
你现在的截图其实已经把追溯层级跑通了。我建议第一份文档先定为六层：

L0 结果呈现层
L1 执行过程总览层
L2 节点摘要层
L3 节点内事件层
L4 工具 / 技能详情层
L5 原始命令 / 原始输出层
对应你的截图：

a.png → L0 结果呈现层
b.png → L1 执行过程总览层
c.png → L2 节点摘要层
d.png → L3 节点内事件层
e.png → L4 工具 / 技能详情层
f.png → L5 原始命令 / 原始输出层
这套层级要成为整套规范的主干。
问题 5：不同层级由什么 UI 介质承载？
第一份文档还要定清楚：不是所有信息都放在主流里。
我建议明确三种承载介质：

主对话流
├─ 承载 L0 结果
├─ 承载 L1 过程总览
└─ 承载 L2 节点摘要
主对话内展开
├─ 承载 L2 节点详情
└─ 承载 L3 事件摘要
底部浮层 / 详情浮层
├─ 承载 L4 工具 / 技能详情
└─ 承载 L5 原始命令 / 输出
这个非常关键。
因为它决定了信息密度如何控制：
结果留在主流；
产品化过程可以展开；
高密度工具和日志进入浮层；
原始命令和输出继续下钻。
这也正好符合你前面文档里的“越靠上越产品化，越靠下越原始化”。
问题 6：哪些东西必须分离？
第一份文档必须把几个边界写死：

结果 ≠ 过程
过程 ≠ 原始日志
任务理解 ≠ 原始思考
工具调用 ≠ 用户叙事
完成态 ≠ 普通结束语
交付物 ≠ 普通链接
尤其要明确：
思考、执行、结果三者不能混在一起。
可以有“任务理解”和“执行计划”，但不要把原始模型思考直接混进用户结果区。
3. 第一份文档应该长什么样
我建议第一份文档控制在中等篇幅，不要一上来写成百科。它的目标是“对齐认知”，不是覆盖所有细节。

4. 为什么第一步不是做组件规范
因为现在最容易走偏的是直接开始定义组件：
任务耗时组件；
思考过程组件；
节点卡片；
技能浮层；
命令浮层；
交付物卡片。
这些都要做，但不是第一步。
原因是：组件只是表层。真正要先定的是信息模型。
比如“已调用技能，执行命令”到底是一个节点，还是一个事件，还是一个工具调用组？
“思考过程”到底是一级入口，还是规划节点，还是原始思考？
“任务耗时”到底是耗时指标，还是过程入口？
“创建文件、读取文件、编辑文件”是展示给用户的事件，还是只应该收进浮层？
这些不先定，组件会越做越乱。
所以第一步应该先回答：
这个系统里的信息对象是什么？它们怎么分层？什么时候在哪个层级展示？
5. 我建议第一步的具体产出
第一步产出不要太大，就做一个 **v0.1 总框架文档**。
我建议它包含 4 个核心图 / 表。
图 1：Agent Run 生命周期图

用户消息
→ 任务理解
→ 执行计划
→ 执行中
→ 工具 / 技能 / 文件操作
→ 异常 / 恢复
→ 结果生成
→ 完成态交付
→ 过程追溯
这个图回答：一次 Run 怎么走完。
图 2：完成态 / 展开态关系图

完成态默认：
结果区 + 交付物 + 下一步
点击执行过程：
结果区 + 过程总览 + 节点列表
继续下钻：
节点详情 → 事件详情 → 工具浮层 → 原始输出
这个图回答：用户怎么从结果走向追溯。
表 1：六级信息层级表

L0 结果呈现层：总结、交付物、结果正文
L1 过程总览层：节点列表、完成状态、耗时
L2 节点摘要层：目标、约束、阶段产出、子任务
L3 节点事件层：调用技能、创建文件、执行命令、修复问题
L4 工具详情层：技能说明、工具调用、参数摘要
L5 原始记录层：命令、输出、错误、路径、日志
这个表回答：每层放什么，不放什么。
表 2：承载介质表

主对话流：L0 / L1 / 部分 L2
对话内展开：L2 / L3
底部浮层：L4
二级浮层：L5
这个表回答：什么信息应该放在哪里。
6. 这一步完成后的判断标准
第一步文档写完后，不是看它文采好不好，而是看它能不能回答下面这些问题：

1. 我们是否明确了 Agent Run 是核心对象？
2. 我们是否明确了执行过程态和结果交付态？
3. 我们是否明确了完成后过程默认折叠？
4. 我们是否明确了追溯至少有 L0-L5？
5. 我们是否明确了每一层放什么、不放什么？
6. 我们是否明确了主流、展开区、浮层的分工？
7. 我们是否明确了思考、执行、结果不能混在一起？
8. 我们是否能用 a-f 截图解释这套模型？
如果这 8 个问题都能回答，第一步就完成了。
7. 后续再拆什么
等第一份总框架文档定下来，再开始拆细文档。
我建议第二步做：
**节点与事件类型规范
因为你现在截图里最复杂、最容易乱的地方就是节点和事件。
例如：

任务理解节点
搜索节点
图片生成节点
文档生成节点
文件操作事件
命令执行事件
技能调用事件
错误恢复事件
来源引用事件
用户确认事件
第三步再做：
**完成态与结果交付规范
把 a.png 这种结果态做成标准模板。
第四步做：
**追溯浮层规范
把 e.png / f.png 这种底部浮层、命令详情、输出详情定清楚。
但第一步一定是总框架。
8. 我的建议一句话
第一步先写：
**《Agent Run 对话流交互框架 v0.1》**
目标不是把所有组件设计完，而是先把这套东西的底层骨架定下来：

一个核心对象：Agent Run
两个阶段：执行过程态 / 结果交付态
六级层级：结果 → 过程 → 节点 → 事件 → 工具 → 原始记录
三种承载：主对话流 / 对话内展开 / 浮层下钻
一个原则：完成后结果优先，过程可追溯
这一步做好，后面的文档、组件、原型、HTML、研发字段设计，都会有共同语言。
