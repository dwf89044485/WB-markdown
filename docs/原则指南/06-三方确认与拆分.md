## 助手

我的理解是：你现在不是要我马上写一份“大而全”的文档，而是要先把**文档体系怎么切**想清楚。尤其要避免三个混乱：
**规范和 mock 数据混在一起
规范应该沉淀规则，不应该塞满“关西旅行方案”的完整 mock 内容。mock 只在 demo / 评审页交接文档里完整出现。规范里只放最小必要示例，用来说明规则。
**静态信息架构和动态交互流程混在一起
信息架构回答“有哪些层级、每层放什么”；动态交互回答“这些信息什么时候出现、怎么加载、完成后怎么折叠、点击后怎么展开、什么时候进入浮层”。这两类要分开写，否则文档会又像原则文档，又像交互说明，读起来散。
**体验规范和研发实现混在一起
你是产品体验设计师，目标不是定义字段、接口、状态机，而是让团队理解交互逻辑、渲染节奏、信息分级和演示方式。所以文档应该站在“体验表达”和“设计评审”的层面。
你原始文档里已经明确了基础原则：Agent 对话流不是普通聊天回复，而是围绕任务执行组织；对话流里至少有结果信息、过程信息、控制信息三类内容，并且不能互相污染。

也明确说主对话流默认服务结果，过程信息默认收起；透明不是默认裸露，而是需要时可追溯。

01 文档：Agent Run 对话流体验规范
这份是**静态规范**。
它回答：
这套 Agent 对话流的基本结构是什么？信息怎么分层？什么应该放在主流，什么应该下钻？
它不写完整 mock 数据，也不写复杂运行过程。
它应该包含：

1. 设计目标
2. 核心对象：Agent Run
3. 两个阶段：执行过程态 / 结果交付态
4. 信息分类：结果信息 / 过程信息 / 控制信息
5. 信息层级：L0-L5
6. 承载介质：主对话流 / 对话内展开 / 浮层下钻
7. 展示原则
8. 反模式
9. 验收 checklist
这里的示例要极简。
比如只写：

L1 过程总览层：
- 任务理解与分解 · 已完成
- 补充搜索旅行信息 · 已完成
- 整合信息并输出文档 · 已完成
不要把完整旅行方案、完整节点内容、完整命令输出放进来。
这份文档的价值是：以后不管 demo 讲什么任务，团队都知道这套对话流的基本规则。
02 文档：Agent Run 动态交互与渲染流程规范
这份是**动态交互规范**。
它回答：
Agent 运行过程中，信息是如何逐步出现、更新、折叠、展开、下钻的？
这部分是你刚才特别提醒的重点：信息架构是静态的，但 Agent 运行是动态的。
它应该单独成文。
它不写底层字段，只写体验层面的动态规则。
比如：
1. 用户发起任务后
页面进入执行过程态。
需要展示：

Agent 已开始处理
当前阶段
已用时间
可展开过程入口
必要时显示停止 / 补充要求
不应该只显示：

Thinking...
因为原文已经强调，等待体验的核心是让用户感知还在推进，长任务状态要具体。

2. 思考 / 规划出现时
展示“任务理解”或“执行计划”，而不是直接展示原始思考。
比如：

任务理解与分解 · 进行中
完成后变成：

任务理解与分解 · 已完成
3. 执行节点逐步出现时
节点不是一开始全部堆出来，而是随着执行逐步生成和更新。

任务理解与分解 · 已完成
补充搜索旅行信息 · 运行中
生成地点图片 · 未开始
整合信息并输出文档 · 未开始
4. 节点完成后
节点状态更新，但内容默认不一定展开。
用户可以点开节点看摘要。
5. 复杂节点内部
如果节点里有工具调用、文件创建、命令执行、错误修复，不直接全部摊开。
先显示事件摘要：

已调用技能，执行命令 >
已创建文件，读取文件，编辑文件 >
检查并修复文档问题 >
继续点击再进入浮层。
6. 任务完成后
体验要发生一次主次切换：

执行过程态
→ 结果交付态
完成后默认展示结果，过程折叠为入口。
也就是：

总结
交付物
方案概要
结果正文
执行过程 · 19m40s · 已完成
这和原始文档里的“完成态不是结束语，而是验收界面”一致：完成态要回答哪些完成、哪些部分完成、哪些失败、结果在哪里、下一步是什么。

7. 用户追溯时
用户可以按层级展开：

结果
→ 执行过程
→ 节点
→ 事件
→ 工具 / 技能浮层
→ 原始命令 / 输出浮层
这部分就是你 a-f 示例里的动态链路。

这份是**交接文档**，不是规范本体。

以下内容仅用于 demo 和评审页演示，不是规范要求。
它可以分成两部分。
A. Demo 交接
用于你本地开发自由体验 demo。
内容包括：

Demo 场景
Mock 用户消息
Mock 完成态结果
Mock 执行节点
Mock 节点详情
Mock 工具浮层
Mock 命令浮层

这里才放完整 mock 内容。
比如“关西家庭旅行方案”可以完整放在这里。
B. 评审页交接
用于你本地开发可步进评审页。
每一步写清楚：

Step 1：完成态
展示什么
设计意图是什么
评审关注点是什么
Step 2：展开执行过程
展示什么
设计意图是什么
评审关注点是什么
Step 3：展开节点
...
评审页文档不需要像 demo 一样完整复刻所有内容，它更像讲解脚本。
这三份文档的边界
我会按下面这个边界处理。
规范文档里放什么
放稳定规则：

什么是 Agent Run
为什么完成后结果优先
信息分几层
每层放什么
每层不放什么
什么信息进入浮层
什么是反模式
只放最小示例。
动态交互文档里放什么
放运行节奏：

信息什么时候出现
节点怎么加载
状态怎么更新
过程什么时候折叠
用户怎么展开
浮层怎么下钻
完成态怎么切换
不写完整 mock 剧情。
Demo / 评审页交接文档里放什么
放演示数据：

完整 mock 场景
完整 mock 节点
完整 mock 文案
完整演示步骤
评审页 step-by-step 讲解
它是实现 demo 和评审页的素材包，不是规范本体。
我建议实际处理顺序
先写 01，再写 02，最后写 03。

01 先定静态结构
02 再定动态行为
03 最后把结构和行为翻译成 mock 演示
