Agent Run 对话流体验规范 v0.1
1. 文档目的
本文定义 Agent 执行型对话流的基础体验规范，用于指导产品设计、交互设计、Demo 制作和团队评审。
本规范关注：
Agent 任务执行后的信息如何组织；
结果、过程、控制信息如何分离；
执行过程如何分层追溯；
哪些信息应该进入主对话流；
哪些信息应该折叠、展开或进入浮层；
如何避免对话流变成黑盒或日志流。
本文不定义：
后端字段；
LLM 执行协议；
工具调用 schema；
真实数据结构；
生产级组件实现；
完整 mock 数据。
mock 数据仅在必要时作为最小示例出现，完整 demo 数据应放入独立的 Demo / 评审页交接文档。
2. 核心判断
Agent 对话流不是普通聊天回复，而是一次任务执行后的结果交付与过程追溯。
普通 Chatbot 的体验核心是：
用户提问，AI 回答。
Agent 对话流的体验核心是：
用户委托一个目标，Agent 理解任务、拆解任务、执行任务、处理异常、生成结果，并在必要时让用户确认、追溯或接管。
因此，Agent 对话流的设计重点不是“如何展示一段回复”，而是：
如何让用户在复杂、异步、可能失败、可能调用工具的执行过程中，始终知道结果是什么、过程是否可信、风险是否可控、自己是否仍然掌握主动权。
一句话原则：
结果优先，过程可查，风险可控，失败可见，细节下钻，交付可验收。
3. 核心对象：Agent Run
一次用户委托触发一次完整执行，这个执行对象称为：
Agent Run
Agent Run 不是单条 Assistant 消息，也不是一组工具日志，而是一个完整任务容器。
一个 Agent Run 通常包含：
用户目标；
任务理解；
执行计划；
执行过程；
执行节点；
节点内事件；
工具 / 技能 / 文件操作；
异常 / 重试 / 恢复；
最终结果；
交付物；
过程追溯入口。
设计时应把 Agent Run 视为一个整体对象，而不是把过程和结果拆成互不关联的多条消息。
4. 两个阶段
Agent Run 在体验上分为两个主要阶段。
4.1 执行过程态
执行过程态发生在用户发起任务之后、最终结果生成之前。
这一阶段的目标是：
让用户感知 Agent 仍在推进，并在必要时可以确认、补充、暂停或接管。
执行过程态需要表达：
当前任务是否已经开始；
Agent 正在做什么；
当前处于哪个阶段；
是否还在推进；
是否遇到异常；
是否正在重试或恢复；
是否需要用户确认；
是否已有部分结果。
执行过程态不应该只显示：
Thinking...
或：
正在处理...
长任务中，状态表达必须更具体。
推荐表达方式：
正在整理旅行方案 · 已完成 3/5 个阶段 · 已用 12m30s
4.2 结果交付态
结果交付态发生在任务执行完成之后。
这一阶段的目标是：
干净地呈现结果，让用户可以验收，同时保留过程追溯能力。
任务完成后，主对话流的主角应该从“执行过程”切换为“最终结果”。
默认展示：
总结；
最终结论；
交付物；
结果正文；
已完成 / 部分完成 / 失败或受限；
需要用户确认的事项；
下一步操作。
默认折叠：
执行节点；
工具调用；
命令执行；
文件操作；
错误修复过程；
原始日志；
原始思考。
核心规则：
运行中，过程在前；完成后，结果在前，过程折叠为可追溯入口。
5. 三类信息
Agent 对话流中至少包含三类信息。
5.1 结果信息
结果信息是用户真正要的内容。
例如：
答案；
方案；
总结；
文档；
表格；
图片；
图表；
草稿；
文件；
待办清单。
结果信息应该出现在结果区，而不是藏在过程区。
5.2 过程信息
过程信息说明 Agent 为了得到结果做了什么。
例如：
理解了任务；
拆解了步骤；
搜索了信息；
读取了文件；
生成了图片；
创建了文档；
遇到异常并恢复；
使用了替代方案。
过程信息用于建立信任，但不应默认污染结果呈现。
5.3 控制信息
控制信息说明哪些事情需要用户确认、修改、授权或接管。
例如：
是否继续执行；
是否允许发送邮件；
是否覆盖文件；
是否采用某个方案；
是否重试失败步骤；
是否跳过某个节点。
控制信息应在需要用户行动时突出展示，而不是长期堆在界面中。
6. 六级信息层级
Agent Run 的信息应按层级组织，支持渐进式披露。
推荐六级结构：
`L0 结果呈现层
L1 执行过程总览层
L2 节点摘要层
L3 节点内事件层
L4 工具 / 技能详情层
L5 原始命令 / 原始输出层`
6.1 L0：结果呈现层
L0 是任务完成后的默认视图。
面向用户：
结果型用户；
只关心任务是否完成、结果是否可用的人。
回答：
完成了吗？
结果是什么？
交付物在哪里？
有没有失败或限制？
下一步可以做什么？
应该展示：
总结；
关键结论；
交付物入口；
结果正文；
重要限制；
下一步操作。
不应该展示：
工具调用；
命令行；
原始日志；
原始思考；
调试信息；
详细修复过程。
最小示例：
所有任务已完成。以下是为你生成的完整旅行方案文档：
查看旅行方案 v1.0
6.2 L1：执行过程总览层
L1 是用户点击“执行过程”后看到的过程概览。
面向用户：
审核型用户；
想确认 Agent 是否真的做过任务的人。
回答：
Agent 大致做了哪些阶段？
哪些阶段完成了？
是否有异常？
是否可以继续展开？
应该展示：
执行过程入口；
总耗时；
阶段节点列表；
每个阶段的状态；
可展开入口。
不应该展示：
完整工具参数；
原始命令输出；
大段日志；
debug trace。
最小示例：
`执行过程 · 19m40s
✓ 任务理解与分解
✓ 补充搜索旅行信息
✓ 生成地点图片
✓ 整合信息并输出文档`
说明：
“执行过程”入口比“任务耗时”更清晰，因为用户点击后查看的不只是耗时，而是完整过程。
6.3 L2：节点摘要层
L2 是用户展开某个阶段节点后看到的内容。
面向用户：
审核型用户；
想确认某一步具体做了什么的人。
回答：
这个阶段做了什么？
识别了哪些重点？
产生了什么阶段产出？
是否有异常或恢复？
是否可以继续下钻？
应该展示：
节点标题；
节点目标；
关键判断；
约束识别；
子任务拆分；
阶段产出；
异常摘要。
不应该展示：
全量命令；
原始工具输出；
未整理的模型思考；
大段英文 debug 文本。
最小示例：
`任务理解与分解
目标：
为一家四口规划日本关西 7 日旅行方案。
关键约束：
- 需要控制预算
- 需要考虑家庭友好性
- 行程不宜过度紧张
阶段产出：
已将任务拆分为交通、住宿、景点、预算、交付文档五个方向。`
6.4 L3：节点内事件层
L3 是复杂节点内部的事件流。
面向用户：
深度审核用户；
想知道某个节点内部发生了哪些动作的人。
回答：
这个节点内部有哪些动作？
是否调用了技能？
是否创建或编辑了文件？
是否执行了命令？
是否发生错误或修复？
哪些动作可以继续查看详情？
应该展示：
事件摘要；
动作类型；
简短状态；
可下钻入口。
不应该默认展示：
完整命令；
完整输出；
文件完整内容；
原始错误堆栈；
长篇工具说明。
最小示例：
`整合信息并输出文档
已调用文档技能 >
已创建文件 >
已读取并编辑文件 >
已检查并修复格式问题 >`
说明：
L3 可以出现“调用技能”“创建文件”“执行命令”等事件语言，但仍应保持摘要化，不直接变成日志流。
6.5 L4：工具 / 技能详情层
L4 用于展示工具、技能、文件操作等更细的信息。
承载方式通常不应继续占用主对话流，而应进入浮层或详情面板。
面向用户：
高级用户；
需要确认工具使用情况的人；
设计评审或调试人员。
回答：
调用了什么工具 / 技能？
这个工具用于什么？
执行了哪些动作？
是否可以继续查看原始命令？
应该展示：
工具 / 技能名称；
简短用途；
动作摘要；
相关事件；
进一步下钻入口。
不应该展示：
过长技能说明；
全量工具文档；
大段原始日志。
最小示例：
`调用技能：docx
用途：创建和编辑 Word 文档
相关动作：
- 检查文档能力
- 创建旅行方案文档
- 编辑文档内容`
6.6 L5：原始命令 / 原始输出层
L5 是最深层追溯信息。
承载方式应使用浮层、二级详情页或日志面板。
面向用户：
较真用户；
高级用户；
debug 用户；
内部评审人员。
回答：
实际执行了什么命令？
原始输出是什么？
原始错误是什么？
文件路径是什么？
环境信息是什么？
应该展示：
命令；
输出；
错误原文；
路径；
原始记录。
不应该默认展示在主对话流里。
最小示例：
`命令：
which node && node -v
输出：
/root/.nvm/versions/node/...
v22.22.2`
说明：
L5 是可验证层，不是普通用户的默认阅读层。
7. 承载介质
不同层级的信息应由不同 UI 介质承载。
7.1 主对话流
主对话流承载：
L0 结果呈现；
L1 执行过程总览入口；
部分 L2 节点摘要。
主对话流的目标是保持任务上下文清晰。
主对话流不应承载：
全量工具日志；
完整命令输出；
大段错误堆栈；
复杂 debug 信息。
7.2 对话内展开
对话内展开承载：
L1 执行过程总览；
L2 节点详情；
L3 事件摘要。
对话内展开适合展示产品化过程信息。
它应该让用户确认 Agent 确实执行了任务，但不应把界面变成开发日志。
7.3 浮层下钻
浮层下钻承载：
L4 工具 / 技能详情；
L5 原始命令 / 原始输出。
当信息颗粒度进入工具、命令、日志、路径、原始输出时，应优先使用浮层或详情页，而不是继续撑开主对话流。
核心规则：
主流承载结果与产品化过程，浮层承载高密度追溯信息。
8. 任务语言与工具语言
Agent 对话流应区分任务语言和工具语言。
8.1 上层使用任务语言
L0-L2 应优先使用用户能理解的任务语言。
推荐：
`补充搜索旅行信息
生成地点图片
整合信息并输出文档`
不推荐：
`web_search
tool_call_1
run_command
file_write`
8.2 深层保留工具语言
L4-L5 可以保留真实工具名、命令和输出。
因为用户已经主动进入深层追溯，此时真实信息比包装表达更重要。
规则：
对上用任务语言，对下保留工具细节。
9. 思考、执行、结果分离
Agent 对话流中需要区分三类内容：
`思考 / 理解
执行 / 行动
结果 / 交付`
9.1 任务理解可以展示
可以展示：
用户目标；
关键约束；
任务拆解；
执行计划；
关键决策摘要。
示例：
`任务理解：
用户希望生成一份家庭旅行方案，需要考虑预算、老人行动便利性和亲子友好性。`
9.2 原始思考默认不展示
原始思考不应直接混入结果区或过程区。
如果产品需要提供“原始思考”入口，应作为深层追溯内容，并与工具执行记录、最终结果严格分离。
9.3 执行记录不等于结果
工具调用、文件操作、命令执行属于执行记录。
它们用于证明过程可信，但不应替代最终结果。
10. 完成态规范
完成态不是普通结束语，而是任务验收界面。
完成态应帮助用户确认：
哪些已完成；
哪些部分完成；
哪些失败或受限；
是否需要用户确认；
结果在哪里；
下一步可以做什么。
推荐结构：
`总结
已完成：
- ...
部分完成：
- ...
失败或受限：
- ...
需要确认：
- ...
交付物：
- ...
下一步：
- ...`
简单任务可以压缩，不必机械展示所有分区。
复杂任务应优先使用完整完成态结构。
11. 交付物规范
Agent 产出的文件、图片、表格、草稿、报告等应视为交付物对象，而不是普通文本链接。
交付物应表达：
它是什么；
是否已生成；
是否可查看；
是否可下载；
是否可继续修改；
是否是最新版本。
最小示例：
`查看旅行方案 v1.0`
更完整的交付物卡片可以包含：
`名称：日本关西家庭旅行方案 v1.0
类型：文档
状态：已生成
操作：查看 / 下载 / 继续修改`
12. 错误与恢复的展示原则
Agent 执行复杂任务时可能失败、重试或自动修复。
错误不应完全隐藏，但也不应污染主结果。
推荐分层：
`L0：只说明是否影响结果
L1：说明哪个阶段有异常
L2：说明异常是否已恢复
L3：展示事件级修复摘要
L4-L5：展示原始错误和输出`
示例：
`L0：
旅行方案已生成。
L1：
生成文档阶段曾遇到异常，已恢复。
L2：
生成过程中出现格式问题，已自动修复。
L5：
展示原始错误、命令和输出。`
原则：
错误不隐藏，但分层展示；失败不美化，但不抢占结果。
13. 用户控制权原则
不是所有 Agent 行为都需要用户提前确认。
信息型任务可以结果优先：
搜索；
总结；
生成文档；
提取信息；
生成草稿。
行动型任务必须确认优先：
发送邮件；
删除文件；
覆盖文件；
创建日历邀请；
下单；
支付；
发布内容；
修改第三方系统数据。
控制权应在正确场景出现，而不是常驻堆满。
运行中可以提供：
停止；
补充要求；
查看过程。
失败时可以提供：
重试；
跳过；
手动补充；
查看原因。
需要确认时必须提供：
允许；
预览；
修改；
拒绝。
完成后可以提供：
查看；
下载；
继续修改；
生成新版本。
14. 状态表达原则
Agent Run 的状态不应只有“完成”和“失败”。
体验层至少需要表达：
未开始；
运行中；
已完成；
部分完成；
失败；
重试中；
已恢复；
已跳过；
等待用户；
需要确认；
已取消；
被阻塞。
这些状态不一定全部出现在主界面。
展示权重按影响决定：
已完成可以弱展示；
运行中需要可感知；
等待用户必须突出；
失败需要可追溯；
已恢复异常可以轻提示；
原始错误放在深层。
15. 关键反模式
15.1 过程污染结果
把所有工具调用、错误、日志直接堆在结果区。
问题：
用户找不到结果；
对话流变成日志流；
普通用户被吓退。
15.2 完全黑盒
只显示“正在处理”，最后直接给结果。
问题：
长等待不可信；
用户不知道是否还在运行；
出错时无法解释；
结果缺乏证据。
15.3 假透明
展示一些看似过程的信息，但无法继续下钻到真实记录。
问题：
用户无法验证；
高级用户不信任；
过程变成装饰。
15.4 工具名主导叙事
把用户任务拆成一堆 API 名称或工具名称。
问题：
用户无法理解；
任务目标被工具细节淹没；
产品像开发者日志。
15.5 原始日志进入主流
把命令、输出、错误堆栈直接插入主对话流。
问题：
信息密度过高；
阅读路径被打断；
结果和过程混乱。
15.6 完成态太弱
复杂任务完成后只说“完成了”。
问题：
用户不知道完成范围；
不知道结果在哪里；
无法判断是否可验收。
15.7 思考、执行、结果混在一起
把任务理解、工具调用、最终回答混在同一信息流。
问题：
用户不知道哪些是结论；
哪些是过程；
哪些是内部分析；
体验秩序混乱。
16. 体验验收 Checklist
设计一个 Agent Run 对话流时，可以用以下问题检查：
`1. 用户能否第一时间看到最终结果？
2. 过程是否默认折叠，而不是污染结果？
3. 用户是否能展开查看执行过程？
4. 执行过程是否按阶段组织？
5. 节点是否使用任务语言，而不是工具语言？
6. 用户是否能继续下钻到节点详情？
7. 工具、命令、日志是否放在浮层或深层详情中？
8. 错误是否可见，但没有抢占主结果？
9. 完成态是否能帮助用户验收？
10. 交付物是否被当作对象展示？
11. 高风险动作是否前置确认？
12. 思考、执行、结果是否被清晰分离？`
17. 与后续文档的关系
本文是静态体验规范，定义 Agent Run 对话流的基础结构与分层原则。
以下内容不在本文展开，应进入后续文档。
17.1 动态交互与渲染流程规范
应进一步定义：
用户发起任务后信息如何出现；
执行节点如何逐步加载；
状态如何更新；
任务完成后过程如何折叠；
用户如何展开过程；
用户如何从节点继续下钻；
浮层如何打开和返回；
失败、重试、恢复如何动态呈现。
17.2 Demo 与评审页交接文档
应进一步定义：
demo 使用的完整 mock 场景；
mock 用户消息；
mock 结果内容；
mock 执行节点；
mock 工具浮层；
mock 命令输出；
评审页 step-by-step 脚本；
每一步的设计意图和评审关注点。
18. 总结
Agent Run 对话流设计的核心，不是把每个工具调用展示出来，也不是把过程全部隐藏，而是建立一套清晰的信息秩序：
完成后结果优先，过程折叠可查；
想确认的人看过程，想较真的人继续下钻；
主流承载结果和产品化过程，浮层承载工具与原始记录；
任务语言在上，工具细节在下；
最终交付必须可验收。
