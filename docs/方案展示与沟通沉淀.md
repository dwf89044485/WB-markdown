## 一、展示总纲

### 1.1 演示者自我定位

你不是在做"产品演示"，也不是在做"进度汇报"。你是**交互设计方案的设计者，带领团队理解一套新品类（Agent 对话流）的信息秩序**。

你要达成的目标不是"团队说 OK"，而是：
- 设计团队 leader 理解了你的**信息分层逻辑**，能判断后续设计稿是否违背底层规则
- 产品团队理解了**用户在不同阶段的体验目标**，能判断后续需求优先级

### 1.2 一句话锁定全场认知

开场第一句就亮出来：

> "WorkBuddy 的对话流不是聊天界面。
> 用户不是'跟 AI 聊天'，而是**委托一个目标，Agent 理解任务、拆解步骤、调用工具、处理异常、生成结果**。
> 所以这次展示，我们不展示 UI 细节，而是一起看——用户如何感知这个过程、验收结果、追溯细节。"

### 1.3 总纲原则（贴在演示者自己的笔记里）

> **结果优先，过程可查，风险可控，失败可见，细节下钻，交付可验收。**

这条原则贯穿整个展示，每次讲到关键设计时就对照这条查：

| 展示阶段 | 对照哪条 |
|---------|---------|
| 讲 Agent Run 整合结构 | "结果优先" |
| 讲节点塌缩 | "结果优先"、"过程可查" |
| 讲状态行 + 浮层 | "过程可查"、"细节下钻" |
| 讲快照语义 | "过程可查"、"失败可见" |
| 讲完成态 | "交付可验收" |
| 讲错误分层 | "失败可见"、"风险可控" |
| 讲 Sheet 拖拽 | "细节下钻" |

## 二、展示历程分幕脚本

整场展示约 **25-30 分钟**，分 5 幕。每幕有一个**核心目标**、一个**具体演示操作**、一段**关键话术**。

---

### 第一幕：建立认知基线（3 分钟）

**核心目标**：让团队理解"Agent Run ≠ Chat"，统一词汇表。

**你做的事**：口述 + PPT/白板，不操作 Demo。

**关键话术**：

> "先对齐一下几个词的意思，后面才不会误解：
>
> **Agent Run**——从用户发送请求到 Agent 交付结果的完整执行对象。它不是一条"Assistant 消息"，它是一个任务容器。
>
> **节点**——Agent 执行中的一个阶段。本次 Demo 有 3 个节点：节点 1 理解任务+搜索信息，节点 2 生成图片，节点 3 整合输出。
>
> **过程类型**——Agent 做的事的种类。本次 Demo 枚举了 13 种，比如思考、搜索、创建文件、调用技能、委派子 Agent。**关西旅行的故事只是载体，这 13 种过程类型才是我们今天要一起看的东西。**"

**为什么这样开场**：因为「节点」「状态行」「浮层」「快照」在后续会反复出现。如果不在开头统一词汇，后面每个人按自己的理解听，信息损耗大。

---

### 第二幕：自然流程欣赏（5 分钟）

**核心目标**：让团队先看一遍完整的 Agent Run，建立整体感受。

**你做的事**：自动播放，不加讲解干扰。唯一动作：**调到慢速（tokensPerSecond ≈ 80-100）**，让每个动画效果能被看清楚。

**观众看到什么**（按时间线）：

```
用户消息气泡出现
  ↓
Agent 头像 + "WorkBuddy" 名称左侧入场
  ↓
【开始思考】spinner + "正在思考" → 完成 → "思考过程 ›" 按钮出现
  ↓
【节点 1 启动】spinner 旋转 → 内部陆续长出 3 条状态行：
  创建待办 → 搜索网页（多条，有扫光动画）→ 节点内 markdown
  ↓
【节点 1 完成】spinner 变绿钩 → 自动塌缩为一行摘要
  ↓
【节点 2 启动】同上节奏 → 生成图片 → 更新待办
  ↓
【节点 3 启动】同上节奏 → 调用技能 → 创建文件(异常→修复)→ 执行命令 → 委派 Subagent
  ↓
【收尾段】Timing bar "执行过程 10m21s" → 总结 markdown → 表格 → 文件卡片
```

**你唯一需要说的一句话**（在播放过程中轻声带过）：

> "注意看每个节点——它在跑的时候展开，跑完自动塌缩。下一节点头顶的 spinner 才开始转。**它们是串行的，一个接一个。**"

**为什么不做讲解**：第一次看最重要的是从零到一的整体感知。任何中途打断都会破坏节奏——团队还没建立起体验框架就开始听细节，容易迷失。

---

### 第三幕：关键设计拆解（12-15 分钟）

这是整场展示的主体，按顺序拆解 5 个关键设计决策。每个拆解包含：**停止播放 → 操作 Demo → 解释设计决策**。

---

#### 3.1 节点的"活生长、跑完塌缩"（3 分钟）

**演示范例**：回退到节点 1 刚开始的位置，重新自动播放到节点 1 塌缩。这次**放慢速度**，边播边讲。

**话术**：

> "注意这个节奏——节点 1 开始后，内部的子事件是**逐步长出来**的：先是创建待办的状态行出现（有扫光），然后搜索网页的状态行出现……
>
> 这里的关键设计是：**同一时刻最多只有一个节点在 RUNNING**。节点 1 不跑完，节点 2 不会出现。节点 1 跑完的瞬间，自动塌缩为一行摘要。
>
> 这个设计的意图是什么？——**主对话流默认服务结果，过程信息默认收起。**
>
> 但注意：塌缩不等于消失。节点内部的所有状态行都保留在 exec area 里，点「展开」就能看到。这就是"过程可查"。"

**操作要点**：
- 可以回到节点 1 刚开始的位置，利用速度滑块调到慢速，让 team 看到每一个子事件"长出来"的过程
- 可以按暂停，指屏幕上的 spinner 和绿钩给 team 看——"节点头只有这两种状态，永远不会出现'未开始的灰圆'"

---

#### 3.2 状态行 + 浮层的两态切换（3 分钟）

**演示范例**：先播放到节点 1 的搜索阶段，暂停。然后演示：
1. 点一条跑中的状态行（"正在搜索网页 ›"）
2. 快速切回播放，等它完成
3. 再点已完成的同一行

**话术**：

> "状态行是用户下钻唯一个人口。
>
> 跑中时点击，看到的是实时推进——事件逐条出现、待办逐个打勾；完成后点击，看到的是**那一刻的全局快照**——事件条停在那一刻、待办列表也停在那一刻。
>
> 这就是"快照语义"：点已完成状态行，就像时光倒流回它刚完成的那一刻。你看到的是一个定格，不是累积日志。"

**操作要点**：
- 可以先点跑中的状态行，让 team 看到打字机效果和待办打勾
- 然后点已完成的同一行，对比两个浮层的内容差异——尤其是待办状态
- 强调："**浮层 = 事件块 + 待办列表**。事件块是私有的，每个状态行只展示自己生命周期内的；待办列表是全局共享的，7 条待办在所有浮层里实时同步。"

---

#### 3.3 浮层的两层独立 + 快照语义（3 分钟）

这是**体验的核心亮点**，值得用足时间。

**演示序列**（预计 2-3 分钟）：

```
Step 1：自动播放到节点 1 完成
Step 2：点节点 1 的"搜索网页 ›"状态行 → 浮层打开 → 看到待办 ②③④⑤ 已打勾
Step 3：关闭浮层
Step 4：自动播放到节点 2 完成
Step 5：点节点 2 的"更新待办 ›"状态行 → 浮层打开 → 看到待办 ⑥ 已打勾
Step 6：关闭浮层
Step 7：**再回去**点节点 1 的"搜索网页 ›"状态行 → 浮层打开 → **待办列表回到 ②③④⑤ 的状态，⑥ 没有打勾**
```

**话术**（Step 7 时重点说）：

> "注意——节点 2 已经完成了 ⑥，但我回去点节点 1 的"搜索网页"，**⑥ 没有打勾**。为什么？
>
> 因为快照语义要求：点已完成状态行，看到的是**它刚完成那一刻的待办状态**。那一刻节点 2 还没开始，⑥ 当然不应该打勾。
>
> 如果这里出现了"未来的 ✓"，就是 bug，就是我们 5 条铁律之一被违反了。"

**这个演示序列为什么有效**：
- 不需要口述"事件块不累积 + 待办全局共享 + 快照语义"三行抽象定义
- Step 7 的"回去点旧的"是一个**反直觉的操作**，会让团队自己产生"诶，怎么变了"的疑问
- 疑问一旦建立，答案就有了载体

---

#### 3.4 Sheet 交互：拖拽、展开、关闭（2 分钟）

**演示范例**：打开任意一个浮层，手动操作展示。

**操作序列**：
1. 上推 handle → 浮层从 40% 展开到 80%
2. 下拉 handle → 回到 40%
3. 在 40% 状态下继续下拉（>40px）→ 浮层关闭
4. 在 80% 状态下上下滑动内容区域 → 展示原生滚动，不中断

**话术**：

> "Sheet 只支持两档高度：40% 看概要，80% 看细节。不搞自由拖拽，因为移动端自由拖拽手感差——两档吸附更稳定。
>
> 另外注意自动展开：当浮层内容超过 42% 时，它会自动展开到合适高度。这个是每次追加内容后自动判断的，不是一次性的。
>
> 关闭有三条路：拖拽 handle 下去、点遮罩背景、点关闭按钮。"

---

#### 3.5 完成态验收 + 5 条铁律总结（2 分钟）

**演示范例**：自动播放到最后，停在最终态。

**操作**：指最终态的整体结构——总结 → 已完成 → 交付物 → ...

**话术**：

> "收尾段不是一条'完成了'的消息。它是验收界面——帮助用户回答：哪些完成了？结果在哪里？下一步能做什么？
>
> 最后，我把这套方案的 5 条底线过一遍——**这些是任何实现都不能违背的规则**："

**在白板上或者 PPT 上亮出 5 条铁律：**

> 1. 节点头无灰圆（IDLE 不渲染，只有 spinner/绿钩）
> 2. 状态行命名统一（11 行全部遵守"正在 X ›" / "X ›"，无例外）
> 3. 浮层两层独立（事件块不累积 + 待办全局共享）
> 4. 浮层标题 = 状态行同名（10 种标题对应 11 个状态行）
> 5. 快照语义（点已完成状态行 = 时光倒流回那一刻）

---

### 第四幕：差距与下一步（3 分钟）

**核心目标**：管理预期，避免团队误以为"Demo 就是这个产品的全部"。

**你做的事**：口述，不做操作。

**话术**：

> "当前 Demo 覆盖了 13 个过程类型中的**执行类**过程，但有一些**控制类**场景没有覆盖——"
>
> **高优先级缺口（应明确告知团队）**：
> - 等待用户确认：Agent 需要用户允许某种操作时（如发送邮件、创建日历），UI 应该出现确认/修改/拒绝的按钮。当前 Demo 中 Agent 全程自主执行，没有触发这类场景。
> - 部分完成状态：当前 Demo 都是完整完成，没有展示"天气查询失败，用历史参考替代"这种部分完成。
> - 取消/停止任务：当前没有展示用户随时可以叫停的机制。
>
> **中优先级缺口**：
> - 用户补充要求：运行中用户说"等等，预算再调一下"，Agent 如何响应？
> - 重试失败步骤：当前异常走的是自动修复（格式修复），如果用户想手动重试某一步呢？
>
> **这些不是没做，是下一轮重点。**"

---

### 第五幕：开放讨论（5-10 分钟）

**核心目标**：收集反馈，对齐下一步。

**建议引导问题**（如果没人先开口）：

- 对设计团队："5 条铁律你们觉得合理吗？有没有哪条到了具体场景会难实现？"
- 对产品团队："13 个过程类型的覆盖度，你觉得够了还是还缺什么？"
- 对所有人："未覆盖的那几个场景，哪个是你们觉得优先级最高的？"

## 三、演示工具说明（对观众）

**播放控制**（下方的控制面板）是演示者工具，不是设计的一部分：

| 工具 | 用途 | 什么时候用 |
|------|------|-----------|
| 速度滑块 | 调节打字动画速度 | 需要降速展示动画细节时调到 80-100 |
| 上一步 / 下一步 | 回退或前进一个时间节点 | 需要重看某一段时 |
| 重播 | 从头开始 | 整场演示开始时，或讨论中需要再看一遍 |
| 工具调用样式切换 | 边框 / 文字 / 堆叠三档 | 只在讨论信息密度时用到，主线演示不动它 |

**特别说明**：速度滑块改变的是打字动画的节奏（类似于视频播放器的速度），不影响设计本身——你看到的是一个 20tps 慢放版和一个 800tps 加速版的 Agent，不是"两个不同版本的设计"。

## 四、演示者备忘录

### 4.1 演示前检查清单

- [ ] URL 参数已配置（默认自动播放、默认速度在 100-150）
- [ ] 手机预览尺寸正确（393×852）
- [ ] 速度滑块初始位置已确认（不在极端值）
- [ ] 右侧说明区已加载对应步骤的说明
- [ ] 不需要演示的窗口/通知已关闭
- [ ] 投影或屏幕共享已测试（确认字体可读性）

### 4.2 演示中的风险控制

| 场景 | 应对 |
|------|------|
| 自动播放过程中速度太快 | 直接拖动速度滑块到 80-100，无需暂停 |
| 想要回看某个步骤 | 用"上一步"跳回，会全量重建时间线，有 1-2s 延迟，正常 |
| 想在某一步暂停讲解 | 点击"暂停"按钮（自动播放按钮切换为暂停态），讲解完继续 |
| 需要反复对比两个浮层的待办状态 | 打开浮层后保持不关，切换页面去看另一个；或者关掉重开 |
| 观众问到了不在当前视野内的步骤 | 用"跳步"到对应位置，而不是手动一步步走 |
| 演示过程中出现渲染异常 | 按"重播"重新开始；向团队说明"这是临界态，我们正在完善" |

### 4.3 演示后跟进行动

- [ ] 将 5 条铁律发送给设计团队作为设计评审 check criteria
- [ ] 将 13 个过程类型清单发送给产品团队确认覆盖度
- [ ] 收集未覆盖场景的优先级排序
- [ ] 根据需要安排下一轮 Demo（覆盖"等待用户确认"等场景）

## 五、Kimi 的独特视角：体验设计与视觉叙事

> 以下内容由 Kimi-K2.6（多模态模型）从"人类体验设计"和"视觉叙事"角度输出，补充 GLM 和架构师视角未覆盖的部分。

### 5.1 Kimi 视角 V.S. 其他 Agent 视角

| 维度 | GLM / 架构师 | Kimi |
|------|-------------|------|
| 展示目标是 | 让观众"理解/认可"方案 | 让观众"记住/被感染" |
| 展示方式是 | 分幕讲解、逐条举证 | 策展式体验、形式即论点 |
| 情感处理 | 用逻辑说服（5 条铁律、13 个类型） | 用节奏感染（情感曲线、callback） |
| 对 Demo 的定位 | 设计方案的验证工具 | 设计哲学的表演载体 |

### 5.2 会议作为一场"体验"来设计

Kimi 认为：你不是在做 PPT presenter，而是做**策展人（curator）**。

**核心原则：让观众"感受到"设计，而不是"听懂"设计。**

关键技巧——**"座位即立场"**：
- 进场时让观众选座：左边坐"相信 AI 能替代人类"的，右边坐"认为 AI 只是工具"的
- Demo 中设计一个争议性节点（比如 Agent 主动拒绝了一个越界的请求）
- 让观众按座席举手表决——**会议本身变成一次用户研究**
- 这不是花哨的暖场，而是让观众在 Demo 结束后自然地意识到："原来我对 AI 的信任感是被信息分层塑造出来的"

### 5.3 "演示中的演示"技巧（形式即论点）

**技巧 A：先展示"症状"，再展示"解药"**

不是直接播放 WorkBuddy 的优雅流程，而是：
1. 先放一段竞品录屏（或早期粗糙原型），故意不调速——让观众感受到**信息过载的烦躁**
2. 然后以**同样的任务**展示 WorkBuddy 渐进式披露的处理方式
3. 关键：两次演示的任务难度完全一致，但体验天壤之别

> 观众不会记得你说了什么，但会记得**那个从混乱到清爽的解脱感**

**技巧 B：用"慢动作"制造洞察**

- 在 Agent 执行关键步骤时，**故意放慢到 0.5 倍速**
- 不是为了看清楚，而是为了**暴露人类自己在同样场景下的笨拙**
- 比如 Agent 在 3 秒内完成了"读取邮件→提取优先级→写回复草稿"，然后 freeze-frame 问观众："你们做这件事要多久？"

**技巧 C："故障美学"——信任建立的关键**

- 在展示异常处理时，**不要跳过错误**
- 故意展示 Agent 说"我不太确定，让我再想想..."的时刻
- 这不是 Bug，这是**信任建立的关节点**——观众看到 AI 也会犹豫，反而觉得真实可信

### 5.4 Agent 对话流的"情感曲线"

Kimi 定义了 Demo 中的情感节奏（不是配乐，而是信息结构的韵律）：

```
紧张 ────────┐
    ↑        │
等待确认中   │
    │        ↓
释放 ←───────┘
    ↑
    │    好奇 ────────┐
    │        ↑        │
    └────────┘   新信息出现
             │        ↓
             └───────→ 确认（"原来如此"）
```

**具体节点映射到 Demo 中：**

| Demo 节点 | 情感目标 | Kimi 建议的手法 |
|-----------|---------|----------------|
| 用户下达复杂指令 | **紧张** | 镜头停在输入框，光标闪烁 3 秒——让观众也屏住呼吸 |
| Agent 开始思考（thinking 动画） | **等待的焦虑** | 不跳过，让动画完整播完——焦虑累积后才能释放 |
| Agent 第一条回复出现 | **释放** | 用 typewriter 效果逐字打出，不是瞬间弹出——让观众"读到"解脱 |
| Agent 展示中间步骤（工具调用） | **好奇** | 用卡片展开动画，每一步像翻牌——"接下来会是什么？" |
| 最终结果+待办清单 | **确认** | 清单逐项打勾，最后来一句温暖的总结 |
| Agent 主动停下来询问用户 | **权力让渡** | "我找到了 3 个方案……你要哪个？"——从被动观看变主动掌控 |

### 5.5 视觉叙事结构：Demo 与 TED 演讲的对应

映射到你的 Demo 流程：

| TED 结构 | Demo 对应 | 具体做法 |
|----------|-----------|---------|
| **Hook（钩子）** | 开场悬念 | 不是"大家好今天展示 WorkBuddy"，而是直接放一个问题："你每天早上花 47 分钟处理邮件，其中 32 分钟是低价值重复劳动。如果这 32 分钟还给你，你会做什么？" |
| **Problem（问题）** | 痛点共鸣 | 用第一人称视角录一段真实使用场景（带环境音：地铁噪音、打字声、叹气声），让观众**代入那个焦虑的使用者** |
| **Insight（洞察）** | 设计理念揭示 | 不讲技术架构，讲一条原则——"AI 不应该是一个回答问题的搜索引擎，而是一个**会主动说'这个我来处理'的同事**" |
| **Climax（高潮）** | Agent 的"高光时刻" | 选最复杂的任务链，一镜到底完成，制造"哇"的时刻 |
| **Call to Action（号召）** | 开放结尾 | 不说"请提意见"，而是说"**你们中的一个痛点，可能就是下一个版本的 killer feature**"—把观众变成共创者 |

### 5.6 Kimi 的终极技巧：叙事闭合——"Callback"

- 开场时提到一个具体细节（比如"那个每天早上 8:47 的邮件噩梦"）
- 在 Demo 高潮处，Agent 完成了一项任务，时间戳正好是 **8:47**
- 观众会在潜意识里产生**叙事闭合的满足感**
- 这是他们**说不清为什么觉得这场 Demo 很'完整'**的原因

### 5.7 Kimi 的总结

> GLM 和 DeepSeek 告诉你怎么让 Demo"正确"，Kimi 想告诉你怎么让 Demo **难忘**：
> 1. 让观众先成为用户，再成为评审
> 2. 形式本身就是论点——你怎么演示，就是在演示你的设计哲学
> 3. 情感节奏不是装饰，是信息的组织方式
> 4. 好 Demo 不是说服，是感染——让观众结束后还在想"那个 8:47 的邮件"
