# Agent 对话流体验哲学：总原则与设计指南 ## 0. 总纲 Agent 对话流不是普通聊天界面。 普通 Chatbot 的体验核心是： > 用户提问，AI 回答。 Agent 产品的体验核心是： > 用户委托一个目标，Agent 理解任务、拆解任务、调用工具、处理异常、生成结果，并在必要时让用户确认、追溯或接管。 因此，Agent 对话流设计的本质不是“如何展示一段回复”，而是： > **如何让用户在一个复杂、异步、可能失败、可能调用外部工具的执行过程中，始终知道结果是什么、过程是否可信、风险是否可控、自己是否仍然掌握主动权。** 一句话总原则： > **结果优先，过程可查，风险可控，失败可见，细节下钻，交付可验收。** --- ## 1. Agent 是执行系统，不是聊天机器人 Agent 类产品的核心不是“生成文本”，而是“完成任务”。 它可能会： * 理解目标； * 拆分步骤； * 联网搜索； * 读取文件； * 写入文件； * 生成图片； * 生成文档； * 创建草稿； * 调用工具； * 委派子任务； * 发生错误； * 自动修复； * 重试； * 等待用户确认； * 产出可操作结果。 所以对话流 UI 不能只围绕“消息气泡”设计，而要围绕“任务执行”设计。 ### 设计含义 对话流里至少有三类信息： 1. **结果信息**：用户真正要的答案、文件、方案、图表、草稿、总结。 2. **过程信息**：Agent 为了得到结果做了什么。 3. **控制信息**：哪些事情需要用户确认、修改、授权或接管。 好的 Agent 对话流，必须同时处理这三类信息，但不能让它们互相污染。 --- ## 2. 结果优先，而不是过程优先 绝大多数用户最关心的是结果，而不是 Agent 调用了哪些工具。 用户真正关心的是： * 方案是什么？ * 文件在哪里？ * 天气结论是什么？ * 路线怎么走？ * 预算够不够？ * 哪些事情完成了？ * 哪些事情失败了？ * 我接下来要做什么？ 用户通常不关心： * 哪个工具先调用； * API 参数是什么； * 中间日志是什么； * 内部如何修复 Unicode 错误； * Agent 每一步原始想法是什么。 这些过程信息有价值，但它们不是默认主角。 ### 原则 > **主对话流默认服务结果，过程信息默认收起。** ### 设计指南 默认视图应该优先展示： * 任务完成状态； * 最终总结； * 关键结论； * 交付物； * 下一步操作； * 需要用户确认的事项。 不应该默认展示： * 全量工具日志； * 原始命令执行过程； * 原始模型思考； * 详细工具参数； * 内部修复细节； * debug trace。 --- ## 3. 过程透明，但不能喧宾夺主 Agent 的过程必须透明，因为过程影响信任。 用户需要知道： * Agent 是否真的执行了任务； * 是否查过相关信息； * 是否遇到失败； * 是否做过重试； * 是否绕开了某些限制； * 是否有东西没有完成。 但透明不等于把全部过程默认暴露出来。 ### 核心原则 > **透明不是默认裸露，而是需要时可追溯。** 也就是说： * 普通用户默认看结果； * 关心过程的用户可以展开任务概览； * 想看细节的用户可以展开节点； * 特别较真的用户可以进入原始执行记录； * 想看模型理解的人可以查看别较真的用户可以进入原始执行记录； * 想看模型理解的人可以查看原始思考。 这就是渐进式披露。 --- ## 4. 渐进式披露是 Agent 对话流的基础结构 复杂 Agent 对话流不能用单层信息流承载。 单层信息流会导致两个极端： 1. **黑盒**：用户只看到结果，不知道过程是否可靠。 2. **日志流**：用户看到大量过程，找不到结果。 正确方式是分层。 推荐的基础结构是四层： 
txt
L0 结果层
L1 任务概览层
L2 节点摘要层
L3 原始追溯层
### L0：结果层 面向大多数用户。 回答： * 完成了吗？ * 结果是什么？ * 文件在哪里？ * 下一步是什么？ ### L1：任务概览层 面向想确认过程的用户。 回答： * Agent 大致做了哪些阶段？ * 哪些步骤完成了？ * 是否有异常？ * 是否可以进一步查看？ ### L2：节点摘要层 面向想看某一步的人。 回答： * 这个阶段具体做了什么？ * 对最终结果有什么贡献？ * 是否发生过失败或修复？ * 是否可以继续下钻？ ### L3：原始追溯层 面向较真用户、高级用户、debug 用户。 回答： * Agent 实际调用了什么？ * 出了什么错？ * 怎么修复？ * 原始思考是什么？ * 原始执行记录是什么？ ### 原则 > **越靠上越产品化，越靠下越原始化。** --- ## 5. 用户关注结果，过程服务信任 过程信息的作用不是替代结果，而是支撑结果可信。 例如，用户要的是天气、路线、预算和旅行方案。 这些内容应该出现在结果里，而不是藏在过程里。 过程层只需要说明： * 查询了天气； * 查询了路线； * 做了预算换算； * 生成了文件； * 遇到错误并恢复； * 某些信息使用了替代来源。 ### 设计判断 天气趋势、路线建议、预算换算结果： > 放在结果层。 查询天气、查询路线、预算换算这些动作： > 放在过程层。 天气 API 超时、网页 404、文件写入失败： > 放在原始追溯层，必要时在节点摘要层轻量提示。 ### 原则 > **用户任务结果归结果区，执行证据归过程区。** --- ## 6. 工具是实现手段，不是用户叙事的主角 Agent 产品会调用很多工具，但用户不一定关心工具本身。 用户说的是： > 帮我规划一次关西家庭旅行。 不是： > 请你依次调用 web_search、weather_api、currency_api、file_writer。 所以 UI 不应该把工具名当成主叙事。 ### 好的任务节点 
txt
理解任务与约束
补充搜索旅行信息
生成地点图片
整合信息并输出方案
### 不好的任务节点 
txt
web_search
tool_call_1
run_command
file_write
工具调用可以存在，但应该作为下钻信息，而不是默认主线。 ### 原则 > **对上用任务语言，对下保留工具细节。** --- ## 7. 等待体验的核心是“感知还在推进” Agent 任务经常不是瞬间完成。 用户可以等待，但不能不知道发生了什么。 等待时用户最需要感知： * Agent 是否还在运行； * 当前做到了哪一步； * 是否卡住； * 是否出错； * 是否正在修复； * 是否需要用户确认； * 是否已经部分完成。 ### 不好的表达 
txt
Thinking...
txt
请稍候...
txt
正在处理...
这些表达太空，无法支撑长任务。 ### 更好的表达 
txt
正在查询交通与天气 · 第 2/5 步 · 已用 03m12s
txt
正在生成旅行手册 · 已完成 3 个步骤，1 个步骤运行中
txt
文件生成遇到错误，正在自动修复
### 原则 > **等待越久，状态越要具体；任务越复杂，过程越要有秩序感。** --- ## 8. 错误、重试、修复是 Agent 过程的一部分 Agent 执行复杂任务时一定会失败。 可能失败的地方包括： * 搜索失败； * 网页打不开； * 文件不存在； * 没有权限； * 格式错误； * 代码执行失败； * 工具超时； * 文件生成失败； * 输出格式错误； * 自动修复失败。 这些错误不应该被完全隐藏。 否则用户无法理解： * 为什么任务耗时很长； * 为什么结果部分缺失； * 为什么 Agent 做了某些替代； * 任务是否真的可靠。 ### 但错误也不应该污染主结果 错误展示应该分层： 
txt
L0：只展示是否影响结果
L1：展示哪个阶段有异常
L2：展示异常是否已恢复
L3：展示原始错误和修复过程
### 示例 L0： 
txt
旅行方案已生成。
L1： 
txt
生成旅行方案文档 · 已完成
L2： 
txt
生成过程中遇到编码问题，已自动修复，最终文档已生成。
L3： 
txt
Unicode escape error
使用 Python 修复文本编码
重新生成文档成功
### 原则 > **错误不隐藏，但分层展示；失败不美化，但不抢占结果。** --- ## 9. 原始透明性比“过度包装”更重要，但要放在正确层级 有些产品会把所有过程都包装成用户友好的表达。 这会带来问题： * 开发成本高； * 各类错误都要做映射； * 原始过程被遮蔽； * 高级用户无法追溯真实原因； * 透明性下降。 更合理的策略是： > **浅层产品化，深层原始化。** 也就是： * L0：产品化结果； * L1：产品化任务阶段； * L2：产品化节点摘要； * L3：保留原始过程和原始思考。 这允许产品同时服务两类用户： * 普通用户：只看结果和摘要； * 较真用户：可以看到真实过程。 ### 原则 > **不要为了“看起来友好”而抹掉真实过程。** --- ## 10. 原始思考可以存在，但必须和结果、执行过程分开 模型原始思考不是结果，也不是工具执行。 它是一类独立信息。 它可能包含： * 任务理解； * 约束识别； * 决策依据； * 内部分析； * 中英文混合； * 未整理推理。 如果产品选择展示它，就应该明确标识其原始性。 ### 推荐命名 
txt
原始思考
模型思考记录
查看原始思考过程
### 不推荐 把原始思考伪装成用户友好的解释。 如果没有额外处理成本，不必强行总结原始思考。 但必须默认隐藏，并且和执行过程分开。 ### 原则 > **思考是理解过程，执行是行动过程，结果是交付内容。三者不能混在一起。** --- ## 11. Agent 对话流要支持不同深度的用户 不是所有用户都一样。 至少有三类用户： ### 1. 结果型用户 只关心： * 完成了吗？ * 结果是什么？ * 能不能用？ 他们只需要 L0。 ### 2. 审核型用户 关心： * Agent 有没有认真做； * 是否查了该查的信息； * 有无失败； * 结果是否可信。 他们需要 L1 和 L2。 ### 3. 较真型用户 / 高级用户 关心： * 原始过程； * 具体工具； * 错误细节； * 修复方式； * 模型思考。 他们需要 L3。 ### 原则 > **同一个对话流，要同时服务“只看结果的人”和“要查到底的人”。** 这正是渐进式披露的价值。 --- ## 12. 风险越高，控制权越要前置 不是所有 Agent 行为都需要用户控制。 如果 Agent 只是搜索信息、生成文档、总结内容，用户可以事后查看。 但如果 Agent 要执行真实外部动作，就必须给用户控制权。 高风险动作包括： * 发送邮件； * 创建日历邀请； * 删除文件； * 覆盖文件； * 付款； * 下单； * 预订； * 发布内容； * 访问敏感文件； * 修改第三方系统数据。 ### 原则 > **信息型任务可以结果优先；行动型任务必须确认优先。** 对于高风险动作，必须明确： * 即将做什么； * 影响范围是什么； * 是否可撤销； * 是否只是草稿； * 用户有哪些选择。 --- ## 13. 用户控制权应按场景出现，而不是常驻堆满 Agent 产品不应该把所有控制按钮一直放在界面上。 这会制造压力，也会增加复杂度。 控制应该按状态出现。 ### 运行中 可以提供： * 停止； * 暂停； * 补充要求； * 查看过程。 ### 失败时 可以提供： * 重试； * 跳过； * 手动补充； * 查看原因。 ### 需要确认时 必须提供： * 允许； * 先预览； * 修改； * 拒绝。 ### 完成后 可以提供： * 预览； * 下载； * 继续修改； * 分享； * 生成新版本。 ### 原则 > **控制权不是按钮数量，而是在正确时刻给用户正确选择。** --- ## 14. 完成态不是结束语，而是验收界面 复杂 Agent 任务完成后，不应该只输出一句： 
txt
完成了。
完成态应该帮助用户验收。 它应该回答： * 哪些完成了？ * 哪些部分完成？ * 哪些失败？ * 哪些需要确认？ * 结果在哪里？ * 下一步可以做什么？ ### 推荐完成态结构 
txt
总结

已完成：
- 生成 7 天旅行方案
- 完成预算拆分
- 生成旅行手册

部分完成：
- 天气使用历史气候参考，无法获得远期精确天气

失败或受限：
- 某网页无法访问，已使用替代搜索

需要确认：
- 是否创建日历草稿

交付物：
- 日本关西家庭旅行方案 v1.0
- 预算表
- 邮件草稿
### 原则 > **Agent 的完成态应该像任务验收，而不是普通回复结尾。** --- ## 15. 交付物要有明确身份 Agent 产出的东西往往不是单纯文本，而是交付物。 例如： * 文档； * 表格； * 图表； * 图片； * HTML； * PDF； * 日历草稿； * 邮件草稿； * 待办清单； * 代码 patch； * 数据文件。 交付物应该让用户明确知道： * 它是什么； * 是否已生成； * 是否可预览； * 是否可下载； * 是否可继续修改； * 是否是最新版本。 ### 原则 > **把 Agent 的产物当作对象，而不是当作一句文本链接。** --- ## 16. 状态体系要真实表达复杂性 Agent 过程不是只有“完成”和“失败”。 至少应该考虑这些状态： * 未开始； * 运行中； * 已完成； * 部分完成； * 失败； * 超时； * 重试中； * 已跳过； * 等待用户； * 权限不足； * 需要确认； * 已取消； * 已恢复。 但这些状态不一定都在主界面展开。 ### 设计原则 > **状态体系要完整，展示权重按影响决定。** 例如： * 已完成可以弱展示； * 运行中需要可感知； * 失败需要可追溯； * 等待用户必须突出； * 原始错误放深层； * 已恢复的错误可以在节点摘要中轻量提示。 --- ## 17. 信息密度要由用户意图驱动 Agent 对话流最容易出现信息过载。 所以每一层都要有明确的信息密度策略。 ### L0 结果层 低密度。 只放结果、交付物、关键总结。 ### L1 任务概览层 中低密度。 只放阶段和状态。 ### L2 节点摘要层 中密度。 放阶段说明、产出、异常摘要。 ### L3 原始追溯层 高密度。 可以放原始日志、错误、工具细节、思考记录。 ### 原则 > **不是所有信息都要变少，而是不同层级承载不同密度。** --- ## 18. 公开透明不是把所有东西放到台面上 Agent 产品需要公开透明，但“公开透明”不等于“默认全部展示”。 更准确的定义是： > 用户有需要时，能够追溯到足够真实的信息。 所以透明性的核心不是默认展示量，而是： * 是否能找到； * 是否够真实； * 是否够完整； * 是否不被过度改写； * 是否能解释结果来源。 ### 原则 > **透明是一种可追溯能力，不是一种默认展示策略。** --- ## 19. 1. 文档目的

本文定义 Agent 执行型对话流的基础体验规范，用于指导产品设计、交互设计、Demo 制作和团队评审。

本规范关注：

  • Agent 任务执行后的信息如何组织；

  • 结果、过程、控制信息如何分离；

  • 执行过程如何分层追溯；

  • 哪些信息应该进入主对话流；

  • 哪些信息应该折叠、展开或进入浮层；

  • 如何避免对话流变成黑盒或日志流。

本文不定义：

  • 后端字段；

  • LLM 执行协议；

  • 工具调用 schema；

  • 真实数据结构；

  • 生产级组件实现；

  • 完整 mock 数据。

mock 数据仅在必要时作为最小示例出现，完整 demo 数据应放入独立的 Demo / 评审页交接文档。

2. 核心判断

Agent 对话流不是普通聊天回复，而是一次任务执行后的结果交付与过程追溯。

普通 Chatbot 的体验核心是：

用户提问，AI 回答。

Agent 对话流的体验核心是：

用户委托一个目标，Agent 理解任务、拆解任务、执行任务、处理异常、生成结果，并在必要时让用户确认、追溯或接管。

因此，Agent 对话流的设计重点不是“如何展示一段回复”，而是：

如何让用户在复杂、异步、可能失败、可能调用工具的执行过程中，始终知道结果是什么、过程是否可信、风险是否可控、自己是否仍然掌握主动权。

一句话原则：

结果优先，过程可查，风险可控，失败可见，细节下钻，交付可验收。

3. 核心对象：Agent Run

一次用户委托触发一次完整执行，这个执行对象称为：

Agent Run

Agent Run 不是单条 Assistant 消息，也不是一组工具日志，而是一个完整任务容器。

一个 Agent Run 通常包含：

  • 用户目标；

  • 任务理解；

  • 执行计划；

  • 执行过程；

  • 执行节点；

  • 节点内事件；

  • 工具 / 技能 / 文件操作；

  • 异常 / 重试 / 恢复；

  • 最终结果；

  • 交付物；

  • 过程追溯入口。

设计时应把 Agent Run 视为一个整体对象，而不是把过程和结果拆成互不关联的多条消息。

4. 两个阶段

Agent Run 在体验上分为两个主要阶段。

4.1 执行过程态

执行过程态发生在用户发起任务之后、最终结果生成之前。

这一阶段的目标是：

让用户感知 Agent 仍在推进，并在必要时可以确认、补充、暂停或接管。

执行过程态需要表达：

  • 当前任务是否已经开始；

  • Agent 正在做什么；

  • 当前处于哪个阶段；

  • 是否还在推进；

  • 是否遇到异常；

  • 是否正在重试或恢复；

  • 是否需要用户确认；

  • 是否已有部分结果。

执行过程态不应该只显示：

Thinking...

或：

正在处理...

长任务中，状态表达必须更具体。

推荐表达方式：

正在整理旅行方案 · 已完成 3/5 个阶段 · 已用 12m30s

4.2 结果交付态

结果交付态发生在任务执行完成之后。

这一阶段的目标是：

干净地呈现结果，让用户可以验收，同时保留过程追溯能力。

任务完成后，主对话流的主角应该从“执行过程”切换为“最终结果”。

默认展示：

  • 总结；

  • 最终结论；

  • 交付物；

  • 结果正文；

  • 已完成 / 部分完成 / 失败或受限；

  • 需要用户确认的事项；

  • 下一步操作。

默认折叠：

  • 执行节点；

  • 工具调用；

  • 命令执行；

  • 文件操作；

  • 错误修复过程；

  • 原始日志；

  • 原始思考。

核心规则：

运行中，过程在前；完成后，结果在前，过程折叠为可追溯入口。

5. 三类信息

Agent 对话流中至少包含三类信息。

5.1 结果信息

结果信息是用户真正要的内容。

例如：

  • 答案；

  • 方案；

  • 总结；

  • 文档；

  • 表格；

  • 图片；

  • 图表；

  • 草稿；

  • 文件；

  • 待办清单。

结果信息应该出现在结果区，而不是藏在过程区。

5.2 过程信息

过程信息说明 Agent 为了得到结果做了什么。

例如：

  • 理解了任务；

  • 拆解了步骤；

  • 搜索了信息；

  • 读取了文件；

  • 生成了图片；

  • 创建了文档；

  • 遇到异常并恢复；

  • 使用了替代方案。

过程信息用于建立信任，但不应默认污染结果呈现。

5.3 控制信息

控制信息说明哪些事情需要用户确认、修改、授权或接管。

例如：

  • 是否继续执行；

  • 是否允许发送邮件；

  • 是否覆盖文件；

  • 是否采用某个方案；

  • 是否重试失败步骤；

  • 是否跳过某个节点。

控制信息应在需要用户行动时突出展示，而不是长期堆在界面中。

6. 六级信息层级

Agent Run 的信息应按层级组织，支持渐进式披露。

推荐六级结构：

L0 结果呈现层
L1 执行过程总览层
L2 节点摘要层
L3 节点内事件层
L4 工具 / 技能详情层
L5 原始命令 / 原始输出层

6.1 L0：结果呈现层

L0 是任务完成后的默认视图。

面向用户：

  • 结果型用户；

  • 只关心任务是否完成、结果是否可用的人。

回答：

  • 完成了吗？

  • 结果是什么？

  • 交付物在哪里？

  • 有没有失败或限制？

  • 下一步可以做什么？

应该展示：

  • 总结；

  • 关键结论；

  • 交付物入口；

  • 结果正文；

  • 重要限制；

  • 下一步操作。

不应该展示：

  • 工具调用；

  • 命令行；

  • 原始日志；

  • 原始思考；

  • 调试信息；

  • 详细修复过程。

最小示例：

所有任务已完成。以下是为你生成的完整旅行方案文档：
查看旅行方案 v1.0

6.2 L1：执行过程总览层

L1 是用户点击“执行过程”后看到的过程概览。

面向用户：

  • 审核型用户；

  • 想确认 Agent 是否真的做过任务的人。

回答：

  • Agent 大致做了哪些阶段？

  • 哪些阶段完成了？

  • 是否有异常？

  • 是否可以继续展开？

应该展示：

  • 执行过程入口；

  • 总耗时；

  • 阶段节点列表；

  • 每个阶段的状态；

  • 可展开入口。

不应该展示：

  • 完整工具参数；

  • 原始命令输出；

  • 大段日志；

  • debug trace。

最小示例：

执行过程 · 19m40s

✓ 任务理解与分解
✓ 补充搜索旅行信息
✓ 生成地点图片
✓ 整合信息并输出文档

说明：

“执行过程”入口比“任务耗时”更清晰，因为用户点击后查看的不只是耗时，而是完整过程。

6.3 L2：节点摘要层

L2 是用户展开某个阶段节点后看到的内容。

面向用户：

  • 审核型用户；

  • 想确认某一步具体做了什么的人。

回答：

  • 这个阶段做了什么？

  • 识别了哪些重点？

  • 产生了什么阶段产出？

  • 是否有异常或恢复？

  • 是否可以继续下钻？

应该展示：

  • 节点标题；

  • 节点目标；

  • 关键判断；

  • 约束识别；

  • 子任务拆分；

  • 阶段产出；

  • 异常摘要。

不应该展示：

  • 全量命令；

  • 原始工具输出；

  • 未整理的模型思考；

  • 大段英文 debug 文本。

最小示例：

任务理解与分解

目标：
为一家四口规划日本关西 7 日旅行方案。

关键约束：
- 需要控制预算
- 需要考虑家庭友好性
- 行程不宜过度紧张

阶段产出：
已将任务拆分为交通、住宿、景点、预算、交付文档五个方向。

6.4 L3：节点内事件层

L3 是复杂节点内部的事件流。

面向用户：

  • 深度审核用户；

  • 想知道某个节点内部发生了哪些动作的人。

回答：

  • 这个节点内部有哪些动作？

  • 是否调用了技能？

  • 是否创建或编辑了文件？

  • 是否执行了命令？

  • 是否发生错误或修复？

  • 哪些动作可以继续查看详情？

应该展示：

  • 事件摘要；

  • 动作类型；

  • 简短状态；

  • 可下钻入口。

不应该默认展示：

  • 完整命令；

  • 完整输出；

  • 文件完整内容；

  • 原始错误堆栈；

  • 长篇工具说明。

最小示例：

整合信息并输出文档

已调用文档技能 >
已创建文件 >
已读取并编辑文件 >
已检查并修复格式问题 >

说明：

L3 可以出现“调用技能”“创建文件”“执行命令”等事件语言，但仍应保持摘要化，不直接变成日志流。

6.5 L4：工具 / 技能详情层

L4 用于展示工具、技能、文件操作等更细的信息。

承载方式通常不应继续占用主对话流，而应进入浮层或详情面板。

面向用户：

  • 高级用户；

  • 需要确认工具使用情况的人；

  • 设计评审或调试人员。

回答：

  • 调用了什么工具 / 技能？

  • 这个工具用于什么？

  • 执行了哪些动作？

  • 是否可以继续查看原始命令？

应该展示：

  • 工具 / 技能名称；

  • 简短用途；

  • 动作摘要；

  • 相关事件；

  • 进一步下钻入口。

不应该展示：

  • 过长技能说明；

  • 全量工具文档；

  • 大段原始日志。

最小示例：

调用技能：docx
用途：创建和编辑 Word 文档

相关动作：
- 检查文档能力
- 创建旅行方案文档
- 编辑文档内容

6.6 L5：原始命令 / 原始输出层

L5 是最深层追溯信息。

承载方式应使用浮层、二级详情页或日志面板。

面向用户：

  • 较真用户；

  • 高级用户；

  • debug 用户；

  • 内部评审人员。

回答：

  • 实际执行了什么命令？

  • 原始输出是什么？

  • 原始错误是什么？

  • 文件路径是什么？

  • 环境信息是什么？

应该展示：

  • 命令；

  • 输出；

  • 错误原文；

  • 路径；

  • 原始记录。

不应该默认展示在主对话流里。

最小示例：

命令：
which node && node -v

输出：
/root/.nvm/versions/node/...
v22.22.2

说明：

L5 是可验证层，不是普通用户的默认阅读层。

7. 承载介质

不同层级的信息应由不同 UI 介质承载。

7.1 主对话流

主对话流承载：

  • L0 结果呈现；

  • L1 执行过程总览入口；

  • 部分 L2 节点摘要。

主对话流的目标是保持任务上下文清晰。

主对话流不应承载：

  • 全量工具日志；

  • 完整命令输出；

  • 大段错误堆栈；

  • 复杂 debug 信息。

7.2 对话内展开

对话内展开承载：

  • L1 执行过程总览；

  • L2 节点详情；

  • L3 事件摘要。

对话内展开适合展示产品化过程信息。

它应该让用户确认 Agent 确实执行了任务，但不应把界面变成开发日志。

7.3 浮层下钻

浮层下钻承载：

  • L4 工具 / 技能详情；

  • L5 原始命令 / 原始输出。

当信息颗粒度进入工具、命令、日志、路径、原始输出时，应优先使用浮层或详情页，而不是继续撑开主对话流。

核心规则：

主流承载结果与产品化过程，浮层承载高密度追溯信息。

8. 任务语言与工具语言

Agent 对话流应区分任务语言和工具语言。

8.1 上层使用任务语言

L0-L2 应优先使用用户能理解的任务语言。

推荐：

补充搜索旅行信息
生成地点图片
整合信息并输出文档

不推荐：

web_search
tool_call_1
run_command
file_write

8.2 深层保留工具语言

L4-L5 可以保留真实工具名、命令和输出。

因为用户已经主动进入深层追溯，此时真实信息比包装表达更重要。

规则：

对上用任务语言，对下保留工具细节。

9. 思考、执行、结果分离

Agent 对话流中需要区分三类内容：

思考 / 理解
执行 / 行动
结果 / 交付

9.1 任务理解可以展示

可以展示：

  • 用户目标；

  • 关键约束；

  • 任务拆解；

  • 执行计划；

  • 关键决策摘要。

示例：

任务理解：
用户希望生成一份家庭旅行方案，需要考虑预算、老人行动便利性和亲子友好性。

9.2 原始思考默认不展示

原始思考不应直接混入结果区或过程区。

如果产品需要提供“原始思考”入口，应作为深层追溯内容，并与工具执行记录、最终结果严格分离。

9.3 执行记录不等于结果

工具调用、文件操作、命令执行属于执行记录。

它们用于证明过程可信，但不应替代最终结果。

10. 完成态规范

完成态不是普通结束语，而是任务验收界面。

完成态应帮助用户确认：

  • 哪些已完成；

  • 哪些部分完成；

  • 哪些失败或受限；

  • 是否需要用户确认；

  • 结果在哪里；

  • 下一步可以做什么。

推荐结构：

总结

已完成：
- ...

部分完成：
- ...

失败或受限：
- ...

需要确认：
- ...

交付物：
- ...

下一步：
- ...

简单任务可以压缩，不必机械展示所有分区。

复杂任务应优先使用完整完成态结构。

11. 交付物规范

Agent 产出的文件、图片、表格、草稿、报告等应视为交付物对象，而不是普通文本链接。

交付物应表达：

  • 它是什么；

  • 是否已生成；

  • 是否可查看；

  • 是否可下载；

  • 是否可继续修改；

  • 是否是最新版本。

最小示例：

查看旅行方案 v1.0

更完整的交付物卡片可以包含：

名称：日本关西家庭旅行方案 v1.0
类型：文档
状态：已生成
操作：查看 / 下载 / 继续修改

12. 错误与恢复的展示原则

Agent 执行复杂任务时可能失败、重试或自动修复。

错误不应完全隐藏，但也不应污染主结果。

推荐分层：

L0：只说明是否影响结果
L1：说明哪个阶段有异常
L2：说明异常是否已恢复
L3：展示事件级修复摘要
L4-L5：展示原始错误和输出

示例：

L0：
旅行方案已生成。

L1：
生成文档阶段曾遇到异常，已恢复。

L2：
生成过程中出现格式问题，已自动修复。

L5：
展示原始错误、命令和输出。

原则：

错误不隐藏，但分层展示；失败不美化，但不抢占结果。

13. 用户控制权原则

不是所有 Agent 行为都需要用户提前确认。

信息型任务可以结果优先：

  • 搜索；

  • 总结；

  • 生成文档；

  • 提取信息；

  • 生成草稿。

行动型任务必须确认优先：

  • 发送邮件；

  • 删除文件；

  • 覆盖文件；

  • 创建日历邀请；

  • 下单；

  • 支付；

  • 发布内容；

  • 修改第三方系统数据。

控制权应在正确场景出现，而不是常驻堆满。

运行中可以提供：

  • 停止；

  • 补充要求；

  • 查看过程。

失败时可以提供：

  • 重试；

  • 跳过；

  • 手动补充；

  • 查看原因。

需要确认时必须提供：

  • 允许；

  • 预览；

  • 修改；

  • 拒绝。

完成后可以提供：

  • 查看；

  • 下载；

  • 继续修改；

  • 生成新版本。

14. 状态表达原则

Agent Run 的状态不应只有“完成”和“失败”。

体验层至少需要表达：

  • 未开始；

  • 运行中；

  • 已完成；

  • 部分完成；

  • 失败；

  • 重试中；

  • 已恢复；

  • 已跳过；

  • 等待用户；

  • 需要确认；

  • 已取消；

  • 被阻塞。

这些状态不一定全部出现在主界面。

展示权重按影响决定：

  • 已完成可以弱展示；

  • 运行中需要可感知；

  • 等待用户必须突出；

  • 失败需要可追溯；

  • 已恢复异常可以轻提示；

  • 原始错误放在深层。

15. 关键反模式

15.1 过程污染结果

把所有工具调用、错误、日志直接堆在结果区。

问题：

  • 用户找不到结果；

  • 对话流变成日志流；

  • 普通用户被吓退。

15.2 完全黑盒

只显示“正在处理”，最后直接给结果。

问题：

  • 长等待不可信；

  • 用户不知道是否还在运行；

  • 出错时无法解释；

  • 结果缺乏证据。

15.3 假透明

展示一些看似过程的信息，但无法继续下钻到真实记录。

问题：

  • 用户无法验证；

  • 高级用户不信任；

  • 过程变成装饰。

15.4 工具名主导叙事

把用户任务拆成一堆 API 名称或工具名称。

问题：

  • 用户无法理解；

  • 任务目标被工具细节淹没；

  • 产品像开发者日志。

15.5 原始日志进入主流

把命令、输出、错误堆栈直接插入主对话流。

问题：

  • 信息密度过高；

  • 阅读路径被打断；

  • 结果和过程混乱。

15.6 完成态太弱

复杂任务完成后只说“完成了”。

问题：

  • 用户不知道完成范围；

  • 不知道结果在哪里；

  • 无法判断是否可验收。

15.7 思考、执行、结果混在一起

把任务理解、工具调用、最终回答混在同一信息流。

问题：

  • 用户不知道哪些是结论；

  • 哪些是过程；

  • 哪些是内部分析；

  • 体验秩序混乱。

16. 体验验收 Checklist

设计一个 Agent Run 对话流时，可以用以下问题检查：

1. 用户能否第一时间看到最终结果？
2. 过程是否默认折叠，而不是污染结果？
3. 用户是否能展开查看执行过程？
4. 执行过程是否按阶段组织？
5. 节点是否使用任务语言，而不是工具语言？
6. 用户是否能继续下钻到节点详情？
7. 工具、命令、日志是否放在浮层或深层详情中？
8. 错误是否可见，但没有抢占主结果？
9. 完成态是否能帮助用户验收？
10. 交付物是否被当作对象展示？
11. 高风险动作是否前置确认？
12. 思考、执行、结果是否被清晰分离？

  • 思考、规划、执行节点如何逐步出现；

  • 节点状态如何变化；

2. 总体动态原则

Agent Run 的动态体验应遵循一条主线：

用户委托
→ Agent 开始理解
→ 生成执行计划
→ 执行节点逐步出现
→ 节点状态持续更新
→ 复杂事件可下钻查看
→ 任务完成
→ 结果交付
→ 过程折叠为可追溯入口

核心原则：

运行中，让用户感知过程还在推进；完成后，让用户优先看到干净结果。

3. 两种主要视图状态

Agent Run 在视觉上至少有两种主要视图状态。

3.1 执行过程态

任务尚未完成时，界面处于执行过程态。

此时用户最关心：

  • Agent 是否已经开始；

  • 当前正在做什么；

  • 是否还在推进；

  • 是否卡住；

  • 是否需要我确认；

  • 是否可以停止或补充要求。

执行过程态的主角是过程，但过程仍然需要被组织，而不是变成日志流。

3.2 结果交付态

任务完成后，界面切换为结果交付态。

此时用户最关心：

  • 最终结果是什么；

  • 交付物在哪里；

  • 哪些完成了；

  • 哪些部分完成或失败；

  • 下一步可以做什么。

结果交付态的主角是结果，执行过程默认折叠为入口。

核心规则：

执行中：过程优先可感知
完成后：结果优先可验收

4. 动态流程总览

Agent Run 的推荐动态流程如下。

Step 0 用户发送消息

Step 1 创建 Agent Run
- 显示 Agent 已开始处理
- 出现基础状态区
- 开始计时

Step 2 任务理解 / 规划
- 显示“任务理解中”或“正在拆解任务”
- 可逐步出现任务理解摘要
- 完成后生成第一个节点

Step 3 执行计划形成
- 展示预计执行阶段
- 阶段可以先以 pending 状态出现
- 当前阶段进入 running 状态

Step 4 节点逐步执行
- 当前节点持续更新
- 已完成节点收起为摘要
- 新节点逐步出现

Step 5 复杂事件出现
- 工具、技能、文件、命令等以事件摘要出现
- 详情默认不展开
- 用户可点击进入浮层

Step 6 异常 / 重试 / 恢复
- 轻量提示异常
- 展示重试或恢复状态
- 已恢复异常不抢占主流程

Step 7 任务完成
- 执行过程收束
- 结果生成
- 进入结果交付态

Step 8 用户追溯
- 点击执行过程入口
- 展开过程总览
- 展开节点
- 打开事件详情
- 进入工具 / 命令浮层

5. Step 0：用户发送消息

用户发送一条委托型消息后，系统应将其识别为一次 Agent Run 的开始。

示例：

此时界面不应只等待最终回答，而应准备进入任务执行体验。

设计重点：

  • 用户消息保留在主对话流；

  • Agent 回复区进入运行态；

  • 不要立即输出长篇假结果；

  • 不要只显示空泛的“Thinking...”。

  • 时间感；

  • 可继续观察；

  • 必要时可停止或补充要求。

6.3 不推荐

正在处理...

这类表达缺少状态信息，无法支撑长任务等待。

后续阶段在 Agent 确认需要时再出现。

8.3 建议规则

  • 简单任务：不必展示完整计划；

  • 中等任务：展示当前阶段 + 下一阶段；

  • 长任务：展示完整阶段列表；

  • 不确定任务：阶段逐步出现，避免承诺过早。

如果错误已恢复且不影响结果：

如果错误导致部分完成：

部分完成：
天气信息未能获得实时数据，已使用历史气候参考。

如果错误导致失败：

失败或受限：
文档生成失败，当前仅提供文本方案。

16.6 原始错误

原始错误不进入结果层。

应进入深层追溯：

错误详情 >
命令输出 >
原始日志 >

核心规则：

运行中说明正在处理什么问题；完成后说明问题是否影响结果；原始错误进入深层追溯。

17.4 确认后

17.5 拒绝后

继续生成旅行方案文档

18. 用户运行中控制

运行中，用户可以有有限控制权。

18.1 可提供操作

19. 部分完成状态

不是所有任务都只有成功或失败。

19.1 运行中部分完成

19.2 完成态部分完成

19.3 过程层说明

19.4 原始追溯

天气 API 超时
使用历史气候来源替代

20.1 自动跳过

20.2 用户选择跳过

22. 信息加载规则

22.1 推荐加载顺序

1. Run 状态

模式 B：过程生长

28. “思考过程”的展示规则

“思考过程”容易被误解，需要谨慎命名和分层。

28.1 推荐命名

优先使用：

28.2 可见内容

可以展示：

  • 目标理解；

  • 约束识别；

  • 任务拆分；

  • 选择依据摘要。

28.3 不默认展示

29.1 避免空泛

29.3 异常文案

异常文案要说明影响。

30. 典型交互链路

以下是一个标准追溯链路。

完成态
用户看到总结和交付物

点击执行过程
展开过程总览

点击节点
展开节点摘要

点击复杂事件
打开工具 / 技能浮层

点击命令详情
打开原始命令 / 输出

关闭浮层
回到节点

收起执行过程
回到结果

这个链路对应的设计目标是：

结果型用户不用看过程，审核型用户可以看节点，高级用户可以追到原始记录。

31. 动态体验验收 Checklist

设计或评审 Agent Run 动态流程时，可以检查：

1. 用户发起任务后，是否立刻知道任务已开始？
2. 运行中是否能看到当前阶段，而不是只有 Thinking？
3. 长任务是否能感知进度、耗时或阶段推进？
4. 执行节点是否逐步出现，而不是一次性堆满？
5. 当前运行节点是否突出？
6. 已完成节点是否能弱化或收起？
7. 复杂节点是否先展示事件摘要，而不是直接展示日志？
8. 工具、技能、命令是否通过浮层下钻？
9. 发生错误时，用户是否知道是否影响结果？
10. 已恢复错误是否轻提示，而不是抢占主流程？
11. 等待用户确认时，是否明确阻塞关系和可选动作？
12. 任务完成后，是否切换为结果优先？
13. 完成后执行过程是否默认折叠？
14. 用户是否能从结果逐级追溯到过程、节点、事件、原始记录？
15. 交付物是否在生成后被明确呈现？

33. 总结

Agent Run 的动态体验不是简单地“边想边输出”，而是一个有秩序的信息生成与收束过程：

运行中，逐步展示任务推进；
复杂处，先摘要再下钻；
出错时，说明影响并保留追溯；
需要用户时，明确等待与选择；
完成后，过程退后，结果前置；
想追溯的人，可以一层一层查到底。
